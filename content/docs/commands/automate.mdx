Commands for VCS event ingestion and reactive automation.

See [Automation Configuration](/docs/concepts/automation-configuration) for the automation layer design.

## `mori automate ingest`

Ingest VCS events into the local event store.

```bash
mori automate ingest git
mori automate ingest git --path /path/to/repo
```

### Behavior

- Scans VCS history for new events
- Normalizes to canonical event format
- Appends to local event store
- Updates cursor position

A commit that fails to parse does not stall the repo: it is recorded as a
`MalformedCommitSkipped` event and the cursor advances past it. Ingest failures
are classified and recorded — see [Ingest Health](/docs/guides/ingest-health).

## `mori automate reset-checkpoint`

Reset a project's ingest cursor. This is the recovery path when the stored
cursor is no longer in `HEAD`'s ancestry — typically after a force-push, rebase,
or other history rewrite, which surfaces as the `orphaned` ingest error class.

```bash
mori automate reset-checkpoint my-app
mori automate reset-checkpoint shinzui/my-app --to-head
mori automate reset-checkpoint my-app --to-commit 9f2c1ab
mori automate reset-checkpoint my-app --to-root
```

The project argument is a bare name, or `namespace/name` when the bare name is
ambiguous.

### Flags

| Flag | Description |
|------|-------------|
| `--to-head` | Reset the cursor to current `HEAD` (**default**) |
| `--to-commit SHA` | Reset to a specific commit; validated with `git cat-file -e` |
| `--to-root` | Re-ingest the entire repository from scratch |

Prefer `--to-head`: it clears the orphaned cursor and resumes from the current
tip. `--to-root` is heavy and re-emits the full history, which can produce
duplicate webhook deliveries to registered Mori Apps.

`mori observe --reingest` is an alias for the `--to-root` form.

## `mori automate run`

Run single-repo automation (ingest + subscriptions).

```bash
mori automate run
mori automate run --config path/to/config.dhall
mori automate run --path /path/to/repo
mori automate run --register
```

### Behavior

- Loads automation config from disk
- Ingests VCS events, then runs all subscriptions concurrently
- Matches events against selectors, triggers and executes reactions

### Flags

| Flag | Description |
|------|-------------|
| `--config`, `-c` | Path to automation config (default: `mori.automation.dhall`) |
| `--path` | Repository path (default: current directory) |
| `--register` | Also register with the daemon via event store |

## `mori automate daemon`

Run multi-repo automation daemon.

```bash
mori automate daemon
mori automate daemon --ingest-interval 60
mori automate daemon --queued-concurrency 6
mori automate daemon --metrics-port 9464
```

### Behavior

- Bootstraps config registry from `automation_registrations` projection
- Subscribes to `automationRegistration` category for live config updates
- Routes repository events to registered repos' automation configs
- Concurrent workers and projections for automation, execution, pending schedules, registry, tech radar, DDD, agent plans, workflow, registration, and app fan-out
- Runs the shibuya worker for legacy per-action `Schedule` plus the scheduled-reactions worker for per-reaction `schedule` deferrals
- Runs FIFO workers for `queued = True` automations. Each automation remains internally ordered, while distinct automations can drain concurrently
- Event-driven after ingest; the daemon also has a periodic auto-ingest loop for observed repos

See [Automation Daemon](/docs/guides/automation-daemon) for details.

### Flags

| Flag | Description |
|------|-------------|
| `--refresh-interval SECONDS` | Interval between config refresh cycles. Default: `60` |
| `--ingest-interval SECONDS` | Interval between auto-ingest cycles for observed projects. Default: `300`; use `0` to disable |
| `--queued-concurrency N` | Number of FIFO worker instances for `queued = True` automations. Default: `3` |
| `--serve` | Also serve the [HTTP API](/docs/commands/serve) from this daemon process |
| `--api-port PORT` | Port for the embedded HTTP API. Default: `8080`, or `$MORI_API_PORT` |
| `--metrics-port PORT` | Port for Kiroku's metrics, health, and subscription-status server, or `$MORI_METRICS_PORT`. Off when neither is set |

### Serving Kiroku's operator surface

`--metrics-port` starts Kiroku's own server, which exposes `/metrics`,
`/metrics/prometheus`, `/health/live`, `/health/ready`, and `/subscriptions`.
The command-line option takes precedence over `MORI_METRICS_PORT`; with neither
set the daemon opens no observability socket.

This server listens on **all interfaces**, unlike the loopback-first HTTP API —
expose it only on a trusted network or behind an authenticated proxy. See
[Automation Daemon › Subscription Observability](/docs/guides/automation-daemon#subscription-observability).

### Serving the HTTP API

Serving is opt-in: it is enabled by `--serve`, by an explicit `--api-port`, or
by setting `MORI_API_PORT`. With none of those the daemon opens no socket. The
server runs as one more concurrent leg on the daemon's *shared* pool and kiroku
store, and Ctrl-C cancels it along with the rest of the daemon. If no kiroku
store is configured the daemon prints `HTTP API: not served — no kiroku store
(set MORI_PG_CONNECTION_STRING)` and continues without it.

## `mori automate register`

Register the current repo's automation config with the daemon.

```bash
mori automate register
mori automate register --config path/to/config.dhall
mori automate register --path /path/to/repo
```

### Behavior

- Loads and validates automation config
- Writes both `ProjectRepoLinked` (so `mori.projects` records the repo) and `AutomationRegistered` events in one step
- Creates `mori/repo-id` if absent
- Idempotent — registering twice is a no-op

A separate `mori observe` step is no longer required to make a registered repo
receive signals. Use `mori observe` when you only want a project's identity
recorded for auto-ingest without attaching an automation config.

### `--path` is authoritative

`--path <dir>` is the authoritative repo root: the config file is read from
`<dir>` (so `--config` resolves relative to it), and the repo TypeID is
derived from `<dir>`. This makes it impossible to silently register repoA's
config against repoB's id by running from the wrong working directory. The
same rule applies to `update`, `deregister`, `run`, and `ingest git`.

## `mori automate deregister`

Remove automation registration for a repo.

```bash
mori automate deregister
mori automate deregister --path /path/to/repo
```

### Behavior

- Writes `AutomationDeregistered` event
- Daemon stops processing events for this repo
- Idempotent — deregistering an unregistered repo is a no-op

## `mori automate update`

Update a registered automation config after editing the config file.

```bash
mori automate update
mori automate update --config path/to/config.dhall
```

### Behavior

- Re-reads config from disk, computes new hash
- Writes `AutomationConfigUpdated` event if hash differs
- Daemon picks up changes live (no restart needed)
- Heals state from older daemon builds: if a registered repo is missing its `mori.projects` row (an artifact of pre-EP-4 register flows), `update` re-emits `ProjectRepoLinked` so the row appears
- Idempotent — updating with same config is a no-op

## `mori automate list`

List all registered automation configs.

```bash
mori automate list
mori automate list --json
```

## `mori automate migrate`

One-time migration: discover all projects with automation configs and register them.

```bash
mori automate migrate
```

### Behavior

- Scans all registered projects for `mori.automation.dhall`
- Registers each discovered config via the event store
- Idempotent — safe to run multiple times

## `mori automate migrate-named`

One-time migration: import legacy registrations into the named `Automation`
aggregate.

```bash
mori automate migrate-named
mori automate migrate-named --dry-run
mori automate migrate-named --apply --i-stopped-the-daemon
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Report the changes without writing (the default) |
| `--apply` | Apply the import and carrier rewrites |
| `--i-stopped-the-daemon` | Required with `--apply`: acknowledge that no automation daemon is running |

`--apply` rewrites carriers that a running daemon would be reading concurrently,
so `--i-stopped-the-daemon` is an acknowledgement rather than a switch. Run the
default dry run first and read what it reports.

## `mori automate inspect`

Inspect automation configuration.

```bash
mori automate inspect
mori automate inspect --json
```

### Output

- Automation config status and hash
- Execution policy (local/CI)
- Registered event selectors
- Declared [`Decision`](/docs/guides/automation#decision) routes, when a reaction
  has any

## `mori automate explain`

Explain why a reaction did or did not run for a specific event.

```bash
mori automate explain <global-position>
mori automate explain <global-position> --config path/to/config.dhall
mori automate explain <global-position> --json
```

### Flags

| Flag | Description |
|------|-------------|
| `--config`, `-c` | Path to automation config |
| `--json` | JSON output |

`--json` includes the declared
[`Decision`](/docs/guides/automation#decision) routes on matched reactions, so
you can confirm which outcome would route where before the producer ever runs.

## `mori automate generate`

Generate automation config templates.

```bash
mori automate generate <template>
mori automate generate <template> --output path/to/output.dhall
```
