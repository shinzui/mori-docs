Commands for querying and managing the local project registry.

## `mori registry list`

List all registered projects.

```bash
mori registry list
mori registry list --json
mori registry list --type library
mori registry list --origin ThirdParty
mori registry list --lifecycle maintenance
mori registry list --namespace shinzui
mori registry list --domain Automation
mori registry list --group my-group
mori registry list --docs-only
mori registry list --observed
```

### Flags

| Flag | Description |
|------|-------------|
| `--json` | JSON output |
| `--type` | Filter by project type |
| `--origin` | Filter by origin (`Own`, `ThirdParty`, `Fork`, `Vendored`) |
| `--lifecycle` | Filter by lifecycle (`active`, `experimental`, `maintenance`, `deprecated`, `archived`; case-insensitive) |
| `--namespace`, `-n` | Filter by namespace |
| `--domain` | Filter by domain tag (repeatable; AND semantics, case-insensitive) |
| `--group` | Filter by group membership (single value; see `mori registry group`) |
| `--docs-only` | Show only docs-only projects (no packages) |
| `--observed` | Show only projects with a linked repository (`repo_id` set by `mori observe`) |
| `--has-templates` | Show only projects shipping at least one seihou template |

All filters compose with AND semantics. Unlike the exact-match `--type` and
`--origin` filters, `--lifecycle` matches case-insensitively, because lifecycle
is stored capitalized but is natural to type in lowercase.

The table includes a **Lifecycle** column, with `Deprecated` styled pale red and
`Maintenance` pale yellow so both stand out in a long listing. The same styling
appears in `mori show`, `mori registry show`, and `mori registry search`. JSON
output carries `lifecycle` plus a `deprecation` object (`alternative` and
`details`, `null` when absent) — see
[Deprecation guidance](/docs/guides/schema-reference#deprecation).

## `mori registry show`

Show details of a registered project. Accepts a project name, `namespace/name`,
or `project:package` for package-qualified lookup. The `--full` flag displays
all project data including packages, dependencies, bundles, docs, skills,
subagents, extensions, and cookbook entries.

```bash
mori registry show <project>
mori registry show <namespace/name>
mori registry show <project:package>
mori registry show <project> --json
mori registry show <project> --full
mori registry show <project> --full --json
```

### Flags

| Flag | Description |
|------|-------------|
| `--json` | JSON output |
| `--full` | Show full details including packages, dependencies, bundles, docs, skills, subagents, extensions, and cookbook entries. Prints a [canonical `mori://` ref](/docs/concepts/canonical-refs) under each artifact (text mode) or as a `canonicalRef` field on each artifact object (JSON mode) |

Both the summary and `--full` renderings print the project's **Lifecycle** and,
when present, its `Alternative` / `Details` deprecation guidance; JSON output
carries the same under `lifecycle` and `deprecation`. In `--full` text output
each package shows its own lifecycle, marked `(inherited)` when the package
declares no override, followed by any package-specific guidance.

## `mori registry search`

Search the local registry.

```bash
mori registry search <query>
mori registry search <query> --domain Platform
mori registry search <query> --domain Platform --domain Internal
mori registry search <query> --json
```

Matches against project name, namespace, and package names.

### Flags

| Flag | Description |
|------|-------------|
| `--json` | JSON output |
| `--domain DOMAIN` | Filter by domain tag. Repeatable; filters compose with AND semantics and match case-insensitively |

## `mori registry dependents`

List registered projects or packages that depend on a project or dependency
name. The reference can be a bare project name, `namespace/name`, or a library
name such as `effectful`.

```bash
mori registry dependents <ref>
mori registry dependents shinzui/rei
mori registry dependents effectful --packages
mori registry dependents effectful --scope test
mori registry dependents effectful --json
```

### Flags

| Flag | Description |
|------|-------------|
| `--json` | JSON output |
| `--packages` | Show per-package dependency edges instead of a project rollup |
| `--scope SCOPE` | Only show edges with this dependency scope, such as `regular`, `dev`, `test`, or `build` |

## `mori registry domains`

List distinct domain tags and project counts.

```bash
mori registry domains
mori registry domains --json
```

Use repeatable `--domain` filters on `registry list` and `registry search` to
find projects carrying every requested domain. Matching is case-insensitive.

### Flags

| Flag | Description |
|------|-------------|

| `--kind` | Filter by doc kind (`reference`, `guide`, `cookbook`, `spec`, `runbook`, `notes`) |

## `mori registry bundles`

List a project's registered OKF knowledge bundles. These are distinct from
`PackageBundle` entries in `mori.dhall`: OKF bundles describe directories of
Markdown knowledge concepts and carry canonical `mori://<ns>/<name>/okf/<bundle>`
refs.

```bash
mori registry bundles <project>
mori registry bundles <namespace/name>
mori registry bundles <project> --json
```

### Flags

| Flag | Description |
|------|-------------|
| `--json` | JSON output |

## `mori registry concepts`

List or search [OKF concepts](/docs/guides/okf). The command has two
mutually-exclusive modes: a project argument walks that project's bundle
directories live from disk, while `--search` / `--id` query the concept index
stored at registration time across every registered project.

```bash
# Live, one project, always current
mori registry concepts <project>
mori registry concepts <project> --bundle team-knowledge
mori registry concepts <project> --json

# Indexed, cross-project
mori registry concepts --search postgres
mori registry concepts --search postgres --json
mori registry concepts --id ADR-7
mori registry concepts --id ADR-7 --json
```

### Flags

| Flag | Description |
|------|-------------|
| `NAME` | Project name or `namespace/name` — live disk mode |
| `--bundle BUNDLE` | Live mode only: list concepts from the named OKF bundle |
| `--search TERM` | Search indexed concepts across all registered bundles |
| `--id DOCUMENT-ID` | Find every indexed concept with this exact document ID |
| `--json` | JSON output |

`--search` matches canonical concept IDs, document IDs, labels, and
descriptions. `--id` returns *every* match, because a document-ID handle may be
legitimately reused across bundles. Indexed rows include the project, bundle,
concept ID, optional document ID, label, type, description, resource, tags, and
the nested canonical `ref`.

Indexed results reflect the last `mori observe` / `mori register`; editing
concept Markdown does not change them until the project is re-registered.

## `mori registry exec`

Run the same command in every project registered in the local registry. Each invocation has its working directory set to the project's local path, so relative arguments behave as if you `cd`'d to the project yourself. Anything after `--` is passed verbatim — mori does not wrap it in `nix develop` and does not interpret it as a shell command.

```bash
mori registry exec -- git fetch --all
mori registry exec --group platform -- just lint
mori registry exec --namespace shinzui -- bun outdated
mori registry exec --type library -- cabal build all
mori registry exec --origin own -- just check
mori registry exec --filter "shinzui/*-kit" -- just lint
mori registry exec --jobs 4 -- just check
mori registry exec --fail-fast -- just check
mori registry exec --dry-run -- anything
mori registry exec --json -- git rev-parse HEAD | jq '.[0]'
```

### Flags

| Flag | Description |
|------|-------------|
| `--group NAME` | Only visit projects that are members of the named registry group |
| `--namespace NS`, `-n` | Filter by namespace (mirrors `registry list`) |
| `--type T` | Filter by project type |
| `--origin O` | Filter by origin (`own`, `third_party`, etc.) |
| `--filter GLOB` | Match qualified `<namespace>/<name>` (`*` and `?` wildcards) |
| `--jobs N` | Run up to N project commands concurrently (default 1, streaming) |
| `--fail-fast` | Abort at the first non-zero project; remaining projects report `not-run` |
| `--dry-run` | Print the projects the filter set would visit without spawning the command |
| `--json` | Emit a JSON array of `{project, path, outcome, …}` objects to stdout |

Filters compose: `--group platform --namespace shinzui` visits only the intersection. In parallel mode (`--jobs N`), per-project output blocks are deferred and printed in input order; the summary table follows. `--fail-fast` lets in-flight workers finish but short-circuits unstarted projects to `not-run`.

After every project has been visited, mori prints a summary table with status, exit code, and duration. If any project's command exited non-zero, a "failed" block follows the summary with the tail of each failure's stderr inlined. The mori process itself exits 0 if every executed command succeeded, 1 if any failed — so `mori registry exec -- just lint && echo all green` works as expected.

Projects without a local path, or whose path no longer exists on disk, are reported as `skipped` and do not affect the exit code.

## `mori registry reregister`

Force re-register all registered projects.

```bash
mori registry reregister
mori registry reregister --dry-run
mori registry reregister --type library
mori registry reregister --namespace shinzui
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Show what would be re-registered without doing it |
| `--type` | Filter by project type |
| `--namespace`, `-n` | Filter by namespace |

## `mori registry templates`

Browse seihou templates across the registry at the *template* grain — one row per template. Answers cross-project questions like "which projects ship a `haskell`-tagged template?" without scrolling through per-project `show --full` output.

```bash
mori registry templates list
mori registry templates list --json
mori registry templates list --tag haskell
mori registry templates list -n shinzui
mori registry templates show <namespace>/<name>/<template>
mori registry templates show <namespace>/<name>/<template> --json
```

### Flags (`list`)

| Flag | Description |
|------|-------------|
| `--json` | JSON output |
| `--tag TAG` | Keep templates whose `tags` list contains `TAG` (exact match) |
| `--namespace`, `-n` | Keep templates whose project is in the given namespace |

`templates show` takes a three-segment reference `<namespace>/<name>/<template>`. The parser requires exactly three non-empty segments and reports a descriptive error otherwise. Non-existent templates exit non-zero with `Template not found:` on stderr.

## `mori registry upgrade-schema`

Walk the registry and upgrade every registered local project whose `schema_hash` diverges from the CLI's pinned schema version. Per project, the driver runs `mori schema upgrade`, then `mori schema migrate --apply` on `mori.dhall` and any known extension files (`mori/cookbook.dhall`, `mori/tech-radar.dhall`), then `mori validate`. One project's failure does not abort the others.

```bash
mori registry upgrade-schema
mori registry upgrade-schema --dry-run
mori registry upgrade-schema --filter "acme/*"
mori registry upgrade-schema --all
mori registry upgrade-schema --commit
mori registry upgrade-schema --allow-dirty
```

### Flags

| Flag | Description |
|------|-------------|
| `--dry-run` | Report what would change without touching any files |
| `--filter GLOB` | Only act on projects whose `<namespace>/<name>` matches `GLOB` (supports `*` and `?`) |
| `--all` | Include projects already on the current schema (default: only stale) |
| `--commit` | Create a git commit in each upgraded project (default: leave changes unstaged) |
| `--allow-dirty` | Upgrade projects even if their working tree has uncommitted changes |

Projects without a `localPath`, or whose path is missing on disk, are reported as skipped. See [Schema Migrations](/docs/guides/schema-migrations) for the per-project migration semantics.

## `mori registry group`

Manage first-class registry **groups** — named, event-sourced collections of projects with optional attached packages, docs, and JSON extension data. Unlike domain tags, groups have their own identity: they can be renamed without re-registering members, and they carry their own metadata.

```bash
mori registry group create <name> [--description TEXT]
mori registry group list [--json]
mori registry group show <name> [--json]
mori registry group describe <name> [DESCRIPTION]
mori registry group rename <old> <new>
mori registry group delete <name>

mori registry group add <name> <project>...
mori registry group remove <name> <project>...
mori registry group members <name> [--json]

mori registry group attach-package <name> <project:package>
mori registry group detach-package <name> <project:package>
mori registry group attach-doc <name> <project> <doc-path>
mori registry group detach-doc <name> <project> <doc-path>
mori registry group set-extension <name> <key> <json-value>
mori registry group unset-extension <name> <key>
```

Group membership shows up in `registry show` (as a `Groups:` line / JSON `groups` array) and is filterable via `registry list --group <name>`.

## `mori registry remove`

Remove a project from the local registry. Cleans up all associated data
including package dependencies. Warns if other projects depend on the one being
removed.

```bash
mori registry remove <project>
mori registry remove <project> --force
mori registry remove <project> --dry-run
```

### Flags

| Flag | Description |
|------|-------------|
| `--force`, `-f` | Skip confirmation prompt |
| `--dry-run` | Preview what would be removed without doing it |

## `mori registry open-doc`

Open a project doc in your editor. Supports fzf-based interactive project and
doc selection, and accepts a full [canonical `mori://`
ref](/docs/concepts/canonical-refs).

```bash
mori registry open-doc
mori registry open-doc <project>
mori registry open-doc <project> <doc-key>
mori registry open-doc mori://shinzui/streamly/docs/effects-cookbook
```

Uses `$EDITOR` (or `$VISUAL`, falling back to `vi`). URLs are opened with the
system `open` command.
