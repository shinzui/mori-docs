This document defines **`mori.automation.dhall`**, the configuration file that enables **reactive behavior** in Mori.

It is intentionally **separate** from `mori.dhall`, which defines **project identity and dependencies**.

## Purpose and Separation of Concerns

Mori uses **two distinct configuration layers**:

### `mori.dhall` (Project Manifest)

* Describes **what the project is**
* Declares ownership, identity, dependencies
* Used for documentation, indexing, and registry purposes
* Safe to load eagerly

### `mori.automation.dhall` (Automation Policy)

* Describes **what Mori should do** in response to events
* Declares event selectors, reactions, execution constraints
* Operational and security-sensitive
* Loaded only during repository interrogation

> A repository may have `mori.dhall` without ever enabling automation.

## Relationship Between the Two Files

`mori.automation.dhall` **must explicitly reference** `mori.dhall`.

This establishes a clear dependency direction:

```
mori.automation.dhall ───▶ mori.dhall
```

Automation **cannot exist without project identity**, but project identity does not imply automation.

## Canonical Structure

```haskell
{ project : ./mori.dhall
, automation : Automation
}
```

This makes the linkage explicit and auditable.

## Automation Schema

```haskell
Automation =
{ events : List EventSelector
, reactions : List Reaction
, execution : ExecutionPolicy
}
```

No project metadata is duplicated here.

## Event Selection

Automation reacts only to **explicitly selected events**.

```haskell
EventSelector =
  < ChangesetObserved : ChangesetObservedSelector
  | ChangesetRewritten : ChangesetRewrittenSelector
  | RefObserved : RefObservedSelector
  >
```

### ChangesetObserved Selector

```haskell
ChangesetObservedSelector =
{ vcs : Optional < Git | Jujutsu >
, branches : Optional (List Text)
, paths : Optional (List Text)
, messagePatterns : Optional (List Text)
, trailerPatterns : Optional (List { mapKey : Text, mapValue : Text })
}
```

Notes:

* `branches` are **observational filters**, not authoritative
* `paths` enables cheap change-based triggering
* `trailerPatterns` matches git trailer key/value pairs (all entries must match)
* `messagePatterns` matches commit message content

### ChangesetRewritten Selector

```haskell
ChangesetRewrittenSelector =
{ reasons : Optional (List < Rebase | Amend | Squash | ConflictResolution >)
}
```

### RefObserved Selector

```haskell
RefObservedSelector =
{ kinds : Optional (List < Branch | Tag | Bookmark >)
, names : Optional (List Text)
}
```

## Reactions

Reactions declare **what Mori does** when selected events occur.

```haskell
Reaction =
{ name : Text
, when : List EventSelector
, run : ReactionAction
}
```

Rules:

* Reactions are declarative
* No implicit control flow
* No access to mutable global state

## Reaction Actions

```haskell
ReactionAction =
  < RunCommand : CommandAction
  | EmitEvent : EmitEventAction
  | Notify : NotifyAction
  | Schedule : ScheduleAction
  >
```

### RunCommand

```haskell
CommandAction =
{ command : Text
, args : List Text
, workingDir : Optional Text
, timeout : Optional Integer
, env : List { mapKey : Text, mapValue : Text }
}
```

Constraints:

* No shell expansion
* Arguments are explicit and deterministic
* Fields support `{{variable}}` event-data interpolation (see [Automation guide](/docs/guides/automation))
* Every `RunCommand` is spawned as `nix develop --command <command> <args…>` against the **target repo's** flake — write `command = "just"`, `args = ["test"]`, not `/bin/bash -lc "cd … && just test"`. See [Nix devshell requirement](#nix-devshell-requirement) below.

### EmitEvent

Records an event-emission intent in the reaction result. The configured stream
and event type are preserved for downstream handling; the executor does not
directly append a custom event itself.

```haskell
EmitEventAction =
{ eventType : Text
, payload : Text
}
```

### Notify

```haskell
NotifyAction =
{ channel : < Slack | Email | Webhook >
, target : Text
}
```

### Schedule

```haskell
ScheduleAction =
{ delaySeconds : Natural
, action : ReactionAction
}
```

Allows deferred execution without embedding queue semantics.

## Execution Policy

```haskell
ExecutionPolicy =
{ allowLocal : Bool
, allowCI : Bool
, maxConcurrency : Natural
}
```

Used to enforce:

* Safety boundaries
* CI vs local execution rules
* Resource limits

## Validation Rules

An automation config is invalid if:

* A reaction references no events
* Execution policy forbids all environments
* Project reference cannot be resolved

An automation config with no reactions is valid but results in no-op behavior.

Invalid automation blocks activation but does not invalidate `mori.dhall`.

## Example Minimal `mori.automation.dhall`

```haskell
{ project = ./mori.dhall
, automation =
  { events = []
  , reactions = []
  , execution =
    { allowLocal = True
    , allowCI = False
    , maxConcurrency = 1
    }
  }
}
```

## Interrogation Semantics

During repository interrogation:

1. Mori loads `mori.dhall` (project identity)
2. Mori checks for `mori.automation.dhall`
3. If present and valid, automation is activated
4. If absent, repository remains non-reactive

This preserves safe defaults.

## Design Invariants

1. Automation is opt-in
2. Identity precedes behavior
3. Configuration is domain data
4. All effects are explainable via events
5. Replay produces identical behavior

## Why This Split Matters

This separation enables:

* Indexing projects without running code
* Safer CI defaults
* Org-wide policy enforcement
* Clear security boundaries
* Easier mental models

> **Projects declare who they are. Automation declares what happens.**

## Relationship to Mori Architecture

* Loaded during repository interrogation
* Emitted as `MoriAutomationObserved` event
* Drives reactor behavior
* References but never duplicates project metadata

## Resolved Design Decisions

The following design questions have been resolved in the implementation:

* **Environment variables**: Explicit via the `env` field on `RunCommand`. Not inherited from parent process.
* **Command templating**: `{{variable}}` syntax for event-data interpolation. See [Automation guide](/docs/guides/automation).
* **Schedule persistence**: Scheduled actions use pgmq (durable PostgreSQL queue) with shibuya workers. Survives restarts.
* **Idempotency tracking**: Tracked via event stream position and reaction event IDs.
* **Error handling**: Reactions emit `ReactionCompleted` or `ReactionFailed` events. Visible via `mori reaction list` and `mori reaction show`.

## Nix devshell requirement

Every `RunCommand` action is executed as `nix develop --command CMD ARGS…`
with cwd set to the target repo root. The **target** repo's flake is
consulted — not the source repo's, and not mori's own flake.

The target repo must have a `flake.nix` at its root with a default devShell
(i.e. `devShells.${system}.default`) that provides the binaries your command
references. Without that, the reaction fails with `error: flake … not found`
or `error: unable to find attribute 'default' in devShells`.

Minimal `flake.nix` suitable for automation-target repos:

```nix
{
  description = "example target repo";
  inputs.nixpkgs.url = "github:nixos/nixpkgs/nixpkgs-unstable";
  inputs.flake-utils.url = "github:numtide/flake-utils";
  outputs = { self, nixpkgs, flake-utils }:
    flake-utils.lib.eachDefaultSystem (system:
      let pkgs = import nixpkgs { inherit system; };
      in {
        devShells.default = pkgs.mkShell {
          nativeBuildInputs = [ pkgs.just pkgs.bun ];
        };
      });
}
```

Add every binary your `RunCommand` actions invoke to `nativeBuildInputs`.

Why this matters for the daemon: when `mori automate daemon` runs under
launchd, the inherited `PATH` is minimal (`/usr/bin:/bin:/usr/sbin:/sbin`) —
nix-installed binaries would not be reachable directly. The devShell wrapper
sidesteps that, so you do not need to wrap commands in `/bin/bash -lc`.

## Config update propagation

A `ReactionTriggered` event captures the full action payload at trigger
time. Editing `mori.automation.dhall` mid-flight does not rewrite already-
triggered reactions — only reactions triggered **after** the daemon
observes the new config (via the registration subscription, typically
within seconds) see the edit.

If a reaction fired with a stale payload, fix the config, run `mori
automate update`, then wait for a fresh event. There is no in-place retry
with the new payload — the original event is immutable.
