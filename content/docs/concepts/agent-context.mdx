Agent context assembly is a **core requirement** of Mori, not an optional feature. It provides structured, queryable context to coding agents so they can find documentation, source code, standards, and examples on the local filesystem.

## Problem Statement

Coding agents need reliable answers to questions like:

* Where is the documentation for this dependency?
* Where is the source code I can read to understand this API?
* What standards apply to this type of project?
* Are there cookbooks or examples for common patterns?

Today, this context is assembled manually via prompts, which is:

* Error-prone (paths change, docs move)
* Time-consuming (repeated for every task)
* Inconsistent (different engineers assemble different context)

Mori solves this by making **dependency knowledge queryable**.

## Core Concept: Dependency Documentation Graph

Mori models dependencies not just as package names, but as **nodes with attached knowledge**:

```
Dependency
  ├── identity (name, source, version)
  ├── localPath (where the code lives)
  └── docs (curated documentation references)
        ├── official docs
        ├── overlay docs (team-specific)
        └── cookbooks / examples
```

This graph is queryable by agents via CLI or structured output.

## Dependency Projects & Local Registry

### The Problem with Per-Project Paths

If every project had to specify `localPath` for each dependency, we'd have:
* Duplication across projects
* Path drift when checkouts move
* No single source of truth

### Solution: Dependencies as Registered Projects

Dependencies become **first-class Mori projects** registered with the **local registry**.

#### Example: Streamly Ecosystem

Create a wrapper project for the streamly ecosystem:

```
streamly-project/
├── streamly/           # git clone of streamly
├── streamly-core/      # git clone of streamly-core
├── mori.dhall          # project manifest
└── docs/
    ├── folds-guide.md
    ├── streaming-patterns.md
    └── performance-notes.md
```

#### `streamly-project/mori.dhall`

```haskell
{ project =
    { name = "streamly-project"
    , namespace = "acme"
    , type = < Library >
    , description = Some "Streamly ecosystem with curated docs"
    , language = < Haskell >
    , lifecycle = < Active >
    , domains = [ "Streaming" ]
    , owners = [ "platform-team" ]
    }

, repos = []

, packages =
    [ { name = "streamly"
      , type = < Library >, language = < Haskell >
      , path = Some "./streamly"
      , description = Some "Streaming library"
      , visibility = < Public >
      , runtime = { deployable = False, exposesApi = False }
      , dependencies = [], docs = [], config = []
      }
    , { name = "streamly-core"
      , type = < Library >, language = < Haskell >
      , path = Some "./streamly-core"
      , description = Some "Core streaming primitives"
      , visibility = < Public >
      , runtime = { deployable = False, exposesApi = False }
      , dependencies = [], docs = [], config = []
      }
    ]

, bundles =
    [ { name = "streamly"
      , description = Some "Streamly + streamly-core"
      , packages = [ "streamly", "streamly-core" ]
      , primary = "streamly"
      }
    ]

, dependencies = []
, apis = []
, agents = []
, standards = []

, docs =
    [ { key = "folds-guide"
      , kind = < Guide >, audience = < User >
      , description = Some "Deep dive into Streamly folds"
      , location = < LocalFile "./docs/folds-guide.md" >
      }
    , { key = "streaming-patterns"
      , kind = < Cookbook >, audience = < User >
      , description = Some "Common streaming patterns"
      , location = < LocalFile "./docs/streaming-patterns.md" >
      }
    , { key = "upstream-docs"
      , kind = < Reference >, audience = < User >
      , description = Some "Streamly haddocks"
      , location = < RepoPath "./streamly/docs" >
      }
    ]
}
```

#### Register with Local Registry

```bash
cd streamly-project
mori register --local
```

Now the local registry knows:
* `streamly-project` exists
* Its filesystem location
* What packages it contains
* What documentation is available

### Resolution Flow

When a service declares a dependency:

```haskell
-- payment-service/mori.dhall
{ dependencies = [ "streamly" ] }
```

Resolution:

```
1. Service references "streamly"
2. Mori queries local registry
3. Registry returns: streamly-project @ /Users/dev/oss/streamly-project
4. Agent gets filesystem paths to code + docs
```

```bash
mori deps locate streamly
```

```json
{
  "name": "streamly",
  "resolvedFrom": "local-registry",
  "project": "streamly-project",
  "projectPath": "/Users/dev/oss/streamly-project",
  "packagePath": "/Users/dev/oss/streamly-project/streamly",
  "docs": [
    { "key": "folds-guide", "path": "/Users/dev/oss/streamly-project/docs/folds-guide.md" },
    { "key": "streaming-patterns", "path": "/Users/dev/oss/streamly-project/docs/streaming-patterns.md" }
  ]
}
```

### Registry Hierarchy

```
Local Registry (machine-specific)
       ↓ fallback
Global Registry (org-wide, optional)
       ↓ fallback
Not Found
```

* Local registry is authoritative for development
* Global registry provides org-wide defaults
* Services don't hardcode paths; they reference by name

### `mori.local.dhall` (Optional Overrides)

For edge cases where per-project overrides are needed:

```haskell
-- mori.local.dhall (gitignored)
-- Overrides for this specific project only

{ dependencyOverrides =
    [ { name = "streamly"
      , extraDocs =
          [ { key = "my-notes"
            , location = < LocalFile "/Users/dev/personal/streamly-notes.md" >
            }
          ]
      }
    ]
}
```

This is rare -- most context comes from the registry.

## Package Bundles

Some packages are only useful together. Streamly without streamly-core, or effectful without effectful-core, isn't practical.

### PackageBundle Schema

```haskell
-- PackageBundle.dhall
{ name : Text                    -- bundle name (e.g., "streamly")
, description : Optional Text
, packages : List Text           -- packages included (e.g., ["streamly", "streamly-core"])
, primary : Text                 -- the "main" package for imports
}
```

### Example: Streamly Bundle

```haskell
-- in streamly-project/mori.dhall

{ project = { name = "streamly-project", ... }

, packages =
    [ { name = "streamly", path = Some "./streamly", ... }
    , { name = "streamly-core", path = Some "./streamly-core", ... }
    ]

, bundles =
    [ { name = "streamly"
      , description = Some "Streamly streaming library"
      , packages = [ "streamly", "streamly-core" ]
      , primary = "streamly"
      }
    ]
}
```

### Resolution Semantics

When a service declares:

```haskell
{ dependencies = [ "streamly" ] }
```

Mori resolves:
1. Look up "streamly" in registry
2. Find it's a bundle in streamly-project
3. Return paths to **all packages in the bundle**

This avoids the need to list every sub-package explicitly.

### Referencing Specific Packages

For fine-grained control:

```haskell
{ dependencies =
    [ "streamly"              -- gets the bundle (streamly + streamly-core)
    , "hasql:hasql-pool"      -- gets only hasql-pool, not the full bundle
    ]
}
```

The `project:package` syntax allows opting out of bundle expansion.

## Documentation Types

### DocKind (extended)

```haskell
< Reference    -- API reference, module docs
| Guide        -- Conceptual guide, tutorial
| Cookbook     -- Recipe-based examples
| Spec         -- Formal specification
| Runbook      -- Operational procedures
| Notes        -- Internal notes, observations
>
```

### DocLocation

```haskell
< LocalFile : Text      -- absolute or relative path
| LocalDir : Text       -- directory of docs
| Url : Text            -- external URL
| RepoPath : Text       -- path within dependency's repo
>
```

## Standards and Cookbooks

Beyond per-dependency docs, projects can declare **standards** that apply broadly, and cookbooks as `docs` entries:

```haskell
-- in mori.dhall
{ standards =
    [ "backend-architecture"
    , "api-guidelines"
    , "haskell-conventions"
    ]

, docs =
    [ { key = "error-handling"
      , kind = < Cookbook >, audience = < Internal >
      , description = Some "Error handling patterns"
      , location = < LocalFile "docs/cookbooks/errors.md" >
      }
    , { key = "streaming-patterns"
      , kind = < Cookbook >, audience = < Internal >
      , description = Some "Common streaming patterns"
      , location = < LocalFile "docs/cookbooks/streaming.md" >
      }
    ]
}
```

Standards are resolved from:
1. Local checkout (if available)
2. Mori registry (if registered)

## Agent Interrogation Interface

```bash
mori deps locate streamly
```

Output:
```json
{
  "name": "streamly",

  "source": { "type": "Hackage", "version": ">= 0.9" },
  "docs": [
    {
      "key": "modules",

      "key": "internal-guide",
      "kind": "Guide",
```

```bash
mori deps docs streamly
```

## Concrete Example: Haskell Service

A Haskell service using hasql, streamly, and effectful.

### Step 1: Set Up Dependency Projects

Create wrapper projects for each ecosystem:

```
~/oss/
├── streamly-project/
│   ├── streamly/
│   ├── streamly-core/
│   ├── mori.dhall
│   └── docs/
├── effectful-project/
│   ├── effectful/
│   ├── effectful-core/
│   ├── mori.dhall
│   └── docs/
└── hasql-project/
    ├── hasql/
    ├── hasql-pool/
    ├── mori.dhall
    └── docs/
```

Register each:

```bash
cd ~/oss/streamly-project && mori register --local
cd ~/oss/effectful-project && mori register --local
cd ~/oss/hasql-project && mori register --local
```

### Step 2: Service Declares Dependencies

```haskell
-- payment-service/mori.dhall

{ project =
    { name = "payment-service"
    , namespace = "acme"
    , type = < Application >
    , description = Some "Core payment processing service"
    , language = < Haskell >
    , lifecycle = < Active >
    , domains = [ "Payments" ]
    , owners = [ "fintech-platform" ]
    }

, repos = []

, packages = []
  -- For simple single-package services, the project-level fields suffice.

, bundles = []

, dependencies =
    [ "streamly"      -- resolved via registry
    , "effectful"     -- resolved via registry
    , "hasql"         -- resolved via registry
    ]

, apis = []

, agents =
    [ { role = "backend-refactor"
      , description = Some "Refactor Haskell service code"
      , includePaths = [ "src" ]
      , excludePaths = [ "dist-newstyle" ]
      , relatedPackages = []
      }
    ]

, standards = [ "backend-architecture", "haskell-conventions" ]

, docs =
    [ { key = "db-patterns", kind = < Cookbook >, audience = < Internal >
      , description = Some "Database access patterns"
      , location = < LocalFile "docs/db-patterns.md" >
      }
    , { key = "effect-patterns", kind = < Cookbook >, audience = < Internal >
      , description = Some "Effectful patterns"
      , location = < LocalFile "docs/effects.md" >
      }
    ]
}
```

Note: No `localPath` declarations for dependencies. The registry resolves them. Cookbooks are modeled as `docs` entries with `kind = Cookbook`.

For richer cookbook classification, projects can add a `mori/cookbook.dhall` file using the cookbook schema extension. When present, `mori agent context` includes a `cookbookCatalog` field with structured metadata — content type, topics, related packages, and language — so agents can select the right cookbook without reading every file. See [Extensions](/docs/guides/extensions) for details.

## Design Principles

1. **Declarative, not imperative**: Context is derived from configuration, not scripts
2. **Local-first**: Works offline with local checkouts
3. **Overlay model**: Machine-specific paths don't pollute shared config
4. **Structured output**: JSON for agents, human-readable for developers
5. **Queryable**: Fine-grained queries, not monolithic dumps

## Implementation Phases

### Phase 1: Local-First (Current Focus)

* Local registry as database-backed service
* Manual creation of dependency wrapper projects
* Manual registration via `mori register --local`
* Works entirely offline

### Phase 2: Global Registry

* Any project with `mori.dhall` can be registered globally
* Local registry becomes a performance cache
* New developers bootstrap by syncing from global registry
* Local still authoritative for doc updates and customization

### Phase 3: Version Pinning

* Third-party dependency version alignment
* Ensure registered wrapper matches what services actually use
* Version-aware doc resolution

## Open Questions

* **Doc freshness**: How to detect stale docs when upstream repos update?
* **Standards distribution**: How are org-wide standards distributed and versioned?
* **Agent context caching**: Should assembled context be cached for performance?
* **Bundle conflicts**: What if two projects define bundles with the same name?

### Resolved

* **Registry storage**: PostgreSQL projections derived from events. See [Event Sourcing](/docs/concepts/event-sourcing).
* **Cookbooks**: Modeled as `docs` entries with `kind = Cookbook` rather than a separate field.
* **Project-level dependencies**: `List Text` at project root, resolved by name via registry.
