Every artifact owned by a registered project — docs, packages, repos, skills,
subagents, APIs, cookbook entries, seihou templates, and OKF bundles — has a stable
canonical identifier in the `mori://` URI scheme. The CLI accepts canonical
refs as input wherever it makes sense, prints them in `--full` and `--json`
output, and the schema can store them in any field typed as `DocLocation`.

## Forms

Canonical (always emitted, always accepted on input):

```
mori://<namespace>/<name>/<kind-plural>[/<key>][#<anchor>]
```

Compact alias (input only — canonical form is what gets stored and printed):

```
<namespace>/<name>[#<kind-singular>:<key>][#<anchor>]
```

The legacy DepRef shorthand `<namespace>/<name>:<package>` is accepted as a
synonym for `<namespace>/<name>#package:<package>`.

## Artifact kinds

The kinds are pinned in the schema. The order matches the Dhall union arms in
`Schema.MoriArtifactKind` and the Haskell mirror.

| Kind | URI segment | Compact | Dhall arm |
|------|-------------|---------|-----------|
| Doc | `docs` | `doc` | `Doc` |
| Package | `packages` | `package` | `Package` |
| Repo | `repos` | `repo` | `Repo` |
| Skill | `skills` | `skill` | `Skill` |
| Subagent | `subagents` | `subagent` | `Subagent` |
| Api | `apis` | `api` | `Api` |
| Cookbook | `cookbook` | `cookbook` | `Cookbook` |
| Template | `templates` | `template` | `Template` |
| MasterPlan | `masterplans` | `masterplan` | URI only |
| ExecPlan | `plans` | `plan` | URI only |
| OkfBundle | `okf` | `okf` | URI only |

`cookbook` and `okf` are the segments that do not pluralise: the cookbook
artifact is "the cookbook entry" (and its extension already uses the singular
form), and `okf` names the OKF format rather than a plural noun.

The last three kinds are **URI-only**. The CLI parses, renders, and resolves
them, but they have no arm in the Dhall `Schema.MoriArtifactKind` union, so
they cannot be stored in a typed `MoriRef` value in a config file — only as
canonical `Text`. The `MasterPlan` and `ExecPlan` kinds come from the
[agent-plans extension](/docs/guides/agent-plans); their trailing key is the
plan's `<id>-<slug>` segment. The `OkfBundle` kind addresses an [OKF knowledge
bundle](/docs/guides/okf).

### Nested OKF concept refs

`okf` is the only kind with a nested grammar. A ref may address one concept
inside a bundle:

```
mori://<namespace>/<name>/okf/<bundle>/concepts/<segment>
```

The segment after `concepts/` is the concept's rename-stable **document ID**
(such as `IR-1`) when its profile declares one, and its **concept ID** (the
file's bundle-relative path with `.md` stripped, which may contain `/`)
otherwise. Both forms resolve — resolution matches the document ID first and
falls back to the concept path — so URIs written before stable handles existed
keep working. Nested refs always render canonically, because the compact
grammar has no lossless nested representation. Two concepts in one bundle
sharing a handle is an OKF profile violation; mori reports an ambiguity error
naming both candidates rather than picking one.

## Examples

```
Project root:                    mori://shinzui/streamly
A doc:                           mori://shinzui/streamly/docs/effects-cookbook
A doc with anchor:               mori://shinzui/streamly/docs/effects#pooling
Compact form for the same doc:   shinzui/streamly#doc:effects-cookbook
A package:                       mori://shinzui/streamly/packages/streamly-core
A skill:                         mori://shinzui/streamly/skills/effects-cookbook
A cookbook entry:                mori://shinzui/streamly/cookbook/postgres-pool
A seihou template:               mori://shinzui/streamly/templates/scaffold-app
An OKF bundle:                   mori://shinzui/streamly/okf/architecture
Compact form for the same OKF:   shinzui/streamly#okf:architecture
A concept (handle form):         mori://shinzui/mori/okf/improvement-requests/concepts/IR-1
A concept (path form):           mori://shinzui/streamly/okf/architecture/concepts/tables/users
A masterplan:                    mori://shinzui/mori/masterplans/9-agent-plans-extension
An exec plan:                    mori://shinzui/mori/plans/70-agent-plans-dhall-schema-and-uri-kinds
```

## Resolution model

Refs resolve against the **local** registry only. There is no network fetch
in v1. To use a ref pointing at project `shinzui/streamly`, that project must
be registered locally:

```bash
mori register ~/code/streamly
```

Every kind in the table above resolves through a registry read model, including
`apis` and `cookbook` (both projected) and the two plan kinds, which resolve to
a path under the project's `docs/` directory. The "unsupported kind" warning
survives only for a malformed ref carrying a nested sub-key on a kind that has
no nested grammar — today `okf` is the only kind that has one.

## Where refs are accepted

On the command line:

```bash
mori path <ref>                 # print resolved filesystem path
mori browse <ref>               # open the artifact in a browser
mori registry open-doc <ref>    # open a doc in $EDITOR (doc refs only)
```

In config files (`mori.dhall`, `mori/cookbook.dhall`,
`mori/checklist.dhall`):

```dhall
location = Schema.DocLocation.Canonical
             "mori://shinzui/streamly/docs/effects-cookbook"
```

The `Canonical` arm of `DocLocation` is accepted anywhere a `DocLocation` is —
`Project.docs`, `Package.docs`, augmented `Dependency.extraDocs`, cookbook
entries, and checklist source docs. Existing `LocalFile` / `LocalDir` /
`RepoPath` / `Url` arms keep working unchanged; the addition is purely
additive.

## Output: canonicalRef in JSON and `--full`

Every artifact JSON object emitted by `mori show --json` and
`mori registry show --json` carries a `canonicalRef` field with its
`mori://` URI:

```bash
mori show --json | jq '.docs[].canonicalRef'
```

`mori show --full` and `mori registry show --full` print a dim canonical-ref
line under each artifact in their text rendering, so you can copy a stable
identifier directly out of the terminal.

## Validation

To parse and resolve every canonical ref in a project's config and extension
files:

```bash
mori validate --check-refs
```

The check walks `mori.dhall`, `mori/cookbook.dhall`, and
`mori/checklist.dhall`, printing a per-source ✓/✗/⚠ report. It exits zero
if every ref resolves through the local registry; it exits 1 if any ref
names a project that is not registered or a missing artifact key. This
includes `okf` refs at both the bundle and the nested concept grain, and
checklist item-level `docs` references. A nested concept ref that matches
more than one indexed concept fails the check with an ambiguity message
naming the candidates.

## Read-model tables

EP-52 added two projection tables that back ref resolution for APIs and
cookbook entries:

| Table                      | Purpose                                |
|----------------------------|----------------------------------------|
| `mori.mori_apis`           | One row per API across all projects    |
| `mori.mori_cookbook_entries` | One row per cookbook entry            |

The subscription handler writes these rows on project events; a
`ProjectCookbookEntriesReplaced` bulk event carries the full new catalog
list when the on-disk cookbook differs from the projection.
