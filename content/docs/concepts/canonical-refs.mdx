Every artifact owned by a registered project has a stable canonical identifier
in the `mori://` URI scheme — including every entity mori's schema extensions
contribute. The CLI accepts canonical refs as input wherever it makes sense,
prints them in `--full` and `--json` output, and the schema can store them in
any field typed as `DocLocation` or `MoriRef`.

For a task-oriented walkthrough, see [Mori URIs](/docs/guides/mori-refs).

## Forms

Canonical (always emitted, always accepted on input):

```
mori://<namespace>/<name>/<kind-segment>[/<key>][#<anchor>]
```

Compact alias (input only — canonical form is what gets stored and printed):

```
<namespace>/<name>[#<kind-singular>:<key>][#<anchor>]
```

The legacy DepRef shorthand `<namespace>/<name>:<package>` is accepted as a
synonym for `<namespace>/<name>#package:<package>`.

## Artifact kinds

Twenty-one kinds are addressable. The order matches the Dhall union arms in
`Schema.MoriArtifactKind` and the constructor order in the Haskell mirror.

Four segments do not pluralise: `cookbook` (the artifact is "the cookbook
entry", and its extension already uses the singular form), `okf` (the format
rather than a plural noun), `radar` (it reads better than `recommendations` and
matches `mori tech-radar`), and `glossary` (a mass noun).

### Typed refs

Every kind has a Dhall arm, so a typed `Schema.MoriRef` value can name any of
them:

```dhall
Schema.MoriRef::{
, namespace = "shinzui"
, name = "mori"
, kind = Some Schema.MoriArtifactKind.DddContext
, key = Some "registry"
}
```

One limitation remains: `MoriRef` has no sub-key field, so the three nested
forms below cannot be expressed as a typed value. They travel as canonical
`Text` in a `DocLocation.Canonical` arm.

### Two-segment DDD kinds

The seven [DDD](/docs/guides/ddd) kinds take a two-segment path. The bare
segment `mori://<ns>/<name>/ddd` is not a ref and reports an unknown kind —
`ddd` is a namespace within the URI, not a kind of its own. The compact form is
flat, so it needs no second segment: `shinzui/mori#ddd-context:registry`.

## Nested grammars

Three kinds accept a nested sub-key:

```
mori://<ns>/<name>/okf/<bundle>/concepts/<segment>
mori://<ns>/<name>/checklists/<key>/steps/<step>
mori://<ns>/<name>/ddd/flows/<key>/steps/<order>
```

Nested refs always render canonically, because the compact grammar has no
lossless nested representation. A nested sub-key on any kind without a nested
grammar is malformed and reports an unsupported-kind warning — that warning
survives for no other case.

### OKF concept refs

The segment after `concepts/` is one of two things. When a concept carries a
profile-declared **document ID** — a rename-stable handle such as `IR-1` or
`ADR-7` — mori prints that handle. Otherwise it prints the **concept ID**, the
concept's path inside the bundle with `.md` stripped, which may contain `/`
(the parser preserves the entire suffix).

Both forms resolve. Resolution tries the document ID first and falls back to
the concept path, so mori round-trips its own output exactly, a file named
after a published handle cannot shadow it, and every URI written before stable
handles existed keeps working. A handle duplicated across two concepts in one
bundle is an OKF profile violation; mori reports an ambiguity error naming both
candidates rather than silently picking one.

## Resolution model

Refs resolve against the **local** registry only. There is no network fetch in
v1. To use a ref pointing at project `shinzui/streamly`, that project must be
registered locally:

```bash
mori register --path ~/code/streamly
```

Every kind resolves through a registry read model — there is no kind whose
resolution is a filesystem convention. The read models are `mori.docs`,
`mori.packages`, `mori.repositories`, `mori.skills`, `mori.subagents`,
`mori.apis`, `mori.cookbook_entries`, `mori.seihou_templates`,
`mori.agent_plans` (both plan kinds), `mori.okf_bundles` and the OKF concept
index, `mori.checklists` and `mori.checklist_items`, `mori.upstream_issues`,
`mori.tech_radar_recommendations`, and the seven `mori.ddd_*` tables.

### Registry-verified plan refs

A `plans/` or `masterplans/` ref resolves only if the owning project publishes
that plan in its `mori/agent-plans.dhall`. A plan file that exists in
`docs/plans/` but is not listed there is not addressable — publishing is a
deliberate act, not a consequence of the file existing. Expect most of a
repository's plan files to be unaddressable.

A registered plan whose markdown has been moved or renamed is reported
distinctly from an unknown ref, because the two call for different fixes.

### Ambiguity

Three shapes can resolve to more than one artifact, and all three report an
error naming the candidates rather than picking one:

- an OKF document handle duplicated inside one bundle;
- a short `radar/<package>` ref for a package recommended under two languages
  (two `Other`-category recommendations sharing a language and package collide
  even fully qualified, because the category segment is the literal `other` for
  both — give one a closed-arm category to separate them);
- two glossary terms that slug to the same segment.

## Where refs are accepted

On the command line:

```bash
mori path <ref>                 # print resolved filesystem path
mori browse <ref>               # open the artifact in a browser
mori registry open-doc <ref>    # open a doc in $EDITOR (doc refs only)
```

In config files:

```dhall
location = Schema.DocLocation.Canonical
             "mori://shinzui/streamly/docs/effects-cookbook"
```

The `Canonical` arm of `DocLocation` is accepted anywhere a `DocLocation` is —
`Project.docs`, `Package.docs`, augmented `Dependency.extraDocs`, cookbook
entries, and checklist source docs. Existing `LocalFile` / `LocalDir` /
`RepoPath` / `Url` arms keep working unchanged; the addition is purely
additive.

Improvement-request `originPlan` and `targetPlan` fields accept only canonical,
unanchored `masterplans/<id>-<slug>` or `plans/<id>-<slug>` references. The
[improvement-request validator](/docs/guides/improvement-requests) additionally
checks project ownership and exact registration; parsing a conventional plan
path alone is not sufficient.

## Output: canonicalRef in JSON and `--full`

Every artifact JSON object emitted by `mori show --json` and
`mori registry show --json` carries a `canonicalRef` field with its `mori://`
URI:

```bash
mori show --json | jq '.docs[].canonicalRef'
```

`mori show --full` and `mori registry show --full` print a dim canonical-ref
line under each artifact in their text rendering, so you can copy a stable
identifier directly out of the terminal.

## Validation

To parse and resolve every canonical ref in a project's config and extension
files:

```bash
mori validate --check-refs
```

The check walks five sources — `mori.dhall`, `mori/cookbook.dhall`,
`mori/checklist.dhall`, `mori/tech-radar.dhall`, and
`mori/agent-plans.dhall` — printing a per-source ✓/✗/⚠ report. It exits zero
if every ref resolves through the local registry; it exits 1 if any ref names a
project that is not registered or a missing artifact key. A missing extension
file contributes nothing and is not an error; a file that fails to load prints
one warning and contributes no refs rather than failing the whole check.

## Reference fragility

No reference form is unconditionally durable. Mori's design goal is to make a
broken reference **loud** rather than silent: each kind fails in a specific,
reported way rather than resolving to the wrong thing.

Renaming the key breaks a doc, package, repo, skill, subagent, api, cookbook,
template, checklist, upstream-issue, or DDD-entity ref — the key is the
identity, and there is no alias table. Renaming or unpublishing a plan breaks
its ref. Editing a glossary term's prose changes its slug. Reordering a context
mapping's pair yields a different ref. Deregistering the owning project breaks
every ref into it, at every kind.

One failure is not loud: **renumbering a DDD flow step**. A flow step is
addressed by its declared `order`, so inserting a step earlier in the flow and
renumbering the rest means an existing URI now names a *different* step. Prefer
stable, sparse step numbers.

`mori help mori-refs` prints the complete per-kind fragility list.
