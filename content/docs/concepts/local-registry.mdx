The local registry is mori's machine-local index of projects, packages,
dependencies, docs, groups, templates, OKF bundles, and extension catalogs. It is
not a manually edited JSON file. It is a PostgreSQL read model derived from
events in the current runtime.

## What It Stores

The registry powers:

- project lookup by `namespace/name`
- dependency resolution for `mori deps`
- filesystem navigation through `mori cd`, `mori path`, and `mori browse`
- agent context assembly
- registry groups and batch execution
- canonical `mori://` reference resolution
- extension catalogs such as plans, tech radar, cookbook, checklist, DDD, and
  OKF bundles

## Runtime Model

```text
mori.dhall on disk
    |
    v
mori register / mori observe / mori automate register
    |
    v
project and repository events
    |
    v
keiro/kiroku event runtime
    |
    v
mori-registry and extension projections
    |
    v
mori.* read-model tables
    |
    v
registry, deps, path, agent, and extension commands
```

Registry behavior is entirely a matter of the keiro/kiroku event runtime and the
PostgreSQL read models derived from it. The legacy MessageDB path has been
retired.

## Database Setup

Set the database connection:

```bash
export MORI_PG_CONNECTION_STRING="host=localhost port=5432 dbname=mori_dev"
```

Run the project's migrations through your normal development command. The
migrations create the runtime schemas, pgmq queues/tables, and the `mori` read
models.

Verify the baseline:

```bash
mori doctor
```

The doctor baseline checks PostgreSQL connectivity and decodes every active
automation registration. Use `mori doctor --ingest` and `mori doctor --reactions`
for the focused ingest and reaction-execution audits.

## Populating The Registry

Register or observe projects:

```bash
mori register
mori observe
mori automate register
```

`mori register` records the project identity. `mori observe` links repository
identity and VCS observation state. `mori automate register` registers the
automation config and also emits the project/repo link needed by the daemon, so
there is no separate observe prerequisite for automation.

Start the daemon to keep projections current:

```bash
mori automate daemon
```

The daemon runs the registry projection alongside automation, workflow,
reaction, app, DDD, tech-radar, and agent-plan processors.

## Querying The Registry

```bash
mori registry list
mori registry show shinzui/mori --full
mori registry search effectful
mori registry dependents effectful --packages
mori deps resolve
mori deps tree --depth 2
mori path shinzui/mori --doc getting-started
```

Most commands query read models rather than reading every `mori.dhall` from disk
on every invocation. That is what makes dependency lookup, canonical refs, and
agent context fast enough for repeated use.

## Important Read Models

The exact schema is migration-owned, but these tables are the main public mental
model:

| Read model | Purpose |
|---|---|
| `mori.projects` | Registered project identity, namespace/name, path, repo id |
| `mori.packages` | Per-project package metadata |
| `mori.package_dependencies` | Package-level dependency graph and scope |
| `mori.docs` | Documentation references and canonical refs |
| `mori.groups` / memberships | Named registry groups for batch workflows |
| `mori.automation_registrations` | Daemon config registrations |
| `mori.reaction_history` | Reaction execution history |
| `mori.pending_scheduled_reactions` | Scheduled reactions waiting in pgmq |
| Extension tables | Plans, DDD, tech radar, OKF, cookbook, checklist, and related catalogs |

Prefer CLI commands for inspection unless you are debugging a projection.

## Troubleshooting

### The registry is empty

Register at least one project, then run the daemon:

```bash
mori register
mori automate daemon
```

### A project was registered but is not queryable

The read model may be behind. Restart `mori automate daemon` and check its logs.
If the issue is ingest-specific, run:

```bash
mori doctor --ingest
```

### Dependency lookup is missing a package

Use the registry command surface first:

```bash
mori registry show <namespace>/<project> --full
mori registry dependents <dependency> --packages
mori deps explain <dependency>
```

If the source `mori.dhall` changed, rerun `mori register` or `mori observe` so
the new events can update the projections.

### You need to verify a projection against its events

Use [`mori ops replay-audit`](/docs/commands/ops#mori-ops-replay-audit) to
prove that streams still fold cleanly without writing anything, and
[`mori ops rebuild`](/docs/commands/ops#mori-ops-rebuild) to rebuild a read
model from the event log when it has genuinely drifted.
