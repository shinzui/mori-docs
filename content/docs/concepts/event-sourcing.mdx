## Overview

Mori is event-sourced: commands append immutable events, current state is
derived by folding those events, and user-facing queries read PostgreSQL
projections. The current runtime is built around the keiro-runtime family:

- **kiroku** stores ordered PostgreSQL event streams and exposes subscription
  delivery.
- **keiro** runs command handlers, routers, process managers, durable timers,
  and async projections on top of those streams.
- **keiki** supplies the pure transducer model used by aggregates and routers.
- **shibuya** supervises long-running processors.
- **pgmq** backs delayed work, FIFO queued automations, webhook delivery, and
  dead-letter queues.

Legacy MessageDB support still exists where mori needs compatibility with old
event history or staged migration. That boundary is explicit: `mori history`
transforms and verifies legacy MessageDB streams into kiroku, and `mori doctor`
still checks the legacy `message_store` schema in its baseline health check.

## Runtime Shape

```text
PostgreSQL
├── kiroku schema
│   ├── streams
│   ├── events
│   └── stream_events
├── keiro runtime tables
│   ├── projection deduplication
│   ├── durable workflow state
│   └── timer state
├── pgmq schema
│   ├── scheduled_actions
│   ├── scheduled_reactions
│   ├── queued_reactions
│   └── dead-letter queues
└── mori schema
    ├── projects
    ├── packages
    ├── package_dependencies
    ├── automation_registrations
    ├── reaction_history
    ├── pending_scheduled_reactions
    ├── workflows
    ├── groups
    ├── apps
    ├── okf_bundles
    ├── ddd read models
    ├── tech-radar read models
    └── agent-plan read models
```

The exact table set is migration-owned and can grow as extensions add read
models. User commands should treat the `mori` schema as the query surface and
avoid depending on private runtime tables.

## Streams And Contexts

Mori organizes events by bounded context. The current supported migration
contexts are:

```text
app
automation_registration
group
project
reaction
repository
workflow
```

Typical stream categories:

| Context | Purpose |
|---|---|
| `project` | Project registration, metadata, dependencies, docs, packages, bundles, extensions |
| `repository` | VCS observations, config observations, workflow signals, ingest health events |
| `reaction` | Reaction lifecycle: triggered, scheduled, skipped, failed, cancelled, completed |
| `workflow` | Cross-repo workflow lifecycle and step state |
| `automation_registration` | Daemon registration, update, and deregistration events |
| `group` | Registry group membership |
| `app` | Webhook app registration and delivery state |

Kiroku stores events in named streams and also records an ordered global log.
Subscriptions can consume categories and consumer groups through the
keiro/shibuya worker host.

## Read Models

Read models are PostgreSQL tables derived from event streams. They make the CLI
fast and predictable:

- `mori registry`, `mori deps`, `mori cd`, `mori path`, and `mori browse` query
  project/package/dependency projections.
- `mori reaction` queries reaction history and pending scheduled reactions.
- `mori workflow` queries workflow projections.
- Extension commands such as `mori plans`, `mori tech-radar search`, `mori ddd
  search`, and `mori registry concepts` query extension-specific projections.

Read models are rebuildable from events. If a projection is stale, restart
`mori automate daemon` or replay the relevant subscription after confirming the
operator impact.

## Worker Host

The multi-repo daemon runs the current reactive runtime:

```text
kiroku streams
    |
    v
shibuya processors
    |
    +-- keiro routers
    +-- keiro process managers
    +-- keiro async projections
    +-- durable timer workers
    +-- bespoke reactors for app fan-out and scheduled action enqueue
```

The worker host gives mori supervised processing, graceful shutdown, retry
visibility, and backpressure without each feature hand-rolling its own loop.
Router and process-manager legs are idempotent by construction; async
projections use keiro projection deduplication.

## Queues

Mori uses pgmq for delayed and queued work:

| Queue family | Used for |
|---|---|
| `scheduled_actions` | Legacy per-action `Schedule` wrapper |
| `scheduled_reactions` | Preferred per-reaction schedule lifecycle |
| Queued reaction jobs | `queued = True` automation reactions with FIFO ordering per automation |
| `webhook_deliveries` | Mori app webhook delivery and retry |
| Dead-letter queues | Failed scheduled/queued jobs that exhausted retry policy |

Scheduled action and scheduled reaction queues use keiro-pgmq `Job`
definitions, so the queue name, JSON codec, retry policy, and dead-letter
configuration live with the job definition. Webhook delivery still uses its
bespoke pgmq adapter.

## Migration Boundary

The MessageDB-to-kiroku migration is an operational concern, not the steady-state
mental model for new features.

Use [`mori history`](/docs/commands/history) for migration work:

```bash
mori history transform-context project
mori history verify-context project --axis both
mori history transform-all
mori history verify-all
```

The command can read legacy MessageDB history, write kiroku streams, and verify
the migrated history by folding both sides. This is why some code and docs still
refer to MessageDB: they are describing the compatibility path, not the current
runtime architecture.

## Operational Checks

```bash
mori doctor
mori doctor --ingest
```

`mori doctor` checks the baseline database connection and legacy MessageDB
compatibility. `mori doctor --ingest` checks `mori.repository_ingest_status` and
exits `2` when repos appear stuck, making it suitable for monitoring.

For day-to-day runtime health, also watch:

- daemon logs from `mori automate daemon`
- stuck ingest rows through `mori doctor --ingest`
- pending scheduled reactions with `mori reaction scheduled list`
- failed or cancelled reactions with `mori reaction list --status failed`
- queued/dead-letter tables when pgmq jobs exhaust retry policy

## Design Invariants

1. Events are the durable source of truth.
2. Read models are derived and rebuildable.
3. CLI write paths route through the configured event backend.
4. Long-running work is supervised by the daemon runtime.
5. Deferred work is explicit in pgmq-backed queues.
6. Legacy MessageDB references should be read as migration compatibility unless
   a command page says the command still checks it directly.
