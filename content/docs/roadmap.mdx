Mori was planned in three phases. **Phase 1 — Local-First — is complete**, and a good deal of
what was originally scoped as Phase 3 shipped along the way. This page describes the current
state honestly: what works, what is declared but not enforced, what is actively being built, and
what has been requested but not committed.

Last reviewed against mori `v3.0.0.0`.

| Phase | Focus | State |
|-------|-------|-------|
| **Phase 1** | Local-First — fully functional on a single developer machine | **Complete** |
| **Phase 2** | Global Registry — organization-wide coordination and sync | Not started |
| **Phase 3** | Advanced features — pinning, trust policies, cross-repo workflows | Partly delivered early |

---

## What ships today

### Identity and configuration

`mori.dhall` is parsed, type-checked against a pinned schema, and projected into a queryable
registry. Projects carry stable identity that survives renames.

- `mori init`, `mori validate`, `mori show`, `mori status`, `mori doctor`
- `mori identity` — mint and inspect stable project identity, with aliases and renames
- `mori schema` — pin management, compatibility checking, and migrations
- Typed `mori://` references across the manifest, resolvable with `mori path`
- Declarative extensions — a repository can add its own typed extension without a mori release

### Registry and dependencies

- `mori register`, `mori registry` — `search`, `show`, `docs`, `group`, `domains`, `templates`,
  `pins`, `relations`, `concepts`, `upgrade-schema`, `exec`
- `mori deps locate | resolve | explain` — dependency resolution by name
- Package-grain dependency edges, so "who uses `hasql-pool`" is answerable as itself rather than
  collapsing to "who uses `hasql`"
- `mori registry dependents` — reverse dependencies
- Version constraints and upstream pointers for fork and vendored projects
- `mori browse`, `mori cd`, `mori path` — navigation

### Agent context

- `mori agent context <role>` — structured JSON grounding for coding agents
- `mori agent ask`, agent sessions, and the compiled prompt templates every session runs on
- `mori kit` — install and version the Claude Code skill and subagent catalog
- `mori cookbook`, `mori checklist`, `mori tech-radar`, `mori upstream-issues` — classified
  catalogs an agent can query instead of guessing

### Knowledge and modelling

- `mori ddd` — subdomains, bounded contexts, aggregates, context mappings, flows, glossary,
  coordination mechanisms, lifecycle and terminology succession, and `mori ddd map` for a
  fleet-wide context map rendered from the registry
- `mori improvement-requests` — cross-project OKF improvement requests, with provenance and
  trust filters
- `mori plans` — cross-project agent-plan queries, including the blocking graph and
  `mori plans graph`
- `mori diagram` — aggregate lifecycles as Mermaid `stateDiagram-v2`

### Automation

- `mori automate ingest git` — cursor-tracked VCS ingestion with content-stable changeset
  identity, so a re-ingest emits nothing for content already seen
- `mori automate run` — single-repo reactive engine
- `mori automate daemon` — multi-repo daemon with live registration, auto-ingest, an optional
  embedded HTTP API, and Kiroku metrics
- Named automations — several independently configured automations per repository
- Selectors for changesets, refs, signals, and projects, with glob, branch, message, and git
  trailer matching
- Actions: `RunCommand`, `EmitEvent`, `Notify`, `Signal`, `Decision`, `Schedule`
- Scheduled reactions with idempotency checks and `coalesceKey` debouncing
- `queued = True` — strict FIFO execution per automation, grouped so different automations still
  run in parallel
- `mori automate inspect | explain | generate | register | list | reset-checkpoint`
- Closed failure taxonomy (`timeout`, `spawn-failure`, `nonzero-exit`,
  `dependency-unavailable`, `decode-failure`) driving retry, dead-letter, or acknowledge

### Cross-repo workflows

- Signals are a first-class delivery domain with their own aggregate, per-target delivery state,
  retry policy, and dead-lettering — a target that cannot be resolved reports as failed rather
  than as a silent success
- Structured signal payloads with predicates; fan-out and chain-depth bounds; target consent
- `*dependents*` dynamic targets resolved from the dependency graph
- **Fan-in joins** — wait until several named signal legs have all arrived for the same
  correlation value, with an optional window and expiry signal
- `mori workflow list | status | trace`, `mori signal list | show | retry`
- `mori.project.v1` integration events published through a durable Keiro outbox

### Operations

- `mori ops` — durable workflows, timers, outbox, inbox, PGMQ, projections, shards, snapshots,
  streams, replay audit, and projection-catalog rebuilds
- `mori app` — Mori Apps as webhook receivers, with delivery retry
- `mori serve` — the HTTP read API
- `mori reaction list | show | scheduled | cancel | recover` — reaction history, pending
  schedules, and recovery
- Projection-catalog drift gates at deploy and daemon startup, recovered by preview-then-adopt

## Known gaps in shipped features

These are things Mori lets you *write* but does not yet *do*. They are listed here rather than
buried, because writing them and expecting them to take effect is a real trap.

| Gap | What actually happens |
|-----|----------------------|
| **`ExecutionPolicy` is not enforced** | `allowLocal`, `allowCI`, and `maxConcurrency` are parsed, validated, stored in the config observation event, and shown by `mori automate inspect` — and never read at execution time. `allowLocal = False` will not stop a reaction from running on your machine. Use `queued = True` for the one execution control that *is* enforced. Tracked as IR-14. |
| **No Jujutsu adapter** | `VcsType` has a `Jujutsu` arm, but `mori automate ingest` accepts only `git`. |
| **No recurring schedules** | A reaction can be delayed (`schedule.after`) but cannot run on a clock. Periodic sweeps still need an external cron. Requested as IR-16. |
| **No wall-clock deadlines** | `schedule.after` is a relative delay only; "do this once, at the end of the day" is inexpressible. Requested as IR-15. |
| **Queue discipline is FIFO only** | A queued automation always runs the *oldest* eligible pending reaction next. Requested as IR-8. |

## Being built

Five pieces of work are open. None of them changes an existing contract.

| Work | What it delivers |
|------|------------------|
| **Upstream-issues cross-repo automation** | Propagate a corpus project's known upstream defects to the dependents that are affected by them. Its authoritative target-resolution prerequisite is complete; the remaining work is the signal-delivery-domain rebase and implementation. |
| **`Agent` automation action** | A declarative action that hands a reaction to a registered agent. The Dhall and Haskell halves are implementable now; the transport waits on the agent runner exposing an HTTP surface. Requested as IR-1. |
| **Typed capability queries** | Cross-registry capability queries and a semantic validation gate over the `coordination.capabilities` OKF profile. The originally planned Dhall `capability` extension is withdrawn — the profile is the authoring format. |
| **Event provenance** | Stamp event metadata and thread causation and trace context through every command-dispatch site. |
| **Store lifecycle** | Retention, compaction, and a fail-closed archive ledger for event streams, built on the `mori ops` verbs rather than a second operator surface. Nothing is deleted before it is archived to disk and verified byte-for-byte. |
| **Improvement-request fulfillment** | Canonical typed source graphs, readiness, actionable Hard leaves, and one versioned CLI/HTTP contract. Mori-local clean, incremental, and replay conformance is complete; provider-neutral Kikan fixture publication remains an integration gate. |

## Requested, not committed

Improvement requests are how other projects — and Mori itself — record a capability gap as a
durable, addressable fact rather than a wish. These seven are registered and open with no plan
behind them. Listing one here is not a commitment to build it.

| Request | Gap |
|---------|-----|
| **IR-3** | Model practice adoption, and re-evaluate affected decisions when registered guidance changes |
| **IR-8** | A LIFO automation queue discipline — run the newest eligible pending reaction next, without losing one-at-a-time execution or cancellation semantics |
| **IR-12** | Orchestrate upgrade cascades in dependency order — a DAG driven in topological waves, not an unordered one-hop fan-out |
| **IR-13** | Expose project grounding over a protocol-neutral agent interface, so an agent that is not Claude Code can retrieve context and resolve `mori://` references |
| **IR-14** | Enforce the declared automation execution policy, and record a refusal as a fact |
| **IR-15** | Schedule a reaction to a wall-clock deadline, with a coalesce key that absorbs repeats into the pending deadline |
| **IR-16** | Trigger automations on a recurring schedule, owned by a durable schedule with an explicit catch-up policy |

Four of these seven are automation-engine gaps, which makes the automation engine the largest
single pool of uncommitted demand.

See [Improvement Requests](/docs/guides/improvement-requests) for how they are raised, linked to
plans, and closed.

## Phase 2: Global Registry

Not started. Mori today is local-first: one registry, one database, resolution within it.
Phase 2 makes that organization-wide.

- A registry service with authentication, authorization, and namespace management
- Sync — push local registrations, pull global metadata, resolve conflicts, keep working offline
- Organization features — team ownership, discovery, dependency graph visualization
- CI integration — registry-gated execution and policy enforcement

Cross-machine signal transport is deliberately deferred to this phase. Delivery currently stays
within one registry's database, and registry-only target resolution is the stepping stone the
Phase 2 transport is meant to reuse.

## Phase 3: Advanced features

Version pinning, upstream pointers, cross-repo workflow orchestration, and typed trust and
provenance arrived early — they are in the shipped list above. What remains genuinely Phase 3:

- Lock file generation and reproducible dependency builds
- Signed policies and automation allow/deny lists
- Cross-organization workflow policies
- Automatic event upcasting driven by a schema registry

## Settled design questions

| Question | Decision |
|----------|----------|
| Event store | Kiroku on PostgreSQL, with the Keiro runtime. MessageDB and the legacy path have been removed entirely |
| Aggregate style | Functional event sourcing — every aggregate is a Keiki transducer with a pure decide/evolve core |
| Local registry storage | PostgreSQL projections, not SQLite |
| Registry read models | Inline projections, current the moment their writing command returns — not polled by a daemon |
| Dependency model | Registry-first resolution, at package grain |
| Repository identity | TypeID minted on `mori init`; stable identity survives renames |
| Cross-repo communication | Signal-based dispatch through one delivery aggregate, with workflow tracking |
| Multi-repo automation | `mori automate daemon` discovers registered repos; registration is event-driven, not filesystem polling |
| Worker process model | One long-running daemon with concurrent Kiroku subscriptions, plus a Shibuya worker for scheduled and queued actions |
| Cookbooks | Modelled as `docs` entries with `kind = Cookbook` |
| Capability authoring | The shared `coordination.capabilities` OKF profile, not a bespoke Dhall extension |

## Still open

| Question | Notes |
|----------|-------|
| VCS adapter mechanism | The daemon auto-ingests on an interval. Git hooks and filesystem watching remain unexplored |
| Standards distribution | How org-wide standards are versioned and resolved across a fleet |
| Event versioning | Additive-only is enforced and upcasters work; automatic upcasting from a schema registry is not built |
