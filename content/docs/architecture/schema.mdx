The `mori.dhall` schema defines the **identity layer** of Mori configuration.

**Mori** is a typed project metadata system for repositories.
It describes *what a project is*, *what it depends on*, and *what agents should know about it*.

Mori is:

* **Schema-first** (Dhall)
* **Graph-oriented** (repos, packages, APIs, consumers)
* **Identity-focused** (what a project *is*, not what *happens*)

## Design Principles

1. **Single source of truth** — Dhall files are authoritative; JSON is derived
2. **Typed, composable metadata** — no stringly-typed conventions
3. **CLI-first UX** — humans interact via `mori` commands, not raw Dhall
4. **Agent-aware by default** — metadata designed to generate reliable agent context
5. **Knowledge lives where it is owned** — shared knowledge in shared projects, not duplicated per repo
6. **Identity precedes behavior** — `mori.dhall` describes what a project *is*; `mori.automation.dhall` describes what *happens*

## v0 Scope

v0 defines the **identity layer**:

* Project identity and ownership
* Repositories and packages
* APIs and dependencies
* Agent context hints

**Automation and reactive behavior are defined separately in `mori.automation.dhall`.**

## Shared Standards & Canonical Knowledge

Many organizations maintain **standardization documents** that are:

* shared across projects
* not owned by any single service or library
* essential when bootstrapping new projects or guiding agents

Examples include:

* architecture guidelines
* API standards
* coding conventions
* event naming rules
* operational runbooks

Mori models these as **standard projects** that act as canonical knowledge sources.

### Standard Project

A *standard project* is a Mori project whose primary purpose is to publish shared documentation and conventions.

```haskell
-- StandardScope.dhall
< Organization
| Domain
| Platform
| Language
| Team
| Other : Text
>
```

```haskell
-- StandardProject.dhall
{ name : Text

, scope : ./StandardScope.dhall

, description : Optional Text

, repo : ./Repo.dhall

, docs : List ./DocRef.dhall

, appliesTo :
    { types : List ./PackageType.dhall
      -- Which project/package types this standard applies to
    , languages : List ./Language.dhall
    }
}
```

Standard projects:

* do **not** define packages or APIs
* exist solely to publish shared knowledge

### Referencing Standards from a Project

Projects may explicitly declare which standards they follow:

```haskell
-- Project.dhall (extension)
{ ...
, standards : List Text
  -- Names of StandardProjects this project adheres to
}
```

This keeps adoption **explicit and auditable**.

### Resolution Rules for Standards

1. Standards are resolved by name
2. If a local checkout exists, it is preferred
3. Otherwise, standards may be fetched from the Mori registry
4. Standards are **read-only** for consuming projects

### Agent Usage

When bootstrapping or modifying a project, agents may be instructed:

> "This project adheres to the following standards:
>
> * backend-architecture
> * api-guidelines
> * event-naming
>
> Consult these documents before making changes."

### CLI Support

```bash
mori standards list
mori standards show <name>
mori standards validate
```

These commands allow:

* inspection of applicable standards
* verification that required standards are declared

### Example: Backend Architecture Standards

```haskell
{ name = "backend-architecture"
, scope = < Platform >
, description = Some "Shared backend architecture and DDD standards"

, repo =
    { name = "platform-standards"
    , github = "org/platform-standards"
    , localPath = Some "../platform-standards"
    }

, docs =
  [ { key = "ddd"
    , audience = < Internal >
    , kind = < Guide >
    , description = Some "Bounded contexts and aggregates"
    , location = < LocalFile "docs/ddd.md" >
    }
  , { key = "events"
    , audience = < Internal >
    , kind = < Guide >
    , description = Some "Event naming and versioning conventions"
    , location = < LocalFile "docs/events.md" >
    }
  ]

, appliesTo =
    { types = [ < Application >, < Worker > ]
    , languages = [ Language.Haskell, Language.TypeScript ]
    }
}
```

### Design Rule (Non-Negotiable)

> **Standards are declared, not inferred.**
>
> Mori never assumes standards apply unless explicitly referenced.

### Why Standards Are Separate from Dependencies

* Standards are **guidance**, not runtime dependencies
* They should never affect builds or deployments
* They exist to guide humans and agents

This separation prevents standards from polluting dependency graphs.

## Root Type: Project

> **Canonical source**: `schema/Project.dhall`

At the top level, Mori models a **Project** as the unit of ownership and intent.
A project may be a deployable service, a reusable library, or a generated client.

Projects use the same `PackageType` enum as packages -- there's no separate `ProjectType`.
This simplifies the model: one enum describes what something *is*, whether it's a project or package.

```haskell
-- Project.dhall (authoritative definition)
{ project :
    { name : Text
      -- Project name (unique within namespace)

    , namespace : Text
      -- Organization namespace (e.g., "acme")
      -- Used for registry identity: @namespace/name

    , type : PackageType

    , description : Optional Text

    , language : Language

    , lifecycle : Lifecycle
      -- Active | Experimental | Deprecated | Archived

    , domains : List Text
      -- High-level domain tags (e.g., "Billing", "Platform")

    , owners : List Text
      -- Team names or handles

    , origin : Origin
      -- Ownership classification: Own | ThirdParty | Fork | Vendored
    }

, repos : List Repo

, packages : List Package

, bundles : List PackageBundle
  -- Package bundles (for wrapper projects)

, dependencies : List Text
  -- Project-level dependencies, resolved by name via the local registry.
  -- For fine-grained control (augmentation, path overrides), declare
  -- dependencies at the Package level using the Dependency union type.

, apis : List Api

, agents : List AgentHint

, skills : List Skill
  -- Agent skills provided by this project

, subagents : List Subagent
  -- Subagent definitions

, standards : List Text
  -- Names of standard projects this project follows

, docs : List DocRef
  -- Project-level documentation
}
```

## Dependency Resolution Rules (Authoritative)

Mori defines **deterministic, explicit rules** for resolving dependency metadata.
These rules exist to prevent duplication, drift, and ambiguity when working across many repositories.

### Design Context: Multi-Repo Microservices

Mori is designed for organizations with **many services across many repositories**.

Problems with per-service path declarations:

* 50 services x 10 shared dependencies = 500 path declarations
* Path drift when checkouts move
* No single source of truth
* Duplicated documentation references

**Solution: Registry-first resolution.**

Services reference dependencies by name. The local registry resolves names to filesystem paths. Dependency metadata lives in **wrapper projects** registered once.

### Core Principles

> **Registry-first resolution.**
> Dependencies are resolved by name via the local registry. Consumers never hardcode paths.

> **Metadata follows ownership.**
> A dependency owns its own Mori metadata; consumers may only *augment* it.

### Resolution Algorithm

For each dependency declared in a project:

1. **Extract dependency name** from declaration
2. **Query local registry** for name
3. **If found in local registry:**
   * Return filesystem path to registered project
   * Load that project's `mori.dhall` as **authoritative**
4. **Else query global registry** (if online)
   * Return cached metadata
5. **Else check `localPathOverride`** (fallback for unregistered deps)
   * Load that path's `mori.dhall` as authoritative
6. **Else:**
   * Treat dependency as **unannotated**
   * Warn user to register the dependency

```
                  +-------------------+
                  | "streamly"        |
                  +--------+----------+
                           |
                  +--------v----------+
                  | Local Registry    |
                  | (SQLite)          |
                  +--------+----------+
                           | found?
              +------------+------------+
              | yes                     | no
    +---------v---------+     +---------v---------+
    | Return path:      |     | Global Registry   |
    | /Users/dev/oss/   |     | (if online)       |
    | streamly-project  |     +---------+---------+
    +-------------------+               | found?
                              +---------+---------+
                              | yes               | no
                    +---------v---------+   +-----v-----+
                    | Return cached     |   | Fallback: |
                    | metadata          |   | localPath |
                    +-------------------+   | Override  |
                                            +-----------+
```

### Wrapper Projects

Dependencies become first-class Mori projects:

```
streamly-project/
├── streamly/           # git clone
├── streamly-core/      # git clone
├── mori.dhall          # project manifest
└── docs/
    ├── folds-guide.md
    └── streaming-patterns.md
```

Register once:

```bash
cd streamly-project
mori register --local
```

All services can now reference `"streamly"` without specifying paths.

### Merge Semantics

When authoritative dependency metadata is found:

* Dependency Mori **cannot be overridden**
* Consumer-declared metadata is **merged additively**

Allowed consumer additions:

* Additional `extraDocs`
* Local usage notes

Disallowed consumer overrides:

* Package type
* APIs owned
* Domain model
* Config requirements

### Augmentation Example

Most dependencies need no augmentation:

```haskell
{ dependencies = [ "streamly", "effectful", "hasql" ] }
```

When you need to add project-specific documentation:

```haskell
{ dependencies =
    [ "streamly"
    , "effectful"
    , < WithAugmentation =
        { name = "hasql"
        , extraDocs =
            [ { key = "our-usage"
              , audience = < Internal >
              , kind = < Notes >
              , description = Some "How payments uses hasql connection pooling"
              , location = < LocalFile "docs/hasql-notes.md" >
              }
            ]
        , localPathOverride = None Text
        }
      >
    ]
}
```

### Fallback: Unregistered Dependencies

For dependencies not yet in the registry (experimental, one-off):

```haskell
< WithAugmentation =
    { name = "experimental-lib"
    , extraDocs = []
    , localPathOverride = Some "/Users/dev/scratch/experimental-lib"
    }
>
```

This is rare. The expectation is that frequently-used dependencies are registered.

### CLI Introspection

```bash
# Locate a dependency
mori deps locate streamly

# Explain resolution
mori deps explain streamly

# Resolve all dependencies
mori deps resolve
```

Output always shows:

* Resolution source (local registry / global registry / fallback)
* Filesystem path
* Applied augmentations

### Invariants

* **Registry-first**: Name lookup before path fallback
* **Single authority**: Exactly one `mori.dhall` per dependency
* **No override**: Consumers augment, never redefine
* **Deterministic**: Same name -> same resolution
* **Offline-capable**: Local registry works without network

## API Clients, Consumers, and Update Graph

APIs evolve, and Mori must capture **who is affected and how updates propagate**.

Mori models APIs as a **directed update graph**:

```
API Owner -> Client Library -> Application Consumers
```

This enables tools and agents to:

* update client libraries first
* then update all downstream consumers
* in a controlled, policy-driven way

### API Dependency Roles

```haskell
-- ApiDependencyRole.dhall
< Client
| Consumer
>
```

### API Dependency Edge

```haskell
-- ApiDependency.dhall
{ package : Text        -- package name
, role : ./ApiDependencyRole.dhall
}
```

### Api Schema

The Api.dhall type (shown in Core Types above) uses `owner` as a package name and `dependencies` as a list of `ApiDependency` edges, replacing the earlier `consumers` list.

### API Update Policy (Agent-Consumable)

> **Note:** This type defines behavioral automation policy and conceptually belongs to the automation layer (`mori.automation.dhall`). It is documented here for schema completeness and to show how identity and behavior types relate.

Policies describe **what agents are allowed or expected to do**, not how they do it.

```haskell
-- ApiUpdatePolicy.dhall
{ strategy : ApiUpdateStrategy
  -- ClientFirst | ManualApproval | NoAutomation

, allowBreaking : Bool

, requireTests : Bool

, consumerBatching : ConsumerBatching
  -- Sequential | Parallel

, notes : Optional Text
}
```

### Example

```haskell
{ name = "MLS Public API"
, type = < OpenAPI >
, specPath = "openapi.yaml"

, owner = "mls-service"

, dependencies =
  [ { package = "mls-client"
    , role = < Client >
    }
  , { package = "reporting-service"
    , role = < Consumer >
    }
  , { package = "analytics-service"
    , role = < Consumer >
    }
  ]

, updatePolicy = Some
  { strategy = < ClientFirst >
  , allowBreaking = False
  , requireTests = True
  , consumerBatching = < Sequential >
  , notes = Some "Client must be regenerated before consumers are touched"
  }
}
```

## Configuration Specification

Many applications require **runtime configuration** (environment variables, secrets, feature flags, endpoints).
Mori can describe *what configuration is required* without prescribing *how it is provided*.

This enables:

* Infrastructure validation (e.g. Kubernetes ConfigMaps / Secrets)
* CI checks for missing or unused config
* Agent context about runtime assumptions

### Design Principles for Config

* **Declarative, not executable**
* **Typed** (strings vs numbers vs URLs)
* **Environment-agnostic** (dev/staging/prod are overlays)
* **Separation of concerns**: Mori describes requirements, infra supplies values

### Core Types

```haskell
-- ConfigValueType.dhall
< String | Integer | Boolean | Secret | Url
| FilePath | Duration | Json | Other : Text >
```

```haskell
-- ConfigSourceHint.dhall
< EnvVar : Text        -- Environment variable name
| K8sSecret : Text     -- Kubernetes secret name
| K8sConfigMap : Text  -- Kubernetes ConfigMap name
| Vault : Text         -- HashiCorp Vault path
| File : Text          -- File path
| Default : Text       -- Default value
>
```

```haskell
-- ConfigItem.dhall
{ key : Text
, type : ConfigValueType
, required : Bool
, description : Optional Text
, sourceHint : Optional ConfigSourceHint
, example : Optional Text
}
```

Configuration is specified **per package** (in `Package.dhall`), since different packages/apps have different runtime needs.

### Example

```haskell
config =
[ { key = "DATABASE_URL"
  , type = < Url >
  , required = True
  , description = Some "PostgreSQL connection string"
  , sourceHint = Some < K8sSecret = "payments-db" >
  , example = None Text
  }
, { key = "LOG_LEVEL"
  , type = < String >
  , required = False
  , description = Some "Logging verbosity"
  , sourceHint = Some < EnvVar = "LOG_LEVEL" >
  , example = Some "info"
  }
]
```

### Environment Overlays (Future-Friendly)

Local or environment-specific overrides can live in:

```text
mori.config.local.dhall
mori.config.prod.dhall
```

These files may supply *values* or *disable* optional config keys, but **cannot change required keys**.

### CLI Extensions

```bash
mori config list <package>
mori config validate
mori config validate --k8s ./k8s
```

Examples:

* Compare Mori config spec against Kubernetes ConfigMaps / Secrets
* Detect missing required keys
* Warn about unused config entries

### CI / Infrastructure Integration

Possible checks:

* Required config missing in deployment manifests
* Secrets referenced but not declared
* Config drift between environments

Mori acts as the **contract**, infrastructure as the **implementation**.

## Mental Model

`mori.dhall` is the **identity layer** of Mori.

It declares:

* **What** a project is (type, ownership, lifecycle)
* **What** it contains (packages, APIs, dependencies)
* **What** agents should know (context hints)

It does **not** declare:

* What happens when events occur (see `mori.automation.dhall`)
* Execution policies or reactions

> **Identity is the foundation; automation builds on top.**
