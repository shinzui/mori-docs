This document describes the **end-to-end architecture of Mori**, including the **local execution runtime** and the **Global Mori Registry**.

It is intended as a **high-level technical overview** suitable for:

* Architecture reviews
* Onboarding
* Aligning local development with CI and org-wide workflows

## Architectural Goal

Mori is designed to:

* React to **VCS events** (Git and Jujutsu)
* Remain **local-first** and replayable
* Scale safely to **CI and organization-wide automation**
* Separate **execution** from **governance**

Core idea:

> **Local Mori executes automation. Global Mori governs trust and policy.**

## Design Context: Multi-Repo Microservices

Mori is designed for organizations with **many services across many repositories**.

Typical environment:

* 50+ services, each in its own repository
* Shared dependencies (internal libraries, third-party ecosystems)
* Multiple teams with different ownership boundaries
* Need for consistent tooling and agent assistance across all repos

Problems Mori solves:

| Problem | Without Mori | With Mori |
|---------|--------------|-----------|
| Dependency paths | Hardcoded in each repo | Resolved via local registry |
| Documentation | Scattered, duplicated | Centralized in wrapper projects |
| Agent context | Manual prompt engineering | Structured, queryable metadata |
| Cross-repo automation | Ad-hoc scripts | Event-driven, policy-governed |

**Key design principle:**

> **Registry-first resolution.** Services reference dependencies by name.
> The local registry resolves names to filesystem paths.
> This eliminates path duplication across dozens of repositories.

## Major Architectural Layers

Mori consists of two primary planes:

### Data Plane (Local Mori Runtime)

* Lives on developer machines and CI workers
* Observes repositories and executes reactions
* Fully functional without any central service

### Control Plane (Global Mori Registry)

* Central, shared service
* Indexes projects and policies
* Never executes automation directly

## Configuration Layers

### Project Manifest (`mori.dhall`)

* Declares project identity
* Declares ownership and dependencies
* Indexed by the global registry
* Does **not** enable automation

### Automation Policy (`mori.automation.dhall`)

* References `mori.dhall`
* Declares event selectors and reactions
* Enforces execution constraints
* Optional and opt-in

Automation is only active when **both**:

* The automation file exists
* Policy resolution allows execution

## Local Registry

The Local Registry is a **projection** (read model) derived from events in the event store.

### Responsibilities

* **Project registration**: Track all Mori projects on the local filesystem
* **Dependency resolution**: Resolve dependency names to filesystem paths
* **Agent context assembly**: Provide structured context for coding agents
* **Cache for global registry**: Sync and cache data from org-wide registry

### Registry Hierarchy

```
Local Registry (machine-specific, authoritative for dev)
       ↓ fallback
Global Registry (org-wide defaults)
       ↓ fallback
Not Found
```

### Implementation

* **Event-sourced**: Registry state derived from `ProjectRegistered`, `ProjectUpdated` events
* **PostgreSQL tables**: Projections stored in `mori.*` schema for fast queries
* **Subscription-updated**: `mori-registry` subscription processes events and updates tables
* **Rebuildable**: Can replay events from position 0 to reconstruct registry

### Key Tables

```
mori.projects      -- Registered projects
mori.packages      -- Packages within projects
mori.dependencies  -- Dependency name → project path lookup
mori.bundles       -- Package bundles
```

## Event Flow Overview

```
VCS Event (git commit, jj operation)
   ↓
Normalize to canonical events
   ↓
Write to MessageDB (repository-{id} stream)
   ↓
Subscriptions process events:
   ├── mori-automation: match events → trigger reactions
   ├── mori-registry: update project/dependency projections
   └── mori-reaction-executor: execute triggered reactions
   ↓
Update projections (PostgreSQL tables)
   ↓
Emit effects (run commands, notify, emit new events)
```

At no point is mutable filesystem state consulted during reaction execution.

## Role of the Global Mori Registry

The Global Mori Registry provides:

* Project discovery and indexing
* Ownership and team metadata
* Organization-wide automation policies
* Trust levels (local-only, CI-approved, org-wide)

It does **not**:

* Execute reactions
* Push automation into repos
* Override local configuration

## Policy Resolution Model

Effective behavior is determined by:

```
Local Automation Rules
        +
Global Registry Policy
        ↓
Effective Execution Policy
```

Rules:

* Global policy may restrict
* Local config may not escalate
* Absence of registry implies permissive local mode

## Local vs CI Execution

| Aspect | Local Mori | CI Mori |
|--------|-----------|---------|
| Execution | Always allowed | Registry-gated |
| Config loading | Local FS | Ephemeral checkout |
| Policy source | Local + optional registry | Registry required |
| Replay | Yes | Yes |

CI uses the **same runtime**, only stricter policy resolution.

## Design Invariants

1. Events are the source of truth
2. Configuration is domain data
3. Execution is local and deterministic
4. Governance is centralized and declarative
5. Replay always yields identical behavior

## Mental Model

> **Mori is an event-sourced automation system with a local execution engine and a global registry that governs trust, policy, and coordination.**

## What This Architecture Enables

* Safe local experimentation
* Deterministic CI automation
* Org-wide governance without tight coupling
* Cross-repo workflows
* Explainable, auditable automation

## Open Questions

The following design questions remain to be resolved:

* **VCS Adapter**: How does it observe events? Git hooks? Polling? `fswatch`? jj's operation log?
* **Registry sync**: Push or pull? How often? What if offline? (Phase 2)
* **Trust enforcement**: How are trust levels verified locally? Signed policies?
* **Event versioning**: Schema evolution strategy? (Elegant solution in progress)
* **Failure recovery**: What happens if Mori crashes mid-reaction?

### Resolved

* **Event Store**: MessageDB on PostgreSQL.
* **Local Registry**: PostgreSQL projections derived from events (not SQLite).
* **Concurrency**: Consumer groups in MessageDB subscriptions enable horizontal scaling.
* **Repository identity**: TypeID (`repo_xxxx`) generated on `mori init`.
