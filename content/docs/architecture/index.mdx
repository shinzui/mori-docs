This document describes mori's high-level architecture: a local execution
runtime for project identity and automation, plus an optional global registry
plane for discovery and governance.

## Architectural Goal

Mori is designed to:

- make repositories self-describing through `mori.dhall`
- resolve dependencies and docs through a local registry
- observe VCS events and run local automation
- provide structured context to coding agents
- scale from one developer machine to CI and organization-wide workflows

Core idea:

> Local Mori executes automation. Global Mori governs trust and policy.

## Major Planes

### Data Plane: Local Mori Runtime

The local runtime lives on developer machines and CI workers. It is fully useful
without a central service.

It contains:

- the `mori` CLI
- the local PostgreSQL database
- the keiro/kiroku event runtime
- pgmq queues for delayed and queued work
- read models in the `mori` schema
- the automation daemon and worker host
- local filesystem paths for repositories, docs, skills, templates, and source

### Control Plane: Global Registry

The global registry is the future shared governance/indexing plane. It can
provide organization-wide discovery, trust, and policy, but it does not execute
automation directly.

## Runtime Stack

Mori's current event runtime is built from the keiro-runtime family:

| Layer | Role in mori |
|---|---|
| `kiroku` | PostgreSQL event store and subscriptions |
| `keiro` | command execution, routers, process managers, durable timers, async projections |
| `keiki` | pure transducer semantics for aggregate behavior |
| `shibuya` | supervised queue processors and graceful worker lifecycle |
| `pgmq` | delayed jobs, FIFO queued automations, webhook delivery, dead-letter queues |

The legacy MessageDB path has been retired: the migration command and the
`message_store` compatibility check are both gone, and kiroku is the only event
store. MessageDB now appears only in older architecture documents kept for
historical context.

## Configuration Layers

### Project Manifest: `mori.dhall`

Declares project identity, ownership, packages, dependencies, docs, APIs,
skills, subagents, templates, OKF bundles, and extension configuration. It does
not enable automation by itself.

### Automation Policy: `mori.automation.dhall`

Declares selectors and reactions. It is optional and opt-in. Automation becomes
active only after the repo is registered or run with the automation command
surface.

## Local Registry

The local registry is a set of PostgreSQL read models derived from events.

Responsibilities:

- track registered projects and repo paths
- resolve dependency names to projects and packages
- resolve canonical `mori://` refs
- assemble agent context
- index extension catalogs
- support navigation commands such as `mori cd`, `mori path`, and `mori browse`
- support batch workflows over registry groups

Typical commands:

```bash
mori registry list
mori registry show shinzui/mori --full
mori registry dependents effectful --packages
mori deps tree --depth 2
mori path shinzui/mori --doc getting-started
```

## Event Flow

```text
CLI command or VCS ingest
    |
    v
domain command handler
    |
    v
keiro/kiroku append
    |
    v
shibuya-supervised processors
    |
    +-- registry projections
    +-- automation matching
    +-- reaction execution
    +-- workflow projections
    +-- extension projections
    +-- app fan-out
    |
    v
mori read models and pgmq jobs
```

Examples:

- `mori register` records project metadata and updates registry projections.
- `mori automate ingest git` records repository observations.
- `mori automate daemon` consumes repository events, matches automation
  selectors, executes reactions, and maintains read models.
- Scheduled reactions enqueue pgmq jobs and later emit lifecycle events.
- Extension projections make plans, DDD, tech-radar, OKF, cookbook, and checklist
  data searchable from any registered project.

## Local vs CI Execution

| Aspect | Local Mori | CI Mori |
|---|---|---|
| Execution | local-first | policy-gated |
| Config loading | checked-out filesystem | ephemeral checkout |
| Registry source | local read model plus optional global input | local read model plus required policy input |
| Event model | same runtime | same runtime |
| Replay | yes | yes |

CI uses the same event/runtime model with stricter policy decisions.

## Design Invariants

1. Events are the source of truth.
2. Read models are derived and rebuildable.
3. Configuration is domain data, not hidden process state.
4. Automation execution is local and explicit.
5. Deferred work is visible in pgmq-backed queues.
6. Global governance constrains local behavior; it does not run local effects.

## Migration Status

Mori has moved its event backend onto the keiro/keiki/kiroku/shibuya stack, and
the migration is complete. The legacy message store, its compatibility checks,
and the transformation command have all been removed.

Any remaining MessageDB reference in these pages is an older architecture
document retained for historical context. When one conflicts with a current
command reference or with source behavior, prefer the command docs and
[Event Sourcing](/docs/concepts/event-sourcing).
