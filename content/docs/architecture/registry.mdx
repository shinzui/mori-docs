> **Historical document.** This was written before the event-sourcing architecture was adopted.
> Key decisions that have been **superseded**:
>
> - **Local registry**: This doc describes a standalone JSON/SQLite registry. The project now uses PostgreSQL read models derived from events in the keiro/kiroku runtime. See [Event Sourcing](/docs/concepts/event-sourcing).
> - **`mori register`**: This doc describes global registry upload as the default. Phase 1 uses `mori register --local` only.
> - **Command details**: The authoritative CLI specification is [CLI Architecture](/docs/architecture/cli).
>
> Some concepts here (navigation, search, namespacing) remain valid and are referenced by CLI.md.

## Core CLI Principles

1. **Local-first, registry-enhanced**
   Mori must work fully offline. The registry augments discovery.

2. **Explicit actions, no background magic**
   Registration, resolution, and navigation are always user-initiated.

3. **Explainability over convenience**
   Every non-trivial command must be inspectable (`--explain`).

4. **One root per project**
   CLI commands always operate relative to a single `mori.dhall` root.

## Global Mori Registry (Conceptual)

The registry is a **read-optimized index** of projects that have opted in.

Each registered entry includes:

* project identity (name, type)
* repository information
* evaluated Mori metadata (JSON)
* registration source (repo + commit)

The registry never mutates local state automatically.

## Command: `mori register`

### Purpose

Register the current project in the global Mori registry.

This enables:

* global discovery
* dependency reuse
* navigation (`mori cd`)

### Preconditions

* Must be executed inside a directory containing `mori.dhall`
* Mori schema must validate

### Behavior

```bash
mori register
```

Steps:

1. Load and validate `mori.dhall`
2. Resolve dependencies (local + registry)
3. Evaluate Dhall to canonical JSON
4. Upload metadata to registry
5. Record registration receipt locally

### Output

```text
✔ Mori project validated
✔ Registered as: internal:agent-qualification
✔ Commit: a1b2c3d
```

### Flags

```bash
mori register --dry-run
mori register --explain
mori register --force
```

* `--dry-run`: show what would be registered
* `--explain`: show resolution and merge decisions
* `--force`: allow overwriting an existing registry entry (ownership required)

## Command: `mori cd`

### Purpose

Navigate to a registered project from anywhere.

This is a **developer productivity command**, not a build feature.

### Basic Usage

```bash
mori cd agent-qualification
```

Behavior:

* Look up project in registry
* Resolve local checkout path
* Change directory to project root

### Resolution Rules

1. Prefer local checkout already known to Mori
2. If missing, prompt to clone
3. Never clone implicitly without confirmation

### Examples

```bash
mori cd streamly
mori cd backend-architecture
```

## Command: `mori search`

### Purpose

Discover existing projects, packages, or standards.

```bash
mori search streamly
mori search --type library
mori search --language haskell
```

Results are always sourced from the registry.

## Command: `mori add dependency`

### Purpose

Add a dependency to the current package using registry metadata.

```bash
mori add dependency streamly
```

Behavior:

1. Query registry for `streamly`
2. Display available metadata (docs, language, source)
3. Prompt for local checkout (optional)
4. Update local `Package.dhall`

This avoids retyping metadata already known to Mori.

## Command: `mori deps resolve`

### Purpose

Resolve and explain all dependencies for the current project.

```bash
mori deps resolve
mori deps resolve --explain
```

Outputs:

* authoritative metadata source (local vs registry)
* applied augmentations
* unresolved dependencies

## Command: `mori introspect`

### Purpose

Analyze project dependencies from build files and compare with Mori metadata.

Examples:

```bash
mori introspect        # auto-detect (cabal, npm, go.mod)
mori introspect cabal
```

Behavior:

* Extract dependency names
* Match against registry
* Suggest additions or enrichment

## Command: `mori list`

### Purpose

List known entities.

```bash
mori list projects
mori list packages
mori list standards
```

Results may come from:

* local Mori
* registry

## Command: `mori explain`

### Purpose

Explain Mori decisions in human terms.

```bash
mori explain dependency streamly
mori explain project agent-qualification
```

This command is **mandatory** for debuggability.

## Non-Goals (Explicit)

The CLI will **not**:

* replace package managers
* auto-modify code
* run builds or deployments
* infer intent implicitly

## Invariants (Must Hold)

* Registry access is optional
* CLI behavior is deterministic
* All side effects are explicit
* All resolution decisions are explainable

## Mental Model

> The Mori CLI is a **navigation and coordination tool**, not an execution engine.

It helps developers and agents:

* find knowledge
* reuse existing context
* move between projects safely
