This document is the **authoritative CLI specification** for Mori.

The goal of this document is to:

* enumerate all supported CLI commands for phase 1
* define their intent and behavior
* lock in naming and semantics before implementation

## CLI Design Principles

1. **Single binary** -- `mori`
2. **Local-first** -- works without a registry
3. **Registry-enhanced** -- global discovery when available
4. **Explicit side effects** -- no background mutation
5. **Explainable behavior** -- every decision can be inspected

## Command Groups

The CLI is organized into clear domains:

* Core
* Registry
* Navigation
* Authoring
* Dependencies
* APIs
* Agents
* Standards
* Config
* Automation
* Diagnostics

Each command must be deterministic and scriptable.

## Core Commands

### `mori init`

Initialize Mori in a repository.

```bash
mori init
```

Behavior:

* creates `mori.dhall`
* creates directory layout (`mori/`)
* optionally prompts for standards
* never overwrites existing files without confirmation

### `mori validate`

Validate the current Mori configuration.

```bash
mori validate
```

Checks:

* Dhall type-checking
* schema compatibility
* internal reference integrity

Exit codes:

* `0` valid
* `1` invalid

### `mori show`

Render evaluated Mori metadata.

```bash
mori show
mori show --json
```

## Registry Commands

### `mori register`

Register the current project in the Mori registry.

```bash
mori register
```

Behavior:

* validates Mori
* evaluates Dhall to canonical JSON
* uploads metadata
* records registration receipt

Flags:

* `--dry-run`
* `--explain`
* `--force`
* `--local` -- register in local registry only (no global upload)

### `mori search`

Search the Mori registry.

```bash
mori search <query>
mori search --type library
mori search --language haskell
```

### `mori registry status`

Check registry connectivity and authentication.

```bash
mori registry status
```

### `mori registry sync`

Sync local registry cache from global registry.

```bash
mori registry sync
mori registry sync --full
```

Behavior:

* pulls updated metadata from global registry
* updates local SQLite cache
* does not modify project files

Flags:

* `--full` -- full resync (not incremental)
* `--dry-run` -- show what would be synced

```bash

```

### `mori deps explain`

```bash

```

### `mori deps locate`

Locate a dependency on the local filesystem.

```bash
mori deps locate streamly
```

* documentation paths

## Automation Commands

Commands for VCS event ingestion and reactive automation.

See [Automation Configuration](/docs/concepts/automation-configuration) for the automation layer design.

### `mori automate ingest`

Ingest VCS events into the local event store.

```bash
mori automate ingest git
mori automate ingest jj
mori automate ingest --repo /path/to/repo --vcs git
```

Behavior:

* scans VCS history for new events
* normalizes to canonical event format
* appends to local event store
* updates cursor position

### `mori automate run`

Execute pending reactions.

```bash
mori automate run
mori automate run --once
mori automate run --dry-run
```

Behavior:

* evaluates event selectors against pending events
* checks policy resolution
* executes allowed reactions
* records execution for idempotency

Flags:

* `--once` -- process one batch, then exit
* `--dry-run` -- show what would run without executing
* `--explain` -- show matching logic

### `mori automate watch`

Watch repositories for VCS events continuously.

```bash
mori automate watch
mori automate watch --repos /path/a,/path/b
```

Behavior:

* monitors repositories for new events
* ingests automatically
* runs reactions when allowed

### `mori automate inspect`

Inspect automation configuration.

```bash
mori automate inspect
mori automate inspect --json
```

Output:

* automation config status
* config hash
* execution policy (local/CI)
* registered event selectors

### `mori automate explain`

Explain why a reaction did or did not run.

```bash
mori automate explain event <event-id>
mori automate explain reaction <reaction-name>
```

Output:

* event matching details
* policy resolution trace
* idempotency status


## Exit Code Policy

* `0` success
* `1` validation error
* `2` registry unavailable
* `3` user abort

## Non-Goals

* Mori will not run builds
* Mori will not deploy services
* Mori will not mutate code without explicit request

## CLI Architecture (Implementation)

This section defines the **internal architecture** of the Mori CLI. It is written to directly guide implementation (especially in Haskell), not as a conceptual overview.

The architecture is designed to ensure:

* deterministic behavior
* explainability
* clear separation of concerns
* testability

### High-Level Pipeline

Every Mori CLI command follows the same conceptual pipeline:

```
Command
  ↓
Argument Parsing
  ↓
Context Discovery
  ↓
Mori Load & Validation
  ↓
Resolution (local + registry)
  ↓
Decision / Planning
  ↓
Rendering (human / json)
```

No command is allowed to skip stages implicitly.

### Core Modules

#### 1. CLI Frontend

**Responsibility:**

* parse arguments
* select command
* collect flags

**Constraints:**

* no business logic
* no IO beyond argument parsing

#### 2. Execution Context

**Responsibility:**

* locate `mori.dhall` root
* load user config (`~/.config/mori`)
* determine registry configuration
* determine offline/online mode

This produces a single immutable value:

```haskell
ExecutionContext
  { cwd :: FilePath
  , moriRoot :: FilePath
  , registryMode :: RegistryMode
  , outputFormat :: OutputFormat
  }
```

#### 3. Mori Loader

**Responsibility:**

* load Dhall files
* type-check
* evaluate to canonical internal representation

**Important rules:**

* Dhall is evaluated exactly once per command
* all errors are surfaced here

Example modules:

* `Mori.Loader`
* `Mori.Schema`

#### 4. Resolution Engine

**Responsibility:**

* dependency resolution
* standard resolution
* registry lookup
* merge semantics

This is where **all deterministic logic lives**.

Key properties:

* pure (no IO)
* produces both results *and* an explanation trace

```haskell
resolve :: ResolveInput -> (ResolvedModel, ResolveTrace)
```

Example modules:

* `Mori.Resolve.Dependencies`
* `Mori.Resolve.Standards`

#### 5. Registry Client

**Responsibility:**

* talk to remote registry (optional)
* fetch / push metadata

**Rules:**

* never mutates local state
* all failures are explicit
* disabled entirely in `--offline` mode

Example modules:

* `Mori.Registry.Client`

#### 6. Planning Layer

**Responsibility:**

* interpret resolved model for a command
* produce a plan or report

Examples:

* API update plan
* dependency impact report
* agent context plan

Plans are **data**, not actions.

```haskell
plan :: ResolvedModel -> Plan
```

#### 7. Rendering Layer

**Responsibility:**

* render output
* human-readable or JSON

**Rules:**

* rendering never affects decisions
* all rendering uses plan + trace

Example modules:

* `Mori.Render.Text`
* `Mori.Render.JSON`

### Explainability (First-Class)

Every decision-making stage must emit structured explanations.

```haskell
ResolveTrace
  { dependencyTraces :: [DependencyTrace]
  , standardTraces :: [StandardTrace]
  }
```

The `mori explain` command is simply a **view** over this trace.

## Error Model

Errors are categorized and surfaced consistently:

* Schema errors (Dhall / typing)
* Resolution errors (conflicts, ambiguity)
* Registry errors (network, auth)
* User aborts

Errors must never be stringly-typed.

## Testing Strategy

* Resolution engine: pure unit tests
* Loader: golden tests
* CLI: snapshot tests

Registry client is always mockable.

## Architectural Invariants

* No hidden IO in resolution
* No registry access without explicit enablement
* No mutation without explicit command
* All decisions explainable

## Mental Model

> The Mori CLI is a **compiler for project knowledge**.
>
> * Dhall = source language
> * Resolution = semantic analysis
> * Plans = IR
> * Rendering = backend

This framing should guide all implementation decisions.
