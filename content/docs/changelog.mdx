## 2026-07-26

### OKF concept index and nested concept refs
- Registration now indexes every declared bundle's concepts and links into `mori.okf_concepts` and `mori.okf_concept_edges` alongside `mori.okf_bundles`; all three are replaced atomically per project, and the snapshot travels in the event so replays never re-read the filesystem
- [`mori registry concepts`](/docs/commands/registry#mori-registry-concepts) gained cross-project indexed modes: `--search <term>` (matches concept IDs, document IDs, labels, descriptions) and `--id <document-id>` (exact document-ID lookup, returning every match). The existing project argument still walks the working tree live
- New nested ref grammar `mori://<ns>/<name>/okf/<bundle>/concepts/<segment>`, addressing a concept by its rename-stable **document ID** (e.g. `IR-1`) when its profile declares one, or by its bundle-relative concept ID otherwise. Both forms resolve; nested refs always print canonically
- `mori path` resolves bundle and concept refs to a directory or Markdown file; `mori validate --check-refs` checks both grains; duplicate document IDs within a bundle produce an ambiguity error naming the candidates
- Indexing problems report as `Warning: could not index OKF bundle …` on stderr, before the profile advisories; both channels remain advisory
- Updated the [OKF Bundles guide](/docs/guides/okf), [Canonical Refs](/docs/concepts/canonical-refs), and [Mori References](/docs/guides/mori-refs)

### `mori improvement-requests` (new)
- New top-level command for cross-repository improvement requests, modelled as profile-governed OKF concepts of type `Improvement Request` with a rename-stable `IR-N` handle
- [`list`](/docs/commands/improvement-requests#mori-improvement-requests-list) with `--project`, `--origin`, `--status`, `--planning-state`, and `--json`; [`show`](/docs/commands/improvement-requests#mori-improvement-requests-show) with `--project`, `--bundle`, `--id`, and `--json`
- [`validate --path`](/docs/commands/improvement-requests#mori-improvement-requests-validate) checks the closed status set, UTC timestamp, canonical references, artifact kinds, project ownership, and exact plan registration
- [`link-plan`](/docs/commands/improvement-requests#mori-improvement-requests-link-plan) safely attaches a registered target plan — atomic, OKF-serialized, `--dry-run` and `--replace` aware, never touching status
- Planning state (`planned` / `unplanned` / `invalid`) is derived, not authored; invalid requests are never reported as unplanned
- New [Improvement Requests guide](/docs/guides/improvement-requests) and `mori help improvement-requests` topic

### `mori serve` and the HTTP API (new)
- New [`mori serve`](/docs/commands/serve) command runs the Servant + Warp HTTP API: application resources under `/v1` (projects, reactions, workflows, repositories, groups, apps, signed ingest), a generated OpenAPI 3.1 document at `/v1/openapi.json`, and standard operational probes under `/health`
- `--port` / `-p`, falling back to `$MORI_API_PORT`, then `8080`. `MORI_PG_CONNECTION_STRING` is required
- [`mori automate daemon`](/docs/commands/automate#mori-automate-daemon) can serve the same API on a shared pool and store with `--serve` / `--api-port` (or `MORI_API_PORT`); serving is opt-in and the daemon otherwise opens no socket
- Fallible routes return typed RFC 9457 problem documents; requests carry OpenTelemetry instrumentation

### Deprecation guidance
- New `Deprecation` record with optional `alternative` and `details`, attachable to a project or a package. A present record must contain at least one non-blank value and is valid only for an effective `Deprecated` lifecycle
- Package `lifecycle` is an `Optional Lifecycle` override that inherits the project lifecycle when absent; deprecation guidance is *never* inherited and must be declared per package
- `mori show --full` and `mori registry show` print lifecycle plus `Alternative` / `Details`, marking inherited package lifecycles `(inherited)`; `mori registry list` gained a **Lifecycle** column and JSON output gained `lifecycle` and `deprecation`
- Documented in [Getting Started](/docs/getting-started), the [Schema Guide](/docs/schema-guide), [Schema Reference](/docs/guides/schema-reference#deprecation), and [Project Configuration](/docs/guides/project-config)

### Checklist item documentation references
- Checklist items gained a `docs` list of step-specific `DocLocation` references, distinct from the checklist-level `sourceDoc`
- `mori checklist show` renders item docs (and the full `Docs` list under `--step`); `mori validate --check-refs` resolves canonical item docs against the registry, tagged `Checklist.checks[i].items[j].docs[k] <checklist-key>/<item-key>`

### Ref resolution
- Every artifact kind now resolves through a registry read model, including `apis` and `cookbook`; the "unsupported kind" warning survives only for a malformed nested sub-key on a kind with no nested grammar
- Plan refs (`masterplans/…`, `plans/…`) resolve to the plan Markdown under the project's `docs/` directory
- `MasterPlan`, `ExecPlan`, and `OkfBundle` are documented as **URI-only** kinds: parsed, rendered, and resolved by the CLI, but with no arm in the Dhall `Schema.MoriArtifactKind` union

## 2026-05-13

### Agent-plans extension and `mori plans` (new)
- New cross-project plan registry: publish a project's MasterPlans and ExecPlans through `mori/agent-plans.dhall` so other projects can declare `Hard` / `Soft` / `Integration` dependencies on them by `mori://` URI
- New top-level command [`mori plans`](/docs/commands/plans) with `list`, `show`, `search`, `deps`, `open`, and `print-schema` subcommands — queries the read-model projection, not the local catalog, so it works from any directory
- `mori plans deps --next-implementable` returns child ExecPlans whose Hard deps (including cross-project ones) are all `Complete`; the seihou `master-plan` and `exec-plan` skills consult this before picking the next plan
- `mori plans search --blocks <uri>` (reverse) and `--blocked-by <uri>` (forward) expose the cross-project dependency graph
- Two new canonical-ref kinds: `mori://<ns>/<name>/masterplans/<id>-<slug>` and `mori://<ns>/<name>/plans/<id>-<slug>` (compact: `#masterplan:` and `#plan:`)
- `mori registry show <project> --full` gains "Plans depending on this project" and "Plans here depending on others" subsections (text and JSON)
- New `mori help agent-plans` topic and [Agent Plans guide](/docs/guides/agent-plans)

### `mori agent bootstrap-agent-plan` (new)
- Claude session pre-loaded with the agent-plans extension schema, a snapshot of the project's existing plans, the canonical Markdown skeleton, and the validate / register / verify workflow
- Optional `--title`, `--kind`, `--summary`, `--description`, and repeatable `--depends-on` flags; `--debug` prints the system prompt without launching a session

### Scheduled reactions (new)
- New per-reaction `schedule` field on `Schema.Reaction`. When set, the whole reaction is enqueued on the `scheduled_reactions` pgmq queue and runs at the absolute `runAt` instant computed from `schedule.after` (ISO 8601 duration; years and weeks not supported)
- Optional `idempotencyCheck`: a shell command run just before the actions fire — if its exit code matches `skipOnExit` (`Zero` or `NonZero`), the reaction is skipped and `ReactionSkipped` is emitted instead of running the actions. The check command sees `MORI_REACTION_ID`, `MORI_REACTION_NAME`, `MORI_REPO_ID`, `MORI_TRIGGER_*`, `MORI_SCHEDULED_AT`, `MORI_RUN_AT`, and `MORI_COALESCE_KEY` env vars
- Optional `coalesceKey`: debounce by `(repo, automation, reaction-name, key)` — a fresh trigger cancels the prior pending reaction (`ReactionCancelled` with `reason = "superseded by …"`) and enqueues a new one. Without a key, repeated triggers stack
- Three new reaction status values: `scheduled`, `skipped`, `cancelled`. `mori reaction list --status` accepts them
- New commands: [`mori reaction cancel`](/docs/commands/reaction#mori-reaction-cancel), [`mori reaction scheduled list`](/docs/commands/reaction#mori-reaction-scheduled-list), and [`mori reaction scheduled show`](/docs/commands/reaction#mori-reaction-scheduled-show)
- New daemon subscriptions: `mori-pending-schedules-projection` (maintains `mori.pending_scheduled_reactions`) and `mori-agent-plans-projection`
- The per-action `Schedule` wrapper is preserved for backwards compatibility; per-reaction `schedule` is preferred for new code

### `mori schema pin` (new)
- Print the pinned mori-schema commit, main schema hash, and agent-plans extension hash. Three-line human transcript by default; `--emit-json` emits a single-line JSON document with a stable key order (`moriSchemaCommit`, `mainSchemaHash`, `agentPlansExtensionHash`) for drift detection (mina's `just check-schema-pin`)

### `mori schema migrate` extends to `mori/agent-plans.dhall`
- The migration pipeline now recognises `mori/agent-plans.dhall`, inserts the pinned `let AgentPlans = … sha256:…` import, and skips the standalone schema-URL rewrite (agent-plans bodies do not reference `let Schema = …`)

### `mori kit status` enhancements
- New `INSTALLED`, `LATEST`, and `STATE` columns. State precedence is `unknown > outdated > dirty > up-to-date`
- Per-install sidecar (`*.mori-kit.json`) records name, kind, version, content hash, and install time. `mori kit uninstall` removes the sidecar too
- New required `version` field in skill / agent manifest entries (legacy entries without a version are tolerated but report `outdated`)

### `mori register` recovery hint
- When an extension load fails with an error that looks like a stale or mismatched pin (HTTP 404, hash mismatch, or `TlsNotSupported` on old binaries), `mori register` now follows the warning with a hint: `run mori schema migrate --apply --file mori/<ext>.dhall to align the extension import with the mori binary's pinned schema`

## 2026-05-01

### Canonical refs (`mori://` URI scheme)
- New [`mori://<namespace>/<name>/<kind>[/<key>][#<anchor>]` URI scheme](/docs/concepts/canonical-refs) for cross-project artifact pointers
- Compact alias accepted on input: `<namespace>/<name>#<kind-singular>:<key>`
- Eight pinned artifact kinds: `docs`, `packages`, `repos`, `skills`, `subagents`, `apis`, `cookbook` (singular), `templates`
- `mori path`, `mori browse`, `mori registry open-doc` accept full canonical refs and the compact form
- `mori show --full` / `--json` and `mori registry show --full` / `--json` print a `canonicalRef` for every artifact
- `Schema.DocLocation` gains a `Canonical : Text` arm — accepted anywhere a `DocLocation` is (project/package docs, augmented `Dependency.extraDocs`, cookbook entries, checklist source docs)
- New schema types: `Schema.MoriRef`, `Schema.MoriArtifactKind`
- `mori path --doc <key>` follows `Canonical` arms transparently to the target's filesystem path via the new effectful `resolveDocLocationE`
- New `mori help mori-refs` topic

### `mori validate --check-refs` (new flag)
- Walks every canonical ref in `mori.dhall`, `mori/cookbook.dhall`, and `mori/checklist.dhall`
- Per-source ✓/✗/⚠ report with positional tags (e.g. `Project.docs[3] <key>`, `Cookbook.entries[2] <key>`)
- Exits 0 if every ref resolves, 1 if any ref fails

### Ref-aware shell completion
- `mori path mori://<TAB>` completes registered namespaces; `mori://<ns>/<TAB>` completes project names
- Phase 2: `mori://<ns>/<name>/<TAB>` completes the eight kind segments (owned-first ranking); `mori://<ns>/<name>/<kind>/<TAB>` completes artifact keys via per-kind read-model queries
- Compact-form parity: `<ns>/<name>#<TAB>` for kind tokens, `<ns>/<name>#<kind>:<TAB>` for keys
- Capped at 200; silent on connection failure or unset `MORI_PG_CONNECTION_STRING`
- No shell-script changes — completer threads through the existing `--bash-completion-enriched` protocol

### `Schema.DependencyScope` (new type)
- Per-package dependency scope: `Regular | Dev | Test | Build` (omission means `Regular`)
- Persisted as `mori.package_dependencies.dep_scope` (TEXT, nullable)
- `mori registry show` and `mori show --full` print a trailing `[test]` / `[dev]` / `[build]` tag
- `mori deps tree --scope=<value>` filters the recursive walk
- `mori agent assist` and `mori agent claude` exclude `Test`-scoped deps from the resolved-deps context block and `Read(path:.../*)` allowed-tools by default; pass `--include-test-deps` to opt back in

### `mori_apis` and `mori_cookbook_entries` projection tables (new)
- New read-model tables backing `resolveMoriRef` for the `apis` and `cookbook` artifact kinds
- Subscription handler writes Api / CookbookEntry rows on project events; `ResolvedApi` / `ResolvedCookbookEntry` arms wired through `mori path`, `mori browse`, and registry display

### `mori agent bootstrap` (registry-first discovery)
- Embedded `## Registry Snapshot` block now includes each project's local path, origin (`own`/`third_party`/`fork`/`vendored`), and shipped package list
- New `## Reference Discovery` section in both `bootstrap` and `--corpus` prompts steers the agent to use `mori registry list/search/show` and `mori path` rather than `find` to locate reference projects
- `--corpus` variant additionally surfaces `mori registry list --origin third_party` for sibling corpus projects

## 2026-04-28

### `mori registry exec` (new)
- Run the same command in every registered project, with `cwd` set to each project's local path
- Filters: `--group`, `--namespace`, `--type`, `--origin`, `--filter GLOB` (compose, AND semantics)
- `--jobs N` for parallel execution; `--fail-fast` to abort at the first failure
- `--dry-run` and `--json` modes; per-project summary table with status, exit code, and duration
- Skips projects without a local checkout; exits 0 if every executed command succeeded, 1 otherwise

### `mori reaction recover` (new)
- Unstick a reaction stuck at `status: triggered` (left over from pre-fix daemon builds that didn't catch executor exceptions)
- Marks the row `failed`, advances the executor checkpoint past the stuck event
- `--retry` re-emits a fresh `ReactionTriggered` carrying the original actions under a new reaction ID
- Refuses to operate on rows already in `completed` or `failed` state

### `mori reaction show`
- Failed `RunCommand` actions now display dedicated `Stdout:` and `Stderr:` blocks captured from the failed process

### `mori automate register` / `update`
- One-step registration: a single `mori automate register` emits both `ProjectRepoLinked` and `AutomationRegistered`, so a separate `mori observe` is no longer required to receive signals
- `mori automate update` heals state from older daemon builds by re-emitting `ProjectRepoLinked` if the projects row is missing
- `--path <dir>` is authoritative across `register`, `update`, `deregister`, `run`, and `ingest git`: the config file is read from `<dir>` and the repo TypeID is derived from `<dir>`, making it impossible to silently register the wrong repo

### Automation: nix devshell wrapping
- Every `RunCommand` is now spawned as `nix develop --command <command> <args…>` against the **target** repo's flake
- Each automation-target repo must have a `flake.nix` exposing a default devShell with the binaries the reaction references on `nativeBuildInputs`
- Removes the need to wrap commands in `/bin/bash -lc "cd … && …"` to pick up nix-installed tools under launchd

### Automation: executor fault tolerance
- The executor subscription wraps `executeActions` in an exception boundary; an uncaught error during action execution is recorded as a `ReactionFailed` event instead of halting the subscription
- Reaction history persists captured stdout/stderr per action result on `mori.reaction_history`

### `mori register --no-seihou-discovery` (new flag)
- Skip the auto-discovery probe for seihou template manifests when the project root holds a `module.dhall` that isn't a seihou module instance (e.g. a seihou type-definition file) and the probe produces noisy "Missing record field" warnings
- Internal callers (`mori observe`, `mori automate register`, `mori registry reregister`) keep the previous behavior

### `mori help`
- New `--width N` flag (with auto-detect, capped at 140) wrapping output for both direct topic rendering and the fzf preview

### Schema: cookbook extension import migration
- `upgrade-cookbook-extension-import` migration normalizes `let Cookbook = …` bindings to the canonical hashed form pinned in lockstep with the root `Schema`
- Rewrites un-hashed `let ContentType = …` / `let Topic = …` direct imports (which fail at runtime with `TlsNotSupported`), bumps stale-pinned `Cookbook` bindings, and injects the binding when files use `Schema.{ContentType,Topic}` references the root package never re-exported
- Runs as part of `mori schema migrate` on `mori/cookbook.dhall` and as part of `mori registry upgrade-schema`'s bulk pipeline

### Test fixtures: automation test repos
- New `just bootstrap-test-repos` / `just reset-test-repos` recipes generate three persistent sibling repos (publisher, happy-path consumer, failure-path consumer) for end-to-end automation repros
- Bootstrap script enforces dev-database-only — refuses to run against `~/.mori/db`

### Cross-repo workflows
- `mori workflow list` / `trace` now display the qualified `namespace/name` source project and the upstream `Source Reaction` whose `Signal` action emitted the workflow
- `SignalSelector.sourceProjects` requires the qualified `namespace/name` form; bare project names will silently match nothing

## 2026-04-18

### Schema: mk-pattern refactor
- Every core schema record is now published as a four-field bundle: `{ Input, Type, default, mk }`
- User configs are written with Dhall's record-completion operator: `Schema.Project::{ … }`, `Schema.Package::{ … }`, `Schema.Repo::{ … }`, etc.
- Fields that equal the published default can be **elided**; additive schema changes no longer break existing configs
- Extension records follow the same convention: `Cookbook.CookbookCatalog::{ … }`, `TechRadar.TechRadar::{ … }`, with per-extension `package.dhall` re-exports under `schema/extensions/<name>/`
- Automation schema (`Reaction`, `EventSelector`, `ReactionAction`, `ExecutionPolicy`) remains pre-mk for now and is a known gap

### `mori schema migrate`
- **`rewrite-to-mk-form`** migration — rewrites legacy bare-record `mori.dhall` into `Schema.Project::{ … }`, wraps inner records, elides default-equal fields, and `.Type`-qualifies annotations where needed
- Handles extension files (`mori/cookbook.dhall`, `mori/tech-radar.dhall`) — detected by path, with per-kind migration pipelines
- Parse-guarded steps: a step whose output doesn't parse is auto-reverted so later migrations still run
- Fixed four anchor / scan bugs that corrupted unusual-but-valid Dhall inputs

### `mori registry upgrade-schema` (new)
- Walks the registry and upgrades all projects whose `schema_hash` diverges from the CLI pin
- Flags: `--dry-run`, `--filter GLOB`, `--all`, `--commit`, `--allow-dirty`
- Covers `mori.dhall` **and** known extension files in a single pass
- One project's failure does not abort the others

### `mori registry` additions
- **`mori registry templates list/show`** — browse seihou templates across the registry at the *template* grain, with `--tag`, `--namespace`, and three-segment `<namespace>/<name>/<template>` references
- **`mori registry group create/list/show/add/remove/attach-package/attach-doc/…`** — first-class groups: named, event-sourced collections of projects with optional attached packages, docs, and JSON extension data
- `registry list` gains `--group`, `--domain`, and `--observed` filters
- Projects track `schema_url` / `schema_hash` and emit `ProjectSchemaVersionChanged` events

### `mori path`
- **`--copy` / `-c`** — copy the resolved path to the system clipboard (pbcopy / xclip) in addition to printing it

### `mori agent bootstrap`
- **`--seihou`** flag — bootstrap a project that ships seihou templates; adds the `seihou` CLI to the session allow-list and injects template authoring guidance into the system prompt

### `mori automate daemon`
- Periodic **auto-ingest loop** — ingests git history for every observed project (any project with a `repo_id`), independent of whether it has an automation config
- New `--ingest-interval SECONDS` flag (default: 300, `0` to disable)
- Daemon now manages six concurrent subscriptions (added app-registration stream)

### Cookbook extension
- **`CookbookEntry.tags`** — new optional field (`List Text`) for cross-cutting tags
- `addCookbookEntryTags` migration brings existing catalogs forward
