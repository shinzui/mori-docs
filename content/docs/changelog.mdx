All notable changes to mori, organized by date. This changelog covers user-facing
features, commands, and schema changes.

## 2026-08-22

### Non-destructive event-store lifecycle governance

- New [`mori store lifecycle`](/docs/commands/store) commands show the total category policy,
  check whether a binary may write to the current lifecycle ledger, and capture a snapshot-bounded
  inventory of visible events, checkpoints, history-retention leases, policy gaps, and proven
  adjacent Repository repeats
- The [Event-Store Lifecycle guide](/docs/guides/event-store-lifecycle) explains deterministic
  replay-grade archives and standalone verification. Archives preserve envelope evidence but do
  not authorize deletion or promise that an import can recreate global positions and links
- One-shot writers, the automation daemon, and its worker host now refuse before projection
  registration when lifecycle evidence is incompatible. Read-only status remains available for
  diagnosis, and the lifecycle command tree exposes no destructive verb

## 2026-08-21

### Truthful event provenance and trace continuation

- New Mori events record an additive process actor and active W3C trace context; event-driven,
  timer, and queued workers add their specific actor and truthful immediate cause without losing
  deterministic IDs, metrics, hooks, or existing metadata
- [`mori reaction show`](/docs/commands/reaction#mori-reaction-show) now renders actor, cause,
  workflow correlation, `traceparent`, and `tracestate`. Historical or malformed absence prints
  `not recorded` and is never inferred or backfilled
- [`mori ops stream causation`](/docs/commands/ops#mori-ops-stream-causation) traverses recorded
  event edges. Timer and message identities stay metadata-only instead of fabricating Kiroku event
  UUIDs

### Immutable project release facts

- [`mori registry release record`](/docs/guides/registry-releases) records one immutable release keyed by project and opaque version; a retry returns the first committed release time and source
- `mori registry releases` queries history or the latest release per project, and `--latest --with-dependents` joins the selected providers to every dependent package without interpreting versions or constraints
- A `RefSelector` reaction can turn observed version tags into the same fact. Recording a release does not implicitly notify dependents or orchestrate an upgrade cascade

### Signal targeting and interpolation now share their authoritative paths

- `"*dependents*"` uses the same reverse-dependency query as `mori registry dependents`, including package dependencies, project dependencies, and pinned imports. `mori signal list` warns about durable emissions that validly resolved to zero targets
- Receiving reactions now expand `{{signal.type}}`, `{{signal.source}}`, `{{signal.deliveredAt}}`, and flat payload `{{meta.<Key>}}` values before the Reaction is recorded
- Unknown trigger-time placeholders remain literal for compatibility, but the daemon logs the reaction, triggering event, and unresolved names instead of failing silently

## 2026-08-20

### Splitting a DDD model across files (new page)
- [Splitting a DDD Model](/docs/guides/ddd-decomposition) covers the supported way to compose one `DddModel` from several Dhall files: a small `mori/ddd.dhall` entry point, one fragment per concern, and `#` to append lists that span files
- Every fragment carries its own schema import — a `let` binding in the entry point is not visible inside an imported file — and every schema-bearing fragment must use the same commit and hash as the entry point
- **A `ddd` directory is never merged automatically.** Unlike `mori automate --config DIRECTORY`, the ddd loader does not enumerate, sort, or merge directory entries, and does not merge fragments by record name. `--config` names an alternative entry-point *file* for local `mori ddd` commands only; `mori register` still discovers `mori/ddd.dhall`
- Schema rewrites do not traverse imports: `mori schema migrate --apply` and `mori registry upgrade-schema` rewrite the entry point only, so update pinned fragments yourself after `mori schema pin`

### Corrected: `--to-root` does not duplicate deliveries
- [`mori automate reset-checkpoint --to-root`](/docs/commands/automate#mori-automate-reset-checkpoint) was documented as producing duplicate webhook deliveries to registered Mori Apps. That has not been true since content-stable changeset identity shipped
- `IngestChangeset` is guarded on `contentHashKnown == False`, so a commit already recorded in `mori.changeset_content_index` emits no `ChangesetObserved` event and nothing re-fires. `--to-root` is heavy because of the re-read, not because of re-emission

### `mori ops` — the operations console (new page)
- [`mori ops`](/docs/commands/ops) is the keiro-ops console mounted inside the mori binary, and the only operator surface for framework-owned state: durable workflows, timers, the transactional outbox and inbox, PGMQ dead letters, advisory snapshots, Kiroku streams, shard ownership, subscription checkpoints, projection dedup state, and read-model rebuilds
- Every mutating command previews first, changes nothing, and **exits 1** until you re-run with `--force`. Every invocation also verifies the live Keiro schema against the binary; a mutating command refuses on drift unless `--allow-schema-drift` is passed
- `--json` emits a versioned envelope that is the automation contract — never scrape a table or stderr

### `mori projections` and `mori replay-audit` removed
- Both commands are gone, replaced by [`mori ops rebuild`](/docs/commands/ops#mori-ops-rebuild) and [`mori ops replay-audit`](/docs/commands/ops#mori-ops-replay-audit)
- `replay-audit`'s `--mode full|targeted` became `--full` / `--target`, `--max-streams` became `--budget`, `--event-type` became `--target`, `--category` no longer repeats, and `--json` moved to the global position. One of `--full` or `--target` is now **required** — there is no default mode
- `rebuild`'s unit is a catalog rebuild *group*, never a table. `start` and `abandon` require operator evidence (`--run-id`, `--requested-by`, `--reason` / `--code`, `--detail`) on the command line
- There is no `seed-checkpoints` command any more. A subscription with no checkpoint row resolves it from a missing-checkpoint policy declared in code on the reactor; every mori reactor declares `FromCurrentHead`

### `mori identity` — stable IDs and renames (new page)
- [`mori identity mint --write`](/docs/commands/identity) inserts an opaque `project.stableId` into `mori.dhall`. It survives renames, so `mori register` updates the existing registry row instead of creating a second one
- [`mori identity show`](/docs/commands/identity#mori-identity-show) compares the manifest identity, repository ID, registry project ID, stable ID, and aliases side by side
- Renaming means changing `namespace` or `name` while keeping the same `stableId`. Mori records the previous canonical identity as an alias automatically; `Schema.ProjectAlias::{ namespace, name }` declares older identities explicitly
- References through an alias keep resolving. `mori validate --check-refs` reports them as warnings naming the current canonical identity

### DDD extension: full coverage for the first-class initiative
- **Canonical identities** — reactors, process managers, and durable workflows are first-class artifacts with their own `mori://…/ddd/{reactors,process-managers,durable-workflows}/<key>` URIs, typed as `DddReactor` / `DddProcessManager` / `DddDurableWorkflow`. They have no file of their own, so [`mori path`](/docs/commands/ddd#canonical-identities) reports a summary and returns the project root
- **Both JSON contracts written out**: [`ddd coordination --json`](/docs/guides/ddd#json-contract) emits a version-1 envelope of `version`/`filters`/`scope`/`results` with a kind-specific `details` object, and [`ddd map --format json`](/docs/guides/ddd#json-contract-1) emits `scope`/`projects`/`nodes`/`edges`
- **External map nodes** have two shapes: a typed out-of-scope endpoint keeps its URI as `id` and `canonical_ref`; an unresolvable or ambiguous plain key gets `id: external:ddd-context-key:<key>` and a null `canonical_ref`. Key on `external`, not on the shape of `id`
- **`--message` and `--message-kind` are an exact pair** against one structured `{ message, kind }` object — a message consumed as an `Event` does not match `--message-kind command` because something else is a command
- **Typed companions do not all cross project boundaries**: `subdomainRef`, aggregate `contextRef`, and a coordination owner `contextRef` must target the declaring project; `supersedesRefs`, `upstreamRef`, `downstreamRef`, `participantRefs`, and `flowRefs` may target another. A `supersedesRefs` key must also appear in the plain `supersedes` list, while a plain key with no local target stays valid

### Extension documentation caught up with two schema bumps
- **DDD**: [coordination mechanisms](/docs/guides/ddd#coordination-mechanisms) (`Reactor`, `ProcessManager`, `DurableWorkflow` and their supporting records, with the decision ladder), [lifecycle and succession](/docs/guides/ddd#lifecycle-and-succession) (`ContextStatus`, `supersedes`, `GlossaryTerm.replaces`), the `ContextMapping` endpoint refs, plus [`mori ddd coordination`](/docs/commands/ddd#mori-ddd-coordination), [`mori ddd map`](/docs/commands/ddd#mori-ddd-map), and `mori ddd search --status/--group`
- **OKF**: [provenance, trust, and staleness](/docs/guides/okf#provenance-trust-and-staleness) filters (`--generated-by`, `--unverified`, `--stale`), [typed concept links](/docs/guides/okf#typed-concept-links) (`--links-from`, `--links-to`, `--relation`), [publishing and consuming profiles](/docs/guides/okf#publishing-and-consuming-profiles) (`Project.profiles`, `OkfBundle.profileBinding`), and [`mori registry pins`](/docs/guides/okf#shared-pinned-imports)
- **Agent plans**: [`mori plans graph`](/docs/commands/plans#mori-plans-graph), the canonical Hard-dependency DAG
- **Tech radar**: [`projectRef` vs `project`](/docs/guides/tech-radar#project-vs-projectref) — one is resolved and fails `--check-refs`, the other is parsed and never resolved
- **Cookbook**: `CookbookEntry.tags`, and the `Canonical` / `CanonicalRef` location arms for cross-project entries

### Projection catalog drift is now a hard gate
- `mori automate daemon` registers its projection catalog **before** reading projection-backed configuration or starting any queue, API, ingest, outbox, schedule, reactor, or timer leg, and refuses to start when the catalog disagrees with what the database has registered
- `just migrate-verify` performs the same comparison at deploy time, after the ledger check, naming the rebuild group and both fingerprints. It changes no catalog metadata
- Restarting clears neither. Preview the group with the candidate binary, then [`mori ops rebuild adopt`](/docs/commands/ops#projection-catalog-drift) deliberately

### Six new guides
- [Signal Deliveries](/docs/guides/signal-deliveries) — delivery states, manual redrive, and the terminal refusals (consent, fan-out, cycle, depth) that are recorded rather than retried
- [Debugging Automation](/docs/guides/debug-automation) — the five-layer path from "nothing happened" to a root cause: registered config, ingested event, matching selector, executed reaction, delivered signal
- [Declarative Extensions](/docs/guides/extensions-declarative) — installing local data-only extensions, and why loading one cannot execute code
- [HTTP API](/docs/guides/api) — the loopback-first perimeter, bearer auth, CORS, Relay pagination, and the plan-graph exception to it
- [Project Identity](/docs/guides/project-identity) — the three identifiers mori distinguishes and what survives a rename
- [Registry Schema Upgrade](/docs/guides/registry-upgrade) — sweeping a schema bump across the registry, with selectors, dry-run, and safety rails

Every `mori help` topic now has guide coverage, either at the same slug or through a named consolidation.

### Registry projections are inline, not daemon-driven
- Every registry read model — projects, packages, dependencies, groups, relations, and the per-extension tables — is now written **inline**, in the same transaction as the event. The tables are current the moment `mori register` returns
- `mori automate daemon` still runs the reactive engine (automation routers, the reaction executor, signal and join routers, integration producers, webhook fan-out), but it is no longer required to populate the registry
- Guidance that told you to start the daemon and wait for a projection to catch up has been corrected across the docs

## 2026-08-07

### `Maintenance` lifecycle stage
- `Lifecycle` gained a fifth stage between `Experimental` and `Deprecated`: **`Maintenance`** — supported and receiving fixes, but not new features. Agents should read it as "fix bugs, don't propose features"
- `Maintenance` takes **no** `deprecation` record. A maintained project is still the right thing to depend on, so it has no replacement to name; guidance remains valid only for an effective `Deprecated` lifecycle
- [`mori registry list --lifecycle`](/docs/commands/registry#mori-registry-list) filters by stage, matched case-insensitively (`active`, `experimental`, `maintenance`, `deprecated`, `archived`) and composing with every other filter
- `Maintenance` renders in pale yellow alongside the existing pale-red `Deprecated` across `mori show`, `mori registry list`, `mori registry show`, and `mori registry search`
- Documented in [Getting Started](/docs/getting-started), the [Schema Guide](/docs/schema-guide#lifecycle), [Schema Reference](/docs/guides/schema-reference#lifecycle), and [Project Configuration](/docs/guides/project-config)

### `Decision` reaction action (new)
- New [`Decision`](/docs/guides/automation#decision) action runs a tool-neutral decision producer, durably checkpoints its structured result, and maps only *declared* outcomes to signals
- The producer speaks a `mori-decision/1` envelope on stdout (or via `resultFile`), with `status` of `ok`, `skip`, or `error`. `ok` requires exactly one outcome; `skip` derives the reserved outcome `skip`; `error` always fails
- Spawn failure, timeout, nonzero exit, invalid or oversized JSON (default cap 1 MiB), an unknown protocol, or trailing stdout fails the action **before any route dispatches**
- Routes are declarative — producer output never supplies signal types or targets. Payloads may interpolate `{{decision.status}}`, `{{decision.outcome}}`, and scalars below `{{decision.data.*}}`; all matching routes render successfully before any is dispatched
- The canonicalized envelope is checkpointed with a SHA-256 digest before routing, so a retry after the checkpoint converges every routed signal on the same logical identity
- Deliberately absent from the nested `ScheduledAction` union: use the reaction-level `schedule` field to defer a whole Decision
- `mori reaction show` prints the recorded outcome, digest, message, envelope, and routed emissions; `mori automate inspect` and `mori automate explain --json` show declared routes

### Signal delivery: structured payloads, predicates, consent, and bounds
- `SignalAction` gained `payloadJson`, a structured JSON document validated at config load time. The flat `payload` map is unchanged and both forms travel with the delivery
- `SignalSelector.signalTypes` entries are now **globs** (`"Schema*"`); `sourceProjects` remains an exact qualified-name match
- New [`payloadPredicates`](/docs/guides/cross-repo-workflows#payload-predicates) narrow a selector by payload content — `Equals`, `Prefix`, and `Exists` over a dotted JSON path, combined with AND. A one-segment path falls back to the flat payload
- New target-side [`consent`](/docs/guides/cross-repo-workflows#target-consent): `allowSignalsFrom` accepts qualified projects or bare namespaces. Absent means allow-all; a declared empty list denies all. A refusal is a terminal failed delivery with a `consent:` reason, never retried
- New emitter-side [`signalBounds`](/docs/guides/cross-repo-workflows#delivery-safety-bounds): `maxFanOut` (default 25) and `maxChainDepth` (default 8). Fan-out is all-or-nothing, and ancestor content digests catch repeated content as a cycle before the depth limit is reached
- New [`mori signal list`](/docs/commands/signal) command, with `--failed`, listing delivery id, signal type, source → target, state, retries, and failure reason

### Workflow chain tracing
- [`mori workflow trace`](/docs/commands/workflow#mori-workflow-trace) now walks to the chain root and renders every descendant workflow and target step as a tree — it can be started from any workflow in the chain
- New flags: `--flat` (the original single-workflow detail view), `--json`, `--mermaid` (a `flowchart LR` diagram), and `--max-depth N` (default 32)
- The HTTP equivalent is `GET /v1/workflows/<WORKFLOW_ID>/chain`. History predating workflow parent correlation is shown honestly as independent roots rather than guessed into a tree

### Reaction execution: enforced timeouts, contained processes, classified failures
- A `RunCommand` without an explicit `timeout` is no longer unbounded. The effective timeout resolves from the action's `timeout`, then `MORI_RUN_COMMAND_DEFAULT_TIMEOUT`, then a bounded **600-second** default. `timeout = Some +0` is now the only way to disable it, and an unparseable override is reported on stderr and ignored
- Commands run in their own process group. On timeout the executor `SIGTERM`s the **whole group**, waits five seconds, then `SIGKILL`s and reaps it — so a `nix develop --command just …` tree cannot be orphaned and left running behind a reaction recorded as timed out
- Action `env` is merged **over** the daemon's environment. The same timeout, containment, and merge rules are reused for a scheduled reaction's idempotency check
- `Notify` requests are bounded by the same timeout policy, and transport problems are preserved rather than swallowed: `curl`'s nonzero exit and stderr, a spawn failure (`127`), and unparseable status output each become actionable command failures
- New closed [failure taxonomy](/docs/guides/automation#failure-classification) — `timeout`, `spawn-failure`, `nonzero-exit`, `dependency-unavailable`, `decode-failure` — persisted as a wire contract that retry policy and the execution-status read model compare against, and reported by `mori doctor --reactions`
- The class now [decides the executor's response](/docs/guides/automation#what-each-failure-class-does-to-the-executor): `dependency-unavailable` retries with exponential backoff, `decode-failure` dead-letters, and `timeout`/`spawn-failure`/`nonzero-exit` are acknowledged — a failing command records a failed reaction and advances rather than stalling the leg or parking an event

### Reaction execution health and recovery
- New [`mori doctor --reactions`](/docs/commands/doctor#--reactions) audits reaction execution: stuck legs, open halts, and parked dead letters. Exits `2` when unhealthy, `0` otherwise
- [`mori reaction recover`](/docs/commands/reaction#mori-reaction-recover) gained two modes beyond the single-reaction one: `--dead-letters [--limit N]` reprocesses parked events through the live admission guard and executor, and `--clear-halt <leg>` closes a halt after its cause is repaired
- [`mori status`](/docs/commands/status) gained an **Automation execution** section and an `automationExecution` JSON field (`{"healthy", "unhealthyLegs"}`). An unhealthy line degrades the verdict to `attention` and points at `mori doctor --reactions`
- `mori doctor`'s baseline now prints the host identity and decodes every active automation registration, naming any that no longer decode

### `ProjectSelector` (new)
- New [`ProjectSelector`](/docs/guides/automation#projectselector) matches the normalized semantic envelope derived from committed Project and Project-artifact events, selecting typed aggregate boundaries, semantic families, artifact kinds, and actions instead of private event constructor names
- Bootstrap `Imported` facts are distinct from `Added` facts and stay suppressed unless `includeImported = True`
- Configuration loading, validation, and matching are available now; live Project-stream subscription and durable delivery remain disabled until the shared signal-delivery infrastructure lands

### Event-store operations commands (new)
- `mori projections` — `rebuild` (offline and destructive; requires `--yes`, supports `--model GROUP` and `--dry-run`) and `seed-checkpoints` (seeds side-effecting subscriptions at the store head so they never replay history)
- [`mori project`](/docs/commands/project) — `bootstrap-functional-streams` (with `--dry-run`) and `audit-functional-streams`
- `mori replay-audit` — read-only replay sweep with `--mode full|targeted`, `--event-type`, `--category`, `--max-streams`, `--parallelism`, `--resume-from`, and `--json`. Exits non-zero on any replay failure or seed divergence

### Daemon subscription observability
- [`mori automate daemon --metrics-port PORT`](/docs/commands/automate#mori-automate-daemon) (or `MORI_METRICS_PORT`) starts Kiroku's own metrics, health, and subscription-status server: `/metrics`, `/metrics/prometheus`, `/health/live`, `/health/ready`, `/subscriptions`
- Mori does not mirror or translate this surface — use Kiroku's released operator client against the same wire contract. `mori doctor`, `mori status`, and the HTTP API's probes keep their existing scopes
- **This server listens on all interfaces**, unlike the loopback-first HTTP API. Expose it only on a trusted network or behind an authenticated proxy

### Structural schema migrations
- `mori schema migrate` now selects targets from the parsed Dhall AST and splices exact source spans. Comments and formatting outside an edited span are preserved; overlapping, out-of-bounds, or non-parsing edit sets are rejected before any file is written
- Ambiguous targets no longer block safe ones: a legacy per-action `Schedule` wrapper migrates automatically when a reaction has exactly one, a non-negative delay, and no existing `schedule`, while mixed reactions are named for manual review and their safe siblings still migrate
- Unknown `mori/*.dhall` extension files are refused rather than guessed to be project files
- New [`mori schema check-compat --against REF|PATH`](/docs/commands/schema#mori-schema-check-compat) classifies changes at the normalized Dhall type level, with a three-way exit: `0` additive, `1` breaking, `2` needs review. `--json` emits the classified changes
- [`mori validate`](/docs/commands/validate#recorded-schema-hash) warns when a URL-pinned `mori.dhall` records a schema hash that differs from the binary's embedded semantic hash. Advisory only — mori ignores the pin, but external Dhall tooling will not

### OKF profile compilation
- Profiles are now **compiled before the bundle is read** — a field cannot be both required and recommended, a conditional rule cannot name an undeclared sibling, a reference policy cannot name a prefix no type owns. One advisory per independent mistake; a profile that fails to compile skips that bundle's rules without affecting indexing or other bundles
- Validation runs in okf-core's **permissive** mode: required rules and all constraints on present values are checked, while an absent `recommended` field stays silent
- Deviations name values by indexed structural path (`reviews[2].outcome`), zero-based
- Document references resolve local handles inside the bundle; an external URI is checked only for shape and permitted scheme (case-insensitively) and is **never resolved** — observe-time validation performs no `mori://` lookup, no network call, and no access outside the bundle directory
- Bundle examples now declare `okfVersion = "0.2"`
- Documented in the [OKF Bundles guide](/docs/guides/okf#advisory-profile-validation)

### HTTP API: loopback-first perimeter and Relay pagination
- [`mori serve`](/docs/commands/serve#security-perimeter) now binds `127.0.0.1` by default and **refuses** a non-loopback bind unless you set `MORI_API_TOKEN` for bearer auth or pass `--insecure-no-auth`. The refusal names the risk: `POST /v1/apps` returns live webhook signing secrets
- New flags `--host`, `--cors-origin` (repeatable, exact-origin only, no wildcard), and `--insecure-no-auth`; new environment variables `MORI_API_HOST`, `MORI_API_TOKEN`, and `MORI_API_CORS_ORIGINS`
- Bearer tokens are compared in constant time. `GET /health/live` and `GET /health/ready` stay reachable without a token so orchestrators can probe. The security contract is published in the generated OpenAPI document
- **Breaking:** eight unbounded collection endpoints (`/v1/projects`, `/v1/reactions`, `/v1/workflows`, `/v1/workflows/active`, `/v1/repositories/configs`, `/v1/repositories/ingest-status`, `/v1/groups`, `/v1/apps`) now return [Relay connections](/docs/commands/serve#pagination) instead of bare arrays, and accept `first`/`after`/`last`/`before`. A stale cursor returns `400` with a Relay page error, distinct from the RFC 9457 problem document used for application errors
- New `GET /v1/workflows/{id}/chain` — the HTTP equivalent of `mori workflow trace`

### First-class named automations
- An automation is now identified by `(repo, name)` rather than by repo alone. [`mori automate register`](/docs/commands/automate#named-automations), `deregister`, and `update` accept `--name NAME`, defaulting to `default` — so single-config repos are unaffected
- A repository can run several independently named automations, each with isolated routing and its own queue group, so a slow or failing automation cannot hold up a sibling
- `mori automate list` gained `--path` for filtering, and keys rows by `(repo, automation name)`

### Daemon double-start guard
- [`mori automate daemon`](/docs/commands/automate#one-executor-per-database) and `mori automate run` now take a PostgreSQL session advisory lock on a dedicated supervised connection, and refuse to start when another executor already holds it for the same database
- Advisory locks are per-database with a constant key, so the guard holds even when two processes reach the same database through differently-spelled connection strings. The lock releases on normal exit, exception, cancellation, or process death, so a crash never strands it

### Schema resolution diagnostics
- Schema imports resolve **only** from the binary's embedded copy — there is no network fallback. A manifest pinned to a commit the binary does not embed now [fails closed with a version-skew diagnostic](/docs/guides/schema-migrations#version-skew-diagnostics) naming the remedy, instead of producing a raw Dhall error
- When a file pins the *same* commit the binary embeds, the message says so and points at the import path — a typo, not skew
- Other config load failures are prefixed with a skew note only when the pins genuinely differ, and semantic validation failures render as actionable sentences

### Removed
- **`mori history`** and the legacy MessageDB path are gone. Kiroku is the only event store; `mori doctor` no longer checks the `message_store` schema, and pages that described the migration boundary now describe verification and rebuild via `mori replay-audit` and `mori projections` instead

### Also
- New `mori automate migrate-named` imports legacy registrations into the named `Automation` aggregate. Defaults to `--dry-run`; `--apply` additionally requires `--i-stopped-the-daemon`
- The [automation test repos](/docs/guides/automation-test-repos) fixture gained `decide.sh` and `handan-adapter.sh` for exercising Decision outcome routing end to end

## 2026-07-27

### `mori://` URIs cover every extension entity
- The artifact-kind grammar grew from 11 kinds to **21**, so every entity mori's schema extensions contribute is now addressable. New kinds: `checklists`, `upstream-issues`, `radar`, and the seven DDD kinds (`ddd/subdomains`, `ddd/contexts`, `ddd/aggregates`, `ddd/mappings`, `ddd/flows`, `ddd/glossary`, `ddd/collaborators`)
- The seven DDD kinds take a **two-segment** URI path; the bare `…/ddd` segment is not a ref and reports an unknown kind. Their compact tokens stay flat (`shinzui/mori#ddd-context:registry`)
- `MasterPlan`, `ExecPlan`, and `OkfBundle` gained Dhall arms, so **every** kind can now be named by a typed `Schema.MoriArtifactKind` value rather than only as canonical `Text`
- Two more nested grammars joined OKF concepts: `checklists/<key>/steps/<step>` and `ddd/flows/<key>/steps/<order>`. A nested sub-key on any other kind remains the one surviving "unsupported kind" warning
- `mori ddd`, `mori tech-radar`, `mori checklist`, and `mori upstream-issues` print canonical refs in their output and carry `canonicalRef` in JSON
- Plan refs are now **registry-verified**: a `plans/` or `masterplans/` ref resolves only if the owning project publishes that plan in `mori/agent-plans.dhall`. A registered plan whose markdown moved is reported distinctly from an unknown ref
- Three shapes can be ambiguous and report candidates instead of guessing: a duplicated OKF document handle, a short `radar/<package>` ref for a package recommended under two languages, and two glossary terms that slug alike
- [`mori validate --check-refs`](/docs/commands/validate) now walks **five** sources, adding `mori/tech-radar.dhall` (each recommendation's `project`) and `mori/agent-plans.dhall` (each plan's cross-project dependency targets)
- Shell completion walks the whole URI: kinds, keys, and the `ddd/` prefix as one entry. Nested sub-keys and partially-typed multi-segment keys deliberately offer nothing
- `mori help mori-refs` gained a **Reference fragility** section stating what breaks a ref of each kind — including the one silent failure, renumbering a DDD flow step
- Documented in [Mori URIs](/docs/guides/mori-refs) and [Canonical Refs](/docs/concepts/canonical-refs)

### Added: ingest health and recovery (previously undocumented)
- New [Ingest Health guide](/docs/guides/ingest-health) — the five ingest failure classes (`orphaned`, `malformed-commit`, `missing`, `transient`, `unknown`), the `mori.repository_ingest_status` read model, the stuck definition (3 consecutive failures, or no success in 6 hours), and recovery
