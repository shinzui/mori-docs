Mori's automation engine reacts to VCS events (commits, branch/tag changes) by
matching them against configurable selectors and executing actions. It runs as a
long-lived process that continuously processes events from the event store.

## Prerequisites

- Database set up and migrations run (see [Local Registry](/docs/concepts/local-registry))
- A `mori.dhall` project config in the current directory
- A repository initialized with `mori init` (provides the repo TypeID)
- A `flake.nix` at the repo root that exposes a default devShell. Mori spawns
  every `RunCommand` as `nix develop <repoRoot> --command <command> <args…>`,
  so any binary the reaction needs (`just`, `bun`, `direnv`, …) must be on
  the devShell's `nativeBuildInputs`. With this in place there's no need to
  wrap commands in `/bin/bash -lc "cd … && …"` to pick up nix-installed
  tools — the devShell hands them to the daemon for free.

> **Trying it out?** See [Automation Test Repos](/docs/guides/automation-test-repos)
> for three ready-made fixture repos (publisher, happy-path consumer,
> failure-path consumer) you can register against without scaffolding by hand.

## Configuration

Mori supports two ways to organize automation configs:

### Single file (default)

Create `mori.automation.dhall` in your project root. The file has three
top-level sections: event selectors, reactions, and an execution policy.

```dhall
let Schema = ./schema/package.dhall

in  Schema.Automation::{=}
```

Every field of `Schema.Automation.default` (`events = [] : List EventSelector`,
`reactions = [] : List Reaction.Type`, `execution = ExecutionPolicy.default`)
flows from the bundle, so the empty completion is already a complete, valid
config. Override any field by adding it to the completion:

```dhall
Schema.Automation::{
  reactions = [ Schema.Reaction::{ name = "tests", on = [ "src" ], actions = [ … ] } ]
}
```

### Config directory (multiple files)

For larger projects, you can split automation configs across multiple `.dhall`
files in a directory. Point the `-c` flag at the directory:

```bash
mori automate run -c ./automation/
```

All `.dhall` files in the directory are loaded (sorted alphabetically) and
merged into a single config:

- **Events** and **reactions** are concatenated from all files
- **Execution policy** is taken from the first file (alphabetically)
- Validation (unique selector names, valid reaction references) runs on the
  merged result

This lets you organize configs by concern — e.g., one file per team or
workflow:

```
automation/
  01-testing.dhall        # test-on-change selectors + reactions
  02-registry-sync.dhall  # registry sync reaction
  03-notifications.dhall  # release notification hooks
```

### Config resolution order

| Flag | Resolves to |
|------|-------------|
| (none) | `mori.automation.dhall` in the current directory |
| `-c path/to/file.dhall` | Single file at the given path |
| `-c path/to/directory/` | All `.dhall` files in the directory, merged |

### Generated templates

Use `mori automate generate` to create config templates:

```bash
mori automate generate registry-sync              # writes registry-sync.automation.dhall
mori automate generate registry-sync -o custom.dhall  # custom output path
```

Generated configs are standalone files you can use directly or place in a
config directory.

### Full example

Every record in `mori.automation.dhall` publishes the
`{ Input, Type, default, mk }` bundle. Prefer the `Schema.<Name>::{ … }`
completion form so additive schema upgrades upstream stay non-breaking — every
defaulted field flows from `default`.

```dhall
let Schema = ./schema/package.dhall

in  Schema.Automation::{
      events =
        [ Schema.EventSelector.ChangesetSelector Schema.ChangesetSelector::{
            name = "core-changes"
          , paths = [ "payments-core/**" ]
          , branches = [ "main" ]
          }
        , Schema.EventSelector.RefSelector Schema.RefSelector::{
            name = "release-tags"
          , refPatterns = [ "release/*" ]
          , kinds = [ "tag" ]
          }
        ]
    , reactions =
        [ Schema.Reaction::{
            name = "test-on-core-change"
          , on = [ "core-changes" ]
          , actions =
              [ Schema.ReactionAction.RunCommand Schema.RunCommandAction::{
                  command = "cabal"
                , args = [ "test", "payments-core" ]
                , timeout = Some +120
                }
              ]
          }
        , Schema.Reaction::{
            name = "notify-release"
          , on = [ "release-tags" ]
          , actions =
              [ Schema.ReactionAction.Notify Schema.NotifyAction::{
                  url = "https://hooks.example.com/releases"
                , bodyTemplate = Some "New release tag created"
                }
              ]
          }
        ]
    }
```

`execution` is omitted because `Schema.ExecutionPolicy.default`
(`allowLocal = True, allowCI = False, maxConcurrency = None Integer`) matches
what we want. An automation file with no overrides at all is a single line:
`Schema.Automation::{=}`.

## Event Selectors

Selectors define which events to watch. Each selector has a unique `name` used
to reference it from reactions.

### ChangesetSelector

Matches `ChangesetObserved` events (commits ingested via `mori automate ingest git`).

| Field | Type | Behavior |
|-------|------|----------|
| `name` | `Text` | Unique selector name |
| `paths` | `List Text` | Glob patterns for touched file paths. Empty = match all. |
| `branches` | `List Text` | Branch name patterns. Empty = match all. |
| `messagePatterns` | `List Text` | Commit message patterns. Empty = match all. |
| `trailerPatterns` | `List { mapKey, mapValue }` | Git trailer key/value patterns. Empty = match all. |

### RefSelector

Matches `RefObserved` events (branch/tag pointer changes).

| Field | Type | Behavior |
|-------|------|----------|
| `name` | `Text` | Unique selector name |
| `refPatterns` | `List Text` | Ref name patterns (e.g., `"main"`, `"release/*"`). Empty = match all. |
| `kinds` | `List Text` | `"branch"`, `"tag"`, or both. Empty = match all. |

### SignalSelector

Matches cross-repository signals delivered from another project. See
[Cross-Repo Workflows](/docs/guides/cross-repo-workflows#signal-selectors) for
signal type globs, payload predicates, and target consent.

### ProjectSelector

Matches the normalized semantic envelope derived from committed Project root and
Project artifact events. It selects typed aggregate boundaries, semantic
families, artifact kinds, and actions, so a selector does not have to depend on
private event constructor names.

| Field | Type | Behavior |
|-------|------|----------|
| `name` | `Text` | Unique selector name |
| `aggregates` | `List ProjectSignalAggregate` | `ProjectRoot` or `ProjectArtifact`. Empty = match all. |
| `families` | `List ProjectSignalFamily` | Stable family such as `Package`, `OkfConcept`, or `DddContext`. Empty = match all. |
| `artifactKinds` | `List ProjectArtifactKind` | Typed artifact kind. Empty = match all. |
| `actions` | `List ProjectSignalAction` | `Imported`, `Added`, `Updated`, or `Removed`. Empty = match all ordinary actions. |
| `eventTypes` | `List Text` | Exact private event type names. Empty = match all. |
| `projectIds` | `List Text` | Canonical `proj_` KindID v7 values. Empty = match all. |
| `references` | `List Text` | Canonical `mori://` project references. Empty = match all. |
| `includeImported` | `Bool` | Explicitly include bootstrap `Imported` facts. Default `False`. |

```dhall
Schema.EventSelector.ProjectSelector Schema.ProjectSelector::{
  name = "package-removals"
, aggregates = [ Schema.ProjectSignalAggregate.ProjectArtifact ]
, families = [ Schema.ProjectSignalFamily.Package ]
, artifactKinds = [ Schema.ProjectArtifactKind.PackageArtifact ]
, actions = [ Schema.ProjectSignalAction.Removed ]
, references = [ "mori://shinzui/mori" ]
}
```

Empty lists are wildcards, as everywhere else. `Imported` bootstrap facts are
distinct from `Added` facts and never alias them: they stay suppressed unless you
set `includeImported = True`, so a one-time backfill does not look like a
project genuinely gaining a hundred packages.

> **Availability.** ProjectSelector configuration loading, validation, and
> matching are available now. Live Project-stream subscription and durable
> delivery remain disabled until the shared signal-delivery infrastructure is
> implemented, so a ProjectSelector will validate but not yet fire.

### Glob patterns

- `*` matches any characters within a single path segment (stops at `/`)
- `**` matches any characters across path segments (crosses `/`)
- Empty pattern lists act as wildcards — they match everything

Examples:

| Pattern | Matches | Does not match |
|---------|---------|----------------|
| `src/**` | `src/Foo.hs`, `src/a/b/c.hs` | `test/Foo.hs` |
| `*.cabal` | `mori.cabal` | `src/mori.cabal` |
| `src/*.hs` | `src/Main.hs` | `src/Mori/Core.hs` |
| `release/*` | `release/v1.0` | `release/v1/patch` |

### Trailer matching

The `trailerPatterns` field matches commits by git trailer key/value pairs.
Each entry requires the trailer key to be present and its value to match the
glob pattern. All entries must match (conjunction). Empty = match all.

```dhall
Schema.EventSelector.ChangesetSelector Schema.ChangesetSelector::{
  name = "intention-commits"
, branches = [ "main" ]
, trailerPatterns = [ { mapKey = "Intention", mapValue = "intention_*" } ]
}
```

This matches any commit on `main` with an `Intention` trailer whose value
starts with `intention_`.

### Event-data interpolation

Action fields support `{{variable}}` template syntax. Templates are expanded
at trigger time before the reaction is written to the event store, so resolved
values appear in reaction history.

| Variable | Source |
|----------|--------|
| `{{changeset.id}}` | Commit hash |
| `{{changeset.subject}}` | First line of commit message |
| `{{changeset.body}}` | Full body (empty if None) |
| `{{changeset.timestamp}}` | Committer timestamp (ISO 8601) |
| `{{changeset.author.name}}` | Author name |
| `{{changeset.author.email}}` | Author email |
| `{{changeset.committer.name}}` | Committer name |
| `{{changeset.committer.email}}` | Committer email |
| `{{trailer.<Key>}}` | Trailer value (e.g., `{{trailer.Intention}}`) |
| `{{meta.<Key>}}` | Event metadata value |
| `{{ref.name}}` | Ref name (for RefObserved) |
| `{{ref.target}}` | Target object ID (for RefObserved) |
| `{{signal.type}}` | Delivered signal type |
| `{{signal.source}}` | Qualified source project name |
| `{{signal.deliveredAt}}` | Actual delivery time (ISO 8601) |

For a receiving signal reaction, `{{meta.<Key>}}` reads the corresponding flat
payload value. Unknown variables are left as-is, and the daemon logs one warning
naming the reaction, triggering event, and unresolved placeholders. Optional
values represented in the context expand to an empty string.

Example using interpolation with trailer matching:

```dhall
Schema.ReactionAction.RunCommand Schema.RunCommandAction::{
  command = "rei"
, args = [ "action", "record", "--at", "{{changeset.timestamp}}", "--intention", "{{trailer.Intention}}" ]
, timeout = Some +60
, env =
    [ { mapKey = "COMMIT_SHA", mapValue = "{{changeset.id}}" }
    , { mapKey = "COMMIT_AUTHOR", mapValue = "{{changeset.author.name}}" }
    ]
}
```

## Reactions

Reactions bind selectors to actions. When any selector listed in `on` matches an
event, all `actions` execute.

```dhall
Schema.Reaction::{
  name = "test-on-change"
, on = [ "core-changes", "api-changes" ]    -- triggers on either selector
, actions = [ ... ]                          -- all actions run
}
```

## Action Types

### RunCommand

Execute a shell command. Every `RunCommand` is spawned as
`nix develop <repoRoot> --command <command> <args…>` against the target
repo's flake — so the command runs inside the project's devShell and any
binary on that devShell's `nativeBuildInputs` is reachable. This is why
every target repo must have a `flake.nix` exposing a default devShell (see
[Prerequisites](#prerequisites)).

```dhall
Schema.ReactionAction.RunCommand Schema.RunCommandAction::{
  command = "make"
, args = [ "test" ]
, workingDir = Some "./packages/core"
, timeout = Some +300              -- seconds
, env = [ { mapKey = "CI", mapValue = "true" } ]
}
```

| Field | Type | Notes |
|-------|------|-------|
| `command` | `Text` | Executable name or path. Resolved inside the devShell, not the daemon's PATH. |
| `args` | `List Text` | Command arguments |
| `workingDir` | `Optional Text` | Working directory. When absent, defaults to the repo root (the directory passed to `mori automate register --path …`). When set, resolves relative to that root. |
| `timeout` | `Optional Integer` | Timeout in seconds. Absent means the effective default — see below |
| `env` | `List { mapKey, mapValue }` | Extra environment variables, merged over the daemon's own environment |

#### Timeouts are always enforced

A command without a `timeout` is **not** unbounded. The effective timeout is
resolved in this order:

1. The action's own `timeout`, when set
2. `MORI_RUN_COMMAND_DEFAULT_TIMEOUT` in the daemon's environment
3. A bounded default of **600 seconds** (10 minutes)

`timeout = Some +0` explicitly disables the timeout — that is the only way to
run genuinely unbounded, and it has to be written down. An unparseable
`MORI_RUN_COMMAND_DEFAULT_TIMEOUT` is reported on stderr and ignored in favour
of the default, rather than silently changing the bound.

#### Process trees are contained, not just signalled

Commands are spawned in their own process group. On timeout the executor
signals `SIGTERM` to the **whole group**, allows a five-second grace period,
then `SIGKILL`s and reaps the group.

This matters because a reaction usually runs `nix develop --command just …`,
which is a tree several processes deep. Killing only the direct child would
leave the real work orphaned and still running while the reaction is recorded
as timed out.

#### Environment merge order

The action's `env` map is merged **over** the daemon's environment, so an entry
you declare wins over an inherited one of the same name. The daemon's
environment is otherwise inherited intact.

The same timeout, containment, and merge rules are reused for a scheduled
reaction's [idempotency check](#idempotency-check), so a hung check cannot pin
the schedule worker either.

### EmitEvent

Record an event-emission intent in the reaction result. The action carries the
target stream and event type; the executor currently records the intent rather
than directly appending a custom event itself.

```dhall
Schema.ReactionAction.EmitEvent Schema.EmitEventAction::{
  eventType = "DeployRequested"
, streamName = "deployment-staging"
, eventData = [ { mapKey = "env", mapValue = "staging" } ]
}
```

### Notify

Send an HTTP request (uses `curl` under the hood).

```dhall
Schema.ReactionAction.Notify Schema.NotifyAction::{
  url = "https://hooks.slack.com/services/..."
, method = Some "POST"
, headers = [ { mapKey = "Content-Type", mapValue = "application/json" } ]
, bodyTemplate = Some "{\"text\": \"Build complete\"}"
}
```

`curl` is bounded by the same timeout policy as `RunCommand` (`--max-time`
resolved from `MORI_RUN_COMMAND_DEFAULT_TIMEOUT`, else 600 seconds), so a
notification endpoint that stops responding cannot hang the executor.

Transport problems are recorded as actionable failures rather than swallowed:

| Outcome | Recorded as |
|---------|-------------|
| Request completed | The HTTP status code. A status of `400` or above fails the reaction |
| `curl` exited nonzero | A command failure carrying `curl`'s exit code and stderr |
| `curl` could not be spawned | A command failure with exit code `127` and the spawn error |
| `curl` printed an unparseable status | A command failure naming the unparsable output |

The distinction that survives into the record is *why* it failed: a `500`
response classifies as `nonzero-exit` with the HTTP status, while an unreachable
host classifies from `curl`'s own exit — so "they rejected it" and "we never got
there" do not look the same afterwards.

### Failure classification

Every failing action is classified into a closed, stable taxonomy. These class
tags are a wire contract: retry policy and the execution-status read model
persist and compare them, and they are what
[`mori doctor --reactions`](/docs/commands/doctor#--reactions) reports as
`last error`.

| Class | Meaning |
|-------|---------|
| `timeout` | The command exceeded its timeout and its process group was killed |
| `spawn-failure` | The process could not be started at all — missing binary, bad path, no devShell |
| `nonzero-exit` | The command ran and exited non-zero (including an HTTP status ≥ 400 from `Notify`) |
| `dependency-unavailable` | A database, queue, or network dependency was unavailable |
| `decode-failure` | A payload or identifier could not be decoded |

Each carries a bounded human-readable detail alongside the class, truncated so a
runaway error message cannot bloat the status row. When a reaction has several
actions, the **first** failure in action order is the one classified.

The `spawn-failure` / `nonzero-exit` split is the one worth internalising:
`spawn-failure` almost always means the devShell or the `command` name is wrong,
while `nonzero-exit` means your command ran and disagreed with you.

### What each failure class does to the executor

Classification is not just labelling — it decides whether the event is retried,
parked, or acknowledged:

| Class | Executor response |
|-------|-------------------|
| `dependency-unavailable` | **Retry** with exponential backoff and jitter |
| `decode-failure` | **Dead-letter** the event as an invalid payload |
| `timeout`, `spawn-failure`, `nonzero-exit` | **Acknowledge** — record the reaction as failed and move on |

The third row is the important one. A reaction whose command fails does **not**
stall the executor, park an event, or halt a leg: it is recorded as `failed`,
the subscription advances, and the next reaction runs. Fixing your command and
re-triggering is the whole recovery path — there is nothing to un-park.

Parked events come from `decode-failure` — mori could not read the event at all,
so it preserves the evidence instead of guessing. That is what
[`mori reaction recover --dead-letters`](/docs/guides/reaction-history#recover-parked-events)
is for, and why it re-runs decoding rather than re-running your command.

A `dependency-unavailable` retry is bounded; appending a terminal outcome has
its own short retry schedule (1s, 2s, 4s) so a brief database blip does not lose
the record of what already happened.

Use [`mori doctor --reactions`](/docs/commands/doctor#--reactions) to see which
of these you are actually looking at before reaching for a recovery command.

### Signal

Emit a cross-repository workflow signal through mori's durable delivery domain.

```dhall
Schema.ReactionAction.Signal Schema.SignalAction::{
  signalType = "SchemaChanged"
, targets = [ "shinzui/rei", "shinzui/mori" ]
, payload = [ { mapKey = "version", mapValue = "v2" } ]
}
```

See [Cross-Repo Workflows](/docs/guides/cross-repo-workflows) for dynamic
targets, the structured `payloadJson` payload, target consent, and fan-out and
chain-depth bounds.

### Decision

Run a tool-neutral decision producer, durably checkpoint its structured result,
and map only *declared* outcomes to signals. Use it when the branch a workflow
should take depends on a judgement some external tool makes — a release
classifier, a risk check, a policy engine — and you want that judgement recorded
rather than inferred from an exit code.

```dhall
Schema.ReactionAction.Decision Schema.DecisionAction::{
  command = "./decide.sh"
, timeout = Some 30
, maxResultBytes = Some 1048576
, routes =
    [ Schema.DecisionRoute::{
        outcome = "proceed"
      , signalType = "ReleaseReady"
      , targets = [ "shinzui/release" ]
      , payload =
          [ { mapKey = "category"
            , mapValue = "{{decision.data.category}}"
            }
          ]
      }
    , Schema.DecisionRoute::{
        outcome = "hold"
      , signalType = "ReleaseHeld"
      , targets = [ "shinzui/release" ]
      }
    ]
}
```

| Field | Type | Behavior |
|-------|------|----------|
| `command` | `Text` | Decision producer program or script (required) |
| `args` | `List Text` | Command-line arguments |
| `workingDir` | `Optional Text` | Working directory (`None` = project root) |
| `timeout` | `Optional Natural` | Timeout in seconds |
| `env` | `Map Text Text` | Extra environment variables |
| `resultFile` | `Optional Text` | Read the envelope from this path (relative to `workingDir`) instead of stdout |
| `maxResultBytes` | `Optional Natural` | Maximum result size (`None` = 1 MiB) |
| `routes` | `List DecisionRoute` | Declared outcome-to-signal routes |

Execution has the same `nix develop`, working directory, environment, timeout,
process-group termination, and nonzero-exit behavior as
[`RunCommand`](#runcommand). By default the producer writes exactly one bounded
JSON value to stdout; set `resultFile` to read a file after a successful process
exit instead.

#### The `mori-decision/1` envelope

```json
{
  "protocol": "mori-decision/1",
  "status": "ok",
  "outcome": "proceed",
  "data": { "category": "Breaking", "confidence": 0.95 },
  "message": "release may proceed",
  "trace": "trace-123"
}
```

`protocol` and `status` are required. `status` is `ok`, `skip`, or `error`:

- `ok` requires exactly one string `outcome`.
- `skip` forbids an outcome and derives the reserved outcome `skip`, so it routes
  only when you declare a `skip` route.
- `error` forbids an outcome and always fails the action.

`data`, when present, must be an object. `message` and `trace` are optional
strings. Spawn failure, timeout, nonzero exit, invalid or oversized JSON, an
unsupported protocol, trailing non-whitespace on stdout, and `status = "error"`
all fail the action **before any route dispatches** — a broken producer never
emits half its signals.

#### Routes

Routes are declarative: producer output supplies the outcome and data, never the
signal type or the targets. Every route matching the outcome runs, in
declaration order.

Payload values may interpolate `{{decision.status}}`, `{{decision.outcome}}`, or
a scalar below `{{decision.data.<path>}}`. A missing, null, object, or array
value fails validation before the first matching route is emitted, so a
half-rendered fan-out is not possible.

#### Checkpointing and retries

Mori canonicalizes the validated envelope and checkpoints it with a SHA-256
digest on the Reaction stream *before* it dispatches any route. A retry before
that checkpoint may rerun the producer; a retry after it reuses the checkpoint
and converges every routed signal on the same logical identity. Immediate,
whole-reaction scheduled, and queued FIFO reactions all behave this way.

Inspect what a Decision did with
[`mori reaction show REACTION_ID`](/docs/commands/reaction) — the recorded
outcome, digest, message, envelope, and routed emissions. `mori automate inspect`
(or `--json`) shows declared routes, and `mori automate explain POSITION --json`
shows them on matched reactions.

#### Where Decision cannot go

`Decision` is deliberately absent from the nested `ScheduledAction` union. An
action-level `Schedule` child runs after its parent Reaction may already be
terminal, so it cannot safely append that Reaction's required checkpoint. When
the whole Decision should be deferred, use the reaction's
[`schedule` field](#scheduled-reactions) instead.

### Schedule (legacy, single-action)

Defer an action for later execution via pgmq + shibuya.

```dhall
Schema.ReactionAction.Schedule Schema.ScheduleAction::{
  delaySeconds = +300
, action = Schema.ScheduledAction.RunCommand Schema.RunCommandAction::{
    command = "make"
  , args = [ "deploy", "staging" ]
  , timeout = Some +600
  }
}
```

Nested scheduled actions can be `RunCommand`, `EmitEvent`, `Notify`, or
`Signal` — but not another `Schedule` (no recursive scheduling) and not
[`Decision`](#where-decision-cannot-go).

> **Prefer per-reaction `schedule` for new code.** The action-level
> `Schedule` wrapper above is preserved for backwards compatibility, but
> the [Scheduled Reactions](#scheduled-reactions) feature below (a
> `schedule` field on the whole reaction) is more expressive: it covers
> multi-action reactions, supports a pre-execution idempotency check, and
> supports debounce via a coalesce key.

#### Migrating a legacy `Schedule` wrapper

The schema migrator can lift an unambiguous legacy wrapper into the per-reaction
`schedule` field:

```bash
mori schema migrate --apply --file mori.automation.dhall
```

A reaction migrates automatically only when its `actions` list contains exactly
one `Schedule` action, its delay is non-negative, and its `schedule` field is
absent or `None`. The inner action and the comments inside its payload are
preserved, and `delaySeconds = +30` becomes `schedule.after = Some "PT30S"`.

Mixed or multiple actions, a negative delay, or an already populated `schedule`
are refused *by reaction name* for manual review — and safe sibling reactions in
the same file still migrate. Re-running after a successful migration is a no-op,
and the legacy wrapper remains supported for projects that choose not to
migrate.

`--file` names the file, but the file *kind* is inferred from the filename, and
only `mori.automation.dhall` is inferred as an automation config. A named
registration living under another name is read as an ordinary project config: the
automation migrations are never considered and the command reports nothing
pending. State the kind explicitly for those:

```bash
mori schema migrate --apply --kind automation --file automation/release.dhall
```

`automation` is the only supported `--kind` override; path inference is unchanged
for every other file.

## Scheduled Reactions

By default, a reaction runs immediately when its trigger fires. Sometimes
you want to defer the whole reaction — "run a release-readiness check 1
hour after the merge commit", "send a follow-up notification 1 day later",
"build only once after the most recent of a burst of commits". The optional
`schedule` field on a reaction turns it into a **scheduled reaction**.

Whole-reaction scheduling and the queued policy below apply uniformly to
reactions selected by Repository facts, Project facts, successful incoming
SignalDelivery receipts, and Join triggers.

### Minimal example

```dhall
Schema.Reaction::{
  name = "deferred-build"
, on = [ "main-commit" ]
, schedule = Some Schema.Schedule::{
    after = Some "PT1H"
  }
, actions =
    [ Schema.ReactionAction.RunCommand Schema.RunCommandAction::{
        command = "make"
      , args = [ "release" ]
      }
    ]
}
```

When `main-commit` fires, mori enqueues a `ScheduledReactionPayload` on the
`scheduled_reactions` pgmq queue with a 1-hour delay and emits
`ReactionScheduled`. After one hour, the worker pops the message and runs
the reaction's actions.

### Duration syntax (`after`)

`after` is an ISO 8601 duration string. The parser supports:

| Example | Meaning |
|---------|---------|
| `PT30S` | 30 seconds |
| `PT5M` | 5 minutes |
| `PT1H30M` | 1 hour 30 minutes |
| `P1D` | 1 day |
| `P1DT2H3M4S` | 1 day, 2 hours, 3 minutes, 4 seconds |

Years (`Y`) and weeks (`W`) are not supported. Internally `after` is stored
as seconds.

### Idempotency check

A common pattern is "schedule this work for an hour from now, but only run
it if it's still needed when the hour is up." Add an `idempotencyCheck`:

```dhall
schedule = Some Schema.Schedule::{
  after = Some "PT1H"
, idempotencyCheck = Some Schema.IdempotencyCheck::{
    command = "./scripts/should-still-run.sh"
  , args = [] : List Text
  , timeout = Some +30
  , skipOnExit = Schema.SkipOnExit.NonZero
  }
}
```

Just before the worker runs the reaction's actions, it runs the check
command. If the command's exit code matches `skipOnExit`, the reaction is
skipped (`ReactionSkipped` is emitted) and the actions do **not** run.
Otherwise the actions run as normal.

`skipOnExit` is one of:

- `Schema.SkipOnExit.Zero` — skip when the check exits 0.
- `Schema.SkipOnExit.NonZero` — skip when the check exits non-zero.

The check command runs in the repository working directory with the
following environment variables set:

| Variable | Contents |
|----------|----------|
| `MORI_REACTION_ID` | The unique id of this scheduled reaction |
| `MORI_AUTOMATION_NAME` | Basename of the automation config file |
| `MORI_REACTION_NAME` | The reaction's `name` field |
| `MORI_REPO_ID` | The mori repository id |
| `MORI_TRIGGER_STREAM` | Stream that triggered this reaction |
| `MORI_TRIGGER_POSITION` | Position of the triggering event |
| `MORI_TRIGGER_EVENT_TYPE` | E.g. `ChangesetObserved` |
| `MORI_TRIGGER_EVENT_ID` | UUID of the triggering event |
| `MORI_SCHEDULED_AT` | When the reaction was enqueued (UTC) |
| `MORI_RUN_AT` | When the worker plans to run (UTC) |
| `MORI_COALESCE_KEY` | Coalesce key, or empty if none set |

Any `env` map you put on `IdempotencyCheck` is merged on top of these, so
you can pass custom values to the check.

If the check command times out (default 60 seconds, override with
`timeout`) the worker treats it as exit code 124 and consults `skipOnExit`.
If the check command fails to launch (file not found or not executable),
the reaction is marked **failed** with `ReactionFailed`.

### Debounce: `coalesceKey`

Without a coalesce key, repeated triggers **stack**: each trigger schedules
its own deferred run. Use `coalesceKey` to opt into debounce — only the
most recent schedule survives per
`(repository, automation, reaction-name, coalesceKey)` tuple:

```dhall
schedule = Some Schema.Schedule::{
  after = Some "PT1H"
, coalesceKey = Some "deferred-build"
}
```

When a second trigger arrives while the first is still pending, the daemon:

1. Emits `ReactionCancelled` against the first reaction with
   `reason = "superseded by <new-reaction-id>"`.
2. Calls `pgmq.delete` on the first reaction's queue message.
3. Enqueues the new schedule.

The pending-schedules projection sees the cancellation and removes the
first row from `mori.pending_scheduled_reactions`.

### Inspecting and cancelling

List, inspect, and cancel pending scheduled reactions with `mori reaction`:

```bash
mori reaction scheduled list
mori reaction scheduled show rxn_01HZ...
mori reaction cancel rxn_01HZ... --reason "release window closed"
```

See [Reaction History › Scheduled List](/docs/guides/reaction-history#scheduled-list)
for the full command reference and lifecycle.

## Execution Policy

Declares where and how the automation's actions are *intended* to run.

```dhall
Schema.ExecutionPolicy::{
  allowLocal = True           -- declares local execution allowed
, allowCI = False             -- declares CI execution allowed
, maxConcurrency = Some +4    -- declared parallel-action cap
}
```

`ExecutionPolicy` has no required (`Input`) fields — `allowLocal` and
`allowCI` default to `True` / `False` and `maxConcurrency` defaults to
`None Integer`. Override only what differs from the published default.

> **None of these three fields is enforced yet.** They are parsed, validated,
> carried in the config observation event, and printed by
> `mori automate inspect` — and nothing reads them at execution time. The
> executor runs every triggered action regardless of `allowLocal` and
> `allowCI`, and does not bound parallelism by `maxConcurrency`. Setting
> `allowLocal = False` will **not** stop a reaction from running on your
> machine, and `maxConcurrency = Some +1` will **not** serialize anything.
>
> Treat them as declared intent. The enforced control is
> [Queued execution](#queued-execution). Enforcement of the policy itself is
> tracked by `mori://shinzui/mori/okf/improvement-requests/concepts/IR-14`.

## Queued execution

`queued` is the execution control that *is* enforced. It is a field of the
automation, not of a reaction:

```dhall
Schema.Automation::{
  queued    = True
, reactions = [ … ]
}
```

With `queued = True`, every reaction the automation triggers — immediate and
scheduled alike — goes onto the `queued_reactions` pgmq FIFO queue instead of
executing as soon as it is routed. Messages are grouped by
`"<repoId>:<automationName>"` and drained in strict trigger order, one in
flight per group.

| | Behaviour |
|---|---|
| Two reactions of the **same** automation | Serialized — the second starts only after the first reaches a terminal state |
| Reactions of **different** automations (or repos) | Still concurrent — different groups |
| A reaction with `schedule = Some …` | Keeps its delay; `after` becomes the queue visibility delay, then it joins the group |
| A reaction with no `schedule` | Enqueued with delay 0 |
| A reaction whose `after` is malformed | Logged and enqueued at delay 0 — it never degrades to immediate execution, because leaving the queue would break ordering |

Queued reactions do not arm a durable timer, and `mori reaction list` reports
them with source `queued-fifo` rather than `immediate-executor` or
`schedule-timer`.

On the daemon side, `--queued-concurrency N` (default 3) bounds how many
distinct groups drain at once. It never weakens ordering *within* a group.

```bash
mori automate daemon --queued-concurrency 8
```

The discipline is strictly first-in-first-out. A newest-first (LIFO)
discipline is requested by
`mori://shinzui/mori/okf/improvement-requests/concepts/IR-8` and is not
implemented.

## Workflow

### 1. Ingest VCS events

Ingest git history into the local event runtime:

```bash
mori automate ingest git
```

This reads new commits since the last ingestion and writes `ChangesetObserved`
and `RefObserved` repository events. Ingestion is cursor-tracked, so only new
commits are processed on subsequent runs.

To ingest from a different repository path:

```bash
mori automate ingest git --path /path/to/repo
```

> **Note:** If you use the daemon (`mori automate daemon`), it auto-ingests
> all observed projects periodically — you don't need manual `ingest` calls.
> See the [Automation Daemon](/docs/guides/automation-daemon) guide for the
> full daemon behavior, including `--ingest-interval`.

### 2. Start the automation engine

```bash
mori automate run
```

This starts a long-running process with concurrent processors:

| Processor | Listens to | Purpose |
|-------------|------------|---------|
| `mori-automation` | `repository` events | Match selectors, trigger reactions |
| `mori-reaction-executor` | `reaction` events | Execute triggered actions |
| `mori-registry` | `project` events | Populate registry read model |
| `mori-workflow` | `workflow` events | Maintain workflow projections |

Plus queue processors for scheduled work. `scheduled_actions` and
`scheduled_reactions` run as keiro-pgmq jobs, which bundle the queue name,
payload codec, retry policy, and dead-letter queue. Webhook deliveries remain on
the existing pgmq adapter.

On startup, `automate run` also:
- Emits a `MoriAutomationObserved` event (idempotent by config hash)
- Emits a `MoriConfigObserved` event if `mori.dhall` exists
- Creates pgmq queues for scheduled actions, scheduled reactions, webhook deliveries, and the keiro-pgmq dead-letter queues

Use `-c` to specify a custom config path:

```bash
mori automate run -c path/to/mori.automation.dhall
```

### 3. Hot-reload

When the automation config changes, re-run `mori automate run` in a separate
terminal (or restart). The new config hash triggers a `MoriAutomationObserved`
event, and the running subscription detects the hash change and reloads the
config from disk via its IORef.

### 4. Inspect configuration

View a summary of the current automation config and reaction statistics:

```bash

```


## Event Flow

```
git commits
    │
    ▼
mori automate ingest git          (manual / CI)
── or ──
daemon auto-ingest loop           (periodic, every --ingest-interval seconds)
    │
    ▼  ChangesetObserved / RefObserved events
    │  written to repository-{repo_id} stream
    │
    ▼
mori automate run / daemon
    │
    ├─ mori-automation processor
    │  reads repository events
    │  matches against selectors
    │  triggers reactions
    │      │
    │      ▼  ReactionTriggered events
    │      │  written to reaction-{id}:{name} stream
    │      │
    │      ▼
    ├─ mori-reaction-executor processor
    │  reads reaction events
    │  executes RunCommand / Notify / EmitEvent
    │  writes ReactionCompleted / ReactionFailed
    │
    └─ shibuya worker
       processes delayed Schedule actions from pgmq
```

## Multi-Repo Automation

Single-repo mode (`mori automate run`) processes events for one repository.
For workspaces with many projects, the [automation daemon](/docs/guides/automation-daemon)
runs a single process that routes events to all registered repos.

### Registering with the daemon

A single `mori automate register` is enough to make a repo receive signals.
The command both registers the automation config with the daemon **and**
emits the `ProjectRepoLinked` event that records the repo in the projects
read model. There is no longer a separate `mori observe` prerequisite.

```bash
mori automate register                              # uses mori.automation.dhall
mori automate register -c path/to/config.dhall      # custom config path
mori automate register --path /path/to/repo         # different repo
```

`--path <dir>` is the authoritative repo root: the config file is read from
`<dir>` (so `--config` resolves relative to it), and the repo TypeID is
derived from `<dir>`. This makes it impossible to silently register repoA's
config against repoB's id by running from the wrong working directory.

Running `mori observe` against an already-registered repo is a no-op rather
than a duplicate write; it remains the right command when you want to record
a repo's identity *without* attaching an automation config (e.g., so the
daemon's auto-ingest loop will pick up its commits).

### Updating after edits

```bash
mori automate update
```

`update` heals state left over from older daemon builds: if a registered
repo is missing its `mori.projects` row (an artifact of pre-EP-4 register
flows), `update` re-emits `ProjectRepoLinked` so the row appears.

## Troubleshooting Failed Reactions

### Inspecting a failed reaction

When a reaction fails (non-zero exit, missing binary, unreachable notify URL,
or any other runtime error in the executor), `mori reaction list` shows the
row with `status: failed`. Drill in with `mori reaction show <id>`:

```
  Status: ✗ failed
  Started At: 2026-04-24 15:05:22.12345 UTC
  Completed At: 2026-04-24 15:05:22.93821 UTC
  Duration: 816ms

  Error:
    Command failed (exit 127): spawn failed: /usr/local/bin/just: …

  Stdout:
    compiling src/main.c

  Stderr:
    error: unknown type 'foo'
```

The `Stdout:` and `Stderr:` blocks carry whatever the failing `RunCommand`
wrote to those streams before it exited. Non-command actions (`EmitEvent`,
`Notify`, `Schedule`, `Signal`) leave both blocks empty. The `Error:` field
is the high-level summary — `Command failed (exit N): <stderr text>` for
bad commands, `Notification failed (HTTP M)` for notify failures.

### Why config edits don't fix an already-triggered reaction

When a reaction is triggered, the executor freezes a full snapshot of the
reaction's `actions` into the `ReactionTriggered` event. The subscription
then reads that event back to run the actions. Editing
`mori.automation.dhall` and reloading the daemon **does not** change a
reaction that has already been triggered — the event is immutable, and the
frozen payload is the source of truth.

To apply a config fix: edit the config, run `mori automate update`, wait
for (or manually emit via `mori automate ingest git`) a fresh source event,
and the next `ReactionTriggered` event will carry the new payload.

### Recovering a stuck reaction from a pre-EP-6 daemon

Older daemon builds (before commit `76c9f6f`) did not catch exceptions
inside the executor subscription. A `RunCommand` that failed at spawn time
(for example because `just` was not on the daemon's PATH) would halt the
`mori-reaction-executor` subscription; the reaction row stayed at
`status: triggered` indefinitely and no subsequent reaction fired. Recent
builds no longer have this failure mode — the executor wraps
`executeActions` in an exception boundary and records a `ReactionFailed`
event on any uncaught error.

If your database still has a reaction stuck in `status: triggered` from a
pre-fix daemon build, use `mori reaction recover <id>` to unstick it
without writing SQL by hand:

```
$ mori reaction recover rxn_01k000000000000000000000TEST
Advanced executor checkpoint to 12345.
Reaction rxn_01k000000000000000000000TEST marked failed: manually recovered via mori reaction recover.
Restart the daemon (or wait for the next poll) to resume processing.
```

The default `recover` marks the stuck row `failed` with the canonical
error message `manually recovered via mori reaction recover` and advances
the `mori-reaction-executor` subscription's checkpoint past the stuck
event so the next reaction fires normally. Add `--retry` to additionally
re-emit a fresh `ReactionTriggered` carrying the original actions under a
new reaction ID — use this when you've already fixed the root cause
(PATH, missing binary, bad cwd) and want the action to run again. The
command refuses to operate on rows already in `completed` or `failed`
state (exit code 2, "nothing to recover").

> **Safety.** `recover` updates the `checkpoints` table directly. Running
> it while the daemon is actively processing the same subscription can
> race with the live consumer. It is safe against a genuinely stuck
> subscription (which, by definition, is not advancing), but stop the
> daemon first if you are unsure — or simply re-run the command; it is
> idempotent on non-triggered rows.
