The automation daemon manages automation for all registered repos from a
single long-running process. Instead of running `mori automate run` in each
repo, the daemon discovers repos from the local runtime, loads their
automation configs, and routes events to the correct repo automatically.

## Usage

```bash
mori automate daemon
mori automate daemon --ingest-interval 30      # faster cycle for development
mori automate daemon --ingest-interval 0       # disable auto-ingest
mori automate daemon --refresh-interval 120    # config-refresh cycle
mori automate daemon --queued-concurrency 6    # FIFO queued automation workers
mori automate daemon --serve                   # also serve the HTTP API
mori automate daemon --metrics-port 9464       # also serve Kiroku's operator surface
```

### Flags

| Flag | Default | Purpose |
|------|---------|---------|
| `--refresh-interval SECONDS` | 60 | Interval between config-refresh cycles |
| `--ingest-interval SECONDS` | 300 | Interval between auto-ingest cycles (`0` to disable) |
| `--queued-concurrency N` | 3 | Number of FIFO worker instances for `queued = True` automations |
| `--serve` | off | Also serve the [HTTP API](/docs/commands/serve) from this process |
| `--api-port PORT` | 8080 / `$MORI_API_PORT` | Port for the embedded HTTP API |
| `--metrics-port PORT` | off / `$MORI_METRICS_PORT` | Port for Kiroku's metrics, health, and subscription-status server |

Serving the API is opt-in — enabled by `--serve`, an explicit `--api-port`, or
`MORI_API_PORT`. It runs as one more concurrent leg on the daemon's shared pool
and store, and shuts down with the rest of the daemon.

## Subscription Observability

Kiroku owns subscription state, lag semantics, metrics, and the operator wire
contract. Mori does not translate or mirror that surface — it just lets you turn
Kiroku's own server on:

```bash
mori automate daemon --metrics-port 9464
```

`MORI_METRICS_PORT=9464` does the same thing; the command-line option wins when
both are set. With neither set, the daemon opens no observability socket at all.

Native endpoints:

| Endpoint | Content |
|----------|---------|
| `/metrics` | JSON metrics snapshot: subscription lag, database errors, stop reasons, dead-letter counts |
| `/metrics/prometheus` | Prometheus text exposition |
| `/health/live` | Kiroku server liveness |
| `/health/ready` | Kiroku dependency readiness detail |
| `/subscriptions` | Live subscription phase and cursor rows |

Kiroku's released operator client speaks the same wire contract:

```bash
kiroku subscriptions status --remote-url http://127.0.0.1:9464
```

> **Exposure.** A nonzero port uses Kiroku's native server, which listens on
> **all interfaces**. Expose it only on a trusted network or behind an
> authenticated proxy. This is a different perimeter from the HTTP API served by
> `--serve`, which is loopback-first.

`mori doctor`, `mori status`, and the HTTP API's own health probes keep their
existing scopes and do **not** report Kiroku subscription status — that is what
this surface is for.

## One Executor Per Database

Before anything else, startup takes a PostgreSQL session advisory lock on a
dedicated, supervised connection. A second daemon — or a `mori automate run` —
pointed at the same database refuses to start:

```text
another mori daemon already holds the automation lock for this database;
refusing to start (advisory lock key 0x6d6f72696461656d)
```

This is deliberate: two executors on one database would run every reaction
twice. Advisory locks are scoped per database and the key is a constant, so the
guard holds even when two processes reach the same database through
differently-spelled connection strings.

The lock connection is never returned to the pool. Closing it releases the lock
on normal exit, exception, cancellation, or process death, so a crashed daemon
does not strand the lock and block the next start. Losing the lock connection
mid-run is treated as a deliberate stop rather than something to paper over; a
merely unreachable database is retried, since the database recovering does not
mean another daemon took ownership.

## How It Works

1. On startup the daemon bootstraps its config registry from the
   `automation_registrations` projection table (populated by
   `mori automate register`).

2. Configs are loaded into a TVar-based ConfigRegistry keyed by RepoId.

3. The daemon subscribes to the `automationRegistration` category for
   live config updates. When repos register, deregister, or update their
   automation configs, the daemon picks up changes automatically —
   fully event-driven with no filesystem polling.

4. A Kiroku reactor on the repository event category receives all repository
   events. For each event the daemon:
   - Extracts the RepoId from the event payload
   - Looks up the matching RepoConfig in the registry
   - Runs the automation matcher against that repo's config
   - Triggers reactions with `workingDir` automatically set to the
     repo's path (so `RunCommand` actions execute in the right directory)

5. The daemon runs several concurrent workers and projections:

| Subscription | Purpose |
|-------------|---------|
| `mori-automation` (daemon mode) | Route events to per-repo configs + app fan-out |
| `mori-reaction-executor` | Execute triggered actions |
| `mori-pending-schedules-projection` | Maintain `mori.pending_scheduled_reactions` for `ReactionScheduled` / terminal events |
| `mori-registry` | Populate registry read model |
| `mori-tech-radar-projection` | Project tech-radar recommendations |
| `mori-agent-plans-projection` | Project agent-plans catalog and dependencies |
| `mori-workflow` | Maintain workflow projections |
| Registration subscription | Update in-memory config registry on register/deregister |
| App registration subscription | Update app registry on app events |

Plus queue processors for deferred work and a periodic **auto-ingest loop**.
The `scheduled_actions` and `scheduled_reactions` pgmq queues run through
keiro-pgmq `Job` definitions, so the queue name, JSON codec, retry policy, and
dead-letter queue are defined in one place and reused by both producers and
workers. Automations with `queued = True` also run through FIFO pgmq jobs:
events for one automation stay ordered while different automations can drain
concurrently. The `webhook_deliveries` queue still uses its bespoke pgmq adapter.

On startup, the daemon ensures the pgmq queues exist. For the keiro-pgmq jobs,
that includes the main queues and their dead-letter queues.

## Auto-Ingest

The daemon periodically ingests git history for every **observed** project —
any project that has been through `mori observe` (i.e., has a `repo_id` in the
projects table). Auto-ingest runs regardless of whether a project has an
automation config, so Mori Apps also receive events from observed repos.

Use `--ingest-interval SECONDS` to control the cycle time, or
`--ingest-interval 0` to disable auto-ingest and rely on manual
`mori automate ingest git` calls instead.

A repo whose ingest keeps failing goes quiet rather than loud — no events, so no
reactions and no webhook deliveries. Failures are classified and recorded in
`mori.repository_ingest_status`; audit them with `mori doctor --ingest` and
recover an orphaned cursor with `mori automate reset-checkpoint`. See [Ingest
Health](/docs/guides/ingest-health).

## Registering with the Daemon

A single `mori automate register` is enough to make a repo receive signals.
The command both registers the automation config with the daemon **and**
emits the `ProjectRepoLinked` event that records the repo in the projects
read model. There is no longer a separate `mori observe` prerequisite.

```bash
# Register current repo's automation config
mori automate register

# Register a different repo (path is authoritative — see below)
mori automate register --path /path/to/repo

# Update after editing config (also heals missing mori.projects rows from
# pre-EP-4 register flows by re-emitting ProjectRepoLinked)
mori automate update

# Register a second, independently named automation in the same repo
mori automate register --name release --config mori.release.dhall

# Remove registration (pass the same --name you registered with)
mori automate deregister
mori automate deregister --name release

# List all registered configs
mori automate list

# One-time migration: discover and register all existing configs
mori automate migrate

# One-time migration: import legacy registrations into the named Automation aggregate
mori automate migrate-named --dry-run
mori automate migrate-named --apply --i-stopped-the-daemon
```

`migrate-named` imports registrations created before automations became
first-class named aggregates. It defaults to `--dry-run`, reporting the changes
it would make and writing nothing. `--apply` additionally requires
`--i-stopped-the-daemon`, which is exactly what it says: the flag is an
acknowledgement, not a switch, and the import rewrites carriers that a running
daemon would be reading concurrently.

`--path <dir>` is authoritative: the config file is read from `<dir>` (so
`--config` resolves relative to it) and the repo TypeID is derived from
`<dir>`. This makes it impossible to silently register repoA's config
against repoB's id by running from the wrong working directory. The same
rule applies to `update`, `deregister`, `run`, and `ingest git`.

Use `mori observe` only when you want a project's identity recorded for
auto-ingest **without** attaching an automation config — it remains
idempotent against an already-registered repo.

### Named automations

An automation is identified by `(repo, name)`. `--name` defaults to `default`,
so a single-config repo needs no extra flag and behaves exactly as it always
did. Naming a second config lets one repository run several independent
automations, each with isolated routing and its own queue group — so a slow or
failing automation cannot hold up a sibling in the same repo.

`deregister` and `update` address the same name, so pass the `--name` you
registered with or you will operate on `default`.

## Prerequisites

- Each repo needs a `mori.dhall` (project identity). If missing,
  `mori automate register` exits with a clear message pointing at
  `mori init`.
- Each repo needs a `mori.automation.dhall` config defining its event
  selectors and reactions.
- Each repo needs a `flake.nix` at the root with a default devShell — see
  [Nix devshell requirement](#nix-devshell-requirement) below.
- Automation config must be registered with `mori automate register`
  (or use `mori automate run --register` for single-repo mode).

## Nix devshell requirement

When the daemon runs under launchd (e.g. via `com.shinzui.mori-automate`),
the inherited `PATH` is minimal — typically `/usr/bin:/bin:/usr/sbin:/sbin`.
That path does not include `~/.nix-profile/bin`, `/nix/store/…`, or any
other directory where a nix-managed binary might live, so spawning `just`,
`bun`, `direnv`, etc. directly would fail with `posix_spawnp: does not exist`.

Mori automatically wraps every `RunCommand` in
`nix develop --command <command> <args…>`, so nix-installed binaries are
found through the **target** repo's devShell rather than through launchd's
PATH. You do not need to wrap commands in `/bin/bash -lc "cd … && …"`.

If a reaction fails with `error: flake … not found` or `error: unable to
find attribute 'default' in devShells`, the target repo is missing a
`flake.nix` with a default devShell. See the [Automation Configuration
concept](/docs/concepts/automation-configuration#nix-devshell-requirement)
for the minimal flake template.

## Comparison with `mori automate run`

| Mode | Description |
|---|---|
| `mori automate run` | Single-repo mode. Reads config from the current directory (or `--config` path). Must be started separately for each repo. Use `--register` to also register with the daemon. |
| `mori automate daemon` | Multi-repo mode. Event-driven discovery of registered automation configs. Manages all repos in one process with live config updates. |

## Signal Handling

The daemon handles `SIGINT` and `SIGTERM` for graceful shutdown with a
TVar-based broadcast for fast drain and shorter timeout.

## Example

```bash
# Register your repos and their automation configs
cd ~/projects/my-app && mori register && mori automate register
cd ~/projects/my-lib && mori register && mori automate register

# Start the daemon (manages both repos)
mori automate daemon
```
