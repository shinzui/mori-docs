Canonical cross-project references use the `mori://` URI scheme. Every artifact
owned by a registered project has one stable identifier you can copy out of the
terminal, embed in a `mori.dhall`, or paste into a commit message.

Twenty-five built-in kinds are addressable, covering every entity mori's schema
extensions contribute — docs, packages, repos, skills, subagents, APIs,
cookbook entries, seihou templates, plans, OKF bundles, checklists, upstream
issues, tech-radar recommendations, and the ten DDD model entities.

```text
mori://<namespace>/<name>/<kind-segment>[/<key>][#<anchor>]
```

Compact input forms are accepted for command-line convenience:

```text
<namespace>/<name>[#<kind-singular>:<key>][#<anchor>]
<namespace>/<name>:<package>
```

The compact form is input-only. Mori always stores and prints the canonical
form.

`mori help mori-refs` prints the authoritative table with each kind's URI
segment, compact token, and Dhall arm, plus a **Reference fragility** section
stating exactly what breaks a ref of each kind.

| DddDurableWorkflow | `ddd/durable-workflows` | `ddd-durable-workflow` |

Four segments do not pluralise: `cookbook` (the artifact is "the cookbook
entry"), `okf` (the format, not a plural noun), `radar` (it matches
`mori tech-radar`), and `glossary` (a mass noun).

The ten [DDD](/docs/guides/ddd) kinds take a **two-segment** path. The bare
segment `mori://<ns>/<name>/ddd` is not a ref and reports an unknown kind —
`ddd` is a namespace within the URI, not a kind of its own. The compact form
needs no second segment, because each DDD token is flat
(`shinzui/mori#ddd-context:registry`).

See [Canonical Refs](/docs/concepts/canonical-refs) for the full table with
Dhall arms, the nested grammars, and the resolution model.

## Kinds that need a second look

**Plans.** For `masterplans/<id>-<slug>` and `plans/<id>-<slug>` (the
[agent-plans extension](/docs/guides/agent-plans)), the trailing key is the
full `<id>-<slug>`, not the slug alone. Plan refs are registry-verified: a plan
resolves only if the owning project publishes it in `mori/agent-plans.dhall`. A
plan file sitting in `docs/plans/` but not listed there is **not** addressable
— publishing is a deliberate act. Expect most of a repository's plan files to
be unaddressable.

**OKF concepts.** The nested `okf/<bundle>/concepts/<segment>` form addresses
one concept inside an [OKF bundle](/docs/guides/okf) — by its stable document
ID (`IR-1`, `ADR-7`) when the bundle's profile declares one, otherwise by its
bundle-relative concept ID. Both forms resolve; the segment may contain `/`.

**Tech-radar.** Mori renders a recommendation fully qualified
(`radar/haskell/database/hasql`), but the one-segment short form
`radar/hasql` is a valid ref and resolves whenever the package is recommended
only once. Recommended under two languages, it reports an ambiguity error
naming both fully-qualified candidates.

**Context mappings.** `ddd/mappings/<upstream>/<downstream>` is an **ordered**
pair. The reversed pair resolves only if the model declares it too.

**Glossary terms.** Stored as prose (`Bounded Context`), addressed by slug
(`bounded-context`).

**Improvement requests.** `originPlan` accepts a canonical, unanchored plan URI.
`targetPlan` also accepts repository-relative `docs/masterplans/<id>-<slug>.md`
or `docs/plans/<id>-<slug>.md`, normalized to the owning project's canonical
URI. The [semantic validator](/docs/guides/improvement-requests) checks
project ownership and exact registration after normalization.

## Nested refs

Three kinds have a nested grammar:

```text
mori://<ns>/<name>/okf/<bundle>/concepts/<segment>
mori://<ns>/<name>/checklists/<key>/steps/<step>
mori://<ns>/<name>/ddd/flows/<key>/steps/<order>
```

A nested sub-key on any other kind is malformed and reports an unsupported-kind
warning. Nested refs always render canonically, because the compact grammar has
no lossless nested representation.

## Where refs work

```bash
mori path mori://shinzui/streamly/packages/streamly-core
mori browse mori://shinzui/streamly
mori registry open-doc mori://shinzui/streamly/docs/effects-cookbook
mori validate --check-refs
```

Refs resolve through the **local** registry only — there is no network fetch.
Register the target project locally before resolving it:

```bash
mori register --path ~/code/streamly
```

In Dhall configs, use `DocLocation.Canonical`:

```dhall
location = Schema.DocLocation.Canonical
  "mori://shinzui/streamly/docs/effects-cookbook"
```

Every kind now has a Dhall arm, so a typed `Schema.MoriRef` can name any of
them:

```dhall
Schema.MoriRef::{
  namespace = "shinzui"
, name = "mori"
, kind = Some Schema.MoriArtifactKind.DddContext
, key = Some "registry"
}
```

The three nested forms are the exception — `MoriRef` has no sub-key field, so
they travel as canonical `Text` in a `DocLocation.Canonical` arm.

## Validating refs

```bash
mori validate --check-refs
```

The check walks the manifest and shipped reference-bearing extensions, including
DDD typed links, plus installed declarative extensions that opt into canonical
reference collection and stored relationship targets. Manifest checks include
text doc locations, typed dependency and standard companions, ownership refs,
and upstream refs. DDD ownership companions must target the declaring project;
mapping endpoints, succession, participant, and flow refs may cross projects.

Missing optional extension files contribute no references. Load failures are
reported; unresolved projects and artifact keys fail the check. An upstream
outside the registry is carried as declared with a warning. Run the dedicated
capability, terminology, and improvement-request validators for their typed
OKF frontmatter semantics.

## Shell completion

Completion walks the URI segment by segment: namespaces, then project names,
then artifact kinds, then keys.

```bash
mori path mori://shinzui/mori/<TAB>      # every kind, owned-first
mori path mori://shinzui/mori/docs/<TAB> # every doc key
mori path shinzui/mori#doc:<TAB>         # same, compact form
```

The `ddd/` prefix is offered once rather than as ten near-identical entries;
committing it lists the ten members.

Kind menus list every completable kind even when a kind has no rows, so you can
complete a ref to a kind you have not populated yet. Key menus list only
existing artifacts.

Two shapes deliberately offer nothing and fall back to the shell's default: a
**nested sub-key** (`…/checklists/<key>/steps/<TAB>`) and a **partially-typed
multi-segment key** (`…/radar/haskell/<TAB>`). A whole multi-segment key is
still offered as a single suggestion, so
`…/ddd/mappings/registry/automation-engine` completes in one press.

Completion requires `MORI_PG_CONNECTION_STRING` in the same shell where you ran
`eval "$(mori completions bash)"`. See [Shell
Completions](/docs/commands/completions).

## Reference fragility

No reference form is unconditionally durable. Mori's job is to make a broken
reference **loud** rather than silent, so each kind fails in a specific,
reported way rather than resolving to the wrong thing.

- **Renaming the key** breaks a doc, package, repo, skill, subagent, api,
  cookbook, template, checklist, upstream-issue, or DDD-entity ref. The key is
  the identity; there is no alias table. Reported as a not-found error.
- **Renaming a plan file** breaks every ref naming it, because the key is
  `<id>-<slug>`. **Unpublishing** a plan from `mori/agent-plans.dhall` also
  stops its ref resolving — publication is the contract.
- **Renumbering a DDD flow step** silently redirects. A step is addressed by
  its declared `order`, so inserting a step earlier and renumbering the rest
  means an existing URI now names a *different* step. This is the one failure
  that is not loud — prefer stable, sparse step numbers.
- **Reordering a context mapping's pair** yields a different ref.
- **Editing a glossary term's prose** changes its slug and breaks the ref.
- **Adding a second radar recommendation for the same package** makes the short
  `radar/<package>` form ambiguous.
- **Removing a bundle's OKF profile** withdraws its document handles, so
  `okf/<bundle>/concepts/<handle>` refs fall back to needing the concept path.
- **Deregistering the owning project** breaks every ref into it, at every kind.

`mori validate --check-refs` is how you find these before your users do.

## HTTP resolution

`GET /v1/refs/resolve?uri=<encoded-mori-uri>` and `POST /v1/refs/resolve`
share the CLI resolver and canonicalizer, including aliases and installed
extension kinds. Success reports portable identity; checkout paths are absent
unless `include_host_context` is requested. Batches retain input order and accept
at most 100 URIs. Host paths are recorded facts with `path_verified: false`, and
fragments are unverified navigation hints. These routes read current registry
observations without refreshing them. See [HTTP reference resolution](/docs/guides/api#portable-reference-resolution).
