title: Running a Shared Registry
description: Publish project knowledge and grant teammates access to a shared registry

---

A shared registry is an ordinary Mori registry that one publisher fills with
`mori registry push` and teammates read with [mori-lite](/docs/guides/lite). It is
headless: nobody registers checkouts on it, runs `mori path` against it, or runs
`mori automate` on it. Its project paths are the publisher's host context, and
[daemon lock](/docs/commands/ops#one-executor-per-database) permits one
automation executor per database, which stays on the workstation.

Every command below was run once against a throwaway database; the outputs are
from that run, with IDs left as they came out and updated only where a later
release changed their shape.

## 1. Provision PostgreSQL

Mori needs PostgreSQL 18 and one database. On the server host:

```bash
createdb mori
```

Mori learns where its database is only from `MORI_PG_CONNECTION_STRING`, for
example `host=/run/postgresql dbname=mori` over a local socket or
`host=db.internal port=5432 dbname=mori user=mori password=…` over the network.
Put it, and every other secret below, in an environment file only the service
user can read.

## 2. Install the server binaries

```bash
nix build github:shinzui/mori#mori -o mori-server
nix build github:shinzui/mori#mori-migrations -o mori-migrations
```

Put `mori-server/bin/mori` and `mori-migrations/bin/mori-migrations` on the
operator's `PATH`, or copy both closures from a workstation with `nix copy`.

## 3. Apply migrations

```bash
$ HASKELL_ENV=production mori-migrations up --database-url "$MORI_PG_CONNECTION_STRING"
…
mori/20261028224857_project_publications outcome=applied_now duration_ms=1

kioku read models: 19 checked, 0 updated
$ mori-migrations verify --database-url "$MORI_PG_CONNECTION_STRING"
verification ok
applied=198
pending=0
unknown=0

projection catalog: candidate group slices are compatible
```

Migrations are idempotent: `up` on a current database applies nothing. Never
apply migration SQL by hand through `psql`; the ledger would not record it and
every later `verify` would fail.

## 4. Check the connection

```bash
$ mori doctor

  Host identity: host_01m62dbgzzet2bg8b26zk1x7dw

  PostgreSQL connection... ✓ OK
```

## 5. Mint the registry identity

Once per database:

```bash
$ mori registry identity mint --name "acme registry"
Registry ID: registry_01m62dbh61em6bf6e21ftnftrn
Display name: acme registry
Minted at: 2026-10-28T23:26:04.481349Z
```

`mori registry identity show` prints the same three lines afterwards. Every
client pins this ID and refuses a server that answers with another.

## 6. Tokens, principals, and grants

The operator token is the server's own bearer token. It can publish and
administer, so it belongs to the publisher alone:

```bash
openssl rand -hex 32   # store as MORI_API_TOKEN in the server's environment file
```

Each teammate is a principal with grants and a personal token. With
`MORI_PG_CONNECTION_STRING` pointing at the shared database:

```bash
$ mori registry access principal create --label alice
Principal: principal_01m62dc1g2emzvpv1m8avjqngp
Label: alice
Status: active
$ mori registry access grant --principal principal_01m62dc1g2emzvpv1m8avjqngp --namespace acme --permission read
Granted read on namespace acme to principal_01m62dc1g2emzvpv1m8avjqngp
$ mori registry access token mint --principal principal_01m62dc1g2emzvpv1m8avjqngp --label laptop
Token (store it now; it is not shown again): morit_…
Credential: cred_01m62dctkkendsnq5n4kperbvq
```

Hand the token to the teammate over a channel you trust; it is shown once. A
principal with no grants syncs an empty catalog, which is the intended default.
See `mori help registry-access` for project and registry grants and `publish`.

## 7. Start the server under a supervisor

`mori serve` binds `127.0.0.1` by default and refuses any other address unless
`MORI_API_TOKEN` is set ([API security perimeter](/docs/guides/api#security-perimeter)).
Never use `--insecure-no-auth` on a shared server. Behind the proxy in step 8 it
stays on loopback. On start it checks the store, registers its projection
catalog, and logs:

```text
mori-api listening on http://127.0.0.1:8080 (application endpoints under /v1; probes under /health); auth: bearer token; cors origins: 0
```

A `systemd` unit:

```text
[Unit]
Description=Mori shared registry
After=postgresql.service

[Service]
User=mori
EnvironmentFile=/etc/mori/registry.env
ExecStart=/usr/local/bin/mori serve --host 127.0.0.1 --port 8080
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Or `process-compose`, which the dev shell already ships:

```yaml
version: "0.5"
processes:
  mori-registry:
    command: mori serve --host 127.0.0.1 --port 8080
    env_file: /etc/mori/registry.env
    availability:
      restart: on_failure
    readiness_probe:
      http_get:
        host: 127.0.0.1
        port: 8080
        path: /health/ready
```

`/etc/mori/registry.env` holds `MORI_PG_CONNECTION_STRING` and `MORI_API_TOKEN`
and is readable only by the service user.

## 8. Put TLS in front

`mori serve` speaks plain HTTP. Terminate TLS in a reverse proxy; Caddy
provisions its own certificate:

```text
registry.acme.internal {
  reverse_proxy 127.0.0.1:8080
}
```

## Shomei publishers

On a server configured with `MORI_AUTH_MODE=shomei`, set
`MORI_SHOMEI_ISSUER` and `MORI_SHOMEI_AUDIENCE` to the trusted identity deployment
(`mori://shinzui/shomei`). The issuer supplies access tokens through its public
HTTP endpoints; Mori verifies signature, issuer, audience, expiry, and token type.
An ID token cannot authenticate to Mori. Existing personal tokens continue to work
until explicitly revoked.

Create a service account through your Shomei operator, store its one-time secret in
protected operator environment storage, and obtain its exact backing-user subject
from that deployment. Bind that identity to an existing Mori principal on the
receiving registry, then grant only the namespace or project it may publish:

```bash
mori registry access principal bind "$PRINCIPAL" --issuer "$ISSUER" --subject "$SUBJECT"
mori registry access grant --principal "$PRINCIPAL" --namespace acme --permission publish
```

On the workstation, load these settings from protected environment storage:

```bash
export MORI_PUSH_AUTH_MODE=shomei
export MORI_PUSH_SHOMEI_ISSUER=https://identity.acme.internal
export MORI_PUSH_SHOMEI_CLIENT_ID=svcacct_example
export MORI_PUSH_SHOMEI_CLIENT_SECRET="<load from protected storage>"
export MORI_PUSH_SHOMEI_SCOPE=mori:publish
unset MORI_PUSH_TOKEN
mori registry push --url https://registry.acme.internal --all
```

The optional scope must be allowed by that service account; it does not grant a
Mori permission. Tokens are short-lived and refresh-less: the publisher obtains
another as needed. Failed issuance stops publication. Mixed mode settings are
refused. Neither the secret nor token belongs in `mori.dhall`, a snapshot, or a
command argument. Revoke or rotate the service credential in Shomei to stop new
issuance; an issued stateless token remains valid until expiry, while retiring
its bound Mori principal prevents its use immediately.

Publication history retains the workstation registry ID separately from the API
actor's verified issuer, exact subject, and stable principal. A publisher registry
ID alone grants no authority. Delegated tokens are currently refused.

## Prepare En grants

`mori registry access export-en --json` copies granted Phase 1 rows and their
resource-parent layout to a standalone En deployment (`mori://shinzui/en`). It
preserves principal and registry-qualified resource IDs and leaves the current
decision source in place. Repeated exports skip existing tuples without advancing
En's generation. A rejected grant or conflicting parent is named in the report and
exits nonzero.

The En deployment must load the model at `mori-api/access/registry.en` in
`mori://shinzui/mori` (artifact-level URI pending). Load its base URL, separate
read-only/write-capable credentials, schema hash, and datastore ID from protected
operator environment storage as `MORI_EN_BASE_URL`, `MORI_EN_READ_TOKEN`,
`MORI_EN_WRITE_TOKEN`, `MORI_EN_SCHEMA_HASH`, and `MORI_EN_DATASTORE_ID`. The owner
reports its hash and datastore ID at startup; Mori verifies the public model and
consistency evidence against those values. `MORI_EN_TIMEOUT_MILLIS` defaults to
5000 and may be at most 30000. En must permit its public relationship-query route
for read-only keys. Use a deployment containing the query-classification fix
described by `mori://shinzui/mori/okf/friction-log/concepts/FRIC-21`.

## The first push

From the workstation, with the workstation's own `MORI_PG_CONNECTION_STRING`
and the operator token:

```bash
$ export MORI_PUSH_TOKEN="<operator token>"
$ mori registry push --url https://registry.acme.internal --all
Target: acme registry (registry_01m62dbh61em6bf6e21ftnftrn) at https://registry.acme.internal
acme/legacy: refused (own/fork project has no stable ID; run mori identity mint --write in /Users/publisher/src/legacy, mori register, then push again)
acme/widgets: created
vendor/left-pad: created
2 pushed, 0 pruned, 0 skipped, 1 refused, 0 failed
```

The command exits 1 because something was refused. The refusal is the stable-ID
rule: an own or fork project must carry a stable ID before it leaves the
workstation. `--all` is safe to re-run; an unchanged project appends nothing:

```bash
$ mori registry push --url https://registry.acme.internal --all
…
acme/widgets: unchanged
vendor/left-pad: unchanged
```

Now that projects exist, prove a grant before a teammate tries:

```bash
$ mori registry access check --principal principal_01m62dc1g2emzvpv1m8avjqngp --project acme/widgets --permission read
allowed
$ mori registry access check --principal principal_01m62dc1g2emzvpv1m8avjqngp --project vendor/left-pad --permission read
denied
```

See `mori help registry-push` for `--prune` and the outcomes.

## Hosting checklist for the publisher

Every project the catalog lists must be cloneable by the team: each needs at
least one `repos` entry with `github`, `gitlab`, or `git` pointing at a host
every teammate can reach. Curated third-party projects are the usual gap. Their
manifests live in wrapper repositories in the publisher's private hub, and the
wrapper, not the upstream, carries the curated docs, so the wrapper itself has
to be pushed to the team's git host and its `repos` entry pointed there.

The check is `mori-lite doctor`, run by the publisher with the operator token,
which sees the whole catalog. After every `--all` push:

```bash
$ export MORI_LITE_TOKEN="<operator token>"
$ mori-lite setup --url https://registry.acme.internal
Connected to acme registry (registry_01m62dbh61em6bf6e21ftnftrn) at https://registry.acme.internal as the operator
$ mori-lite sync
Synced 2 projects in 1 pages from acme registry (full replacement)
$ mori-lite doctor
Registry: registry_01m62dbh61em6bf6e21ftnftrn
Principal: the operator (scope operator)
Protocol: v2, schema v1
Grant generation: 4
Catalog database: /Users/publisher/.cache/mori-lite/catalog/registry_01m62dbh61em6bf6e21ftnftrn/operator/v2.sqlite
Last sync: 2026-10-28T23:31:27.971143Z
Projects: 2
Cached projects with no github, gitlab, or git repository:
  vendor/left-pad
```

`doctor` exits 1 while the list is non-empty; `--json` gives the same report for
scripts. Treat every listed project as work to do before telling a teammate it
exists. Nothing else should open the client's SQLite files; their layout is the
client's to change.

## 10. Back up

Archive every category `mori store lifecycle inventory` lists, verify each
archive, and keep a plain `pg_dump` beside them:

```bash
$ mori store lifecycle archive --category principal --output /var/backups/mori/2026-10-28/principal
Events: 4
Segments: 1
Digest: sha256:e2593a1744a0894e7d8d16b9f3232bd9948580d2f82b89d2c33aee0a9b1ba7d2
$ mori store lifecycle verify-archive /var/backups/mori/2026-10-28/principal/manifest.json
Events: 4
Segments: 1
Digest: sha256:e2593a1744a0894e7d8d16b9f3232bd9948580d2f82b89d2c33aee0a9b1ba7d2
```

A shared registry holds at least `projectRoot`, `projectArtifactV2`,
`principal`, and `accessGrant`. The archives are the replay-grade record of the
event store; the `pg_dump` is the fast restore path for the whole database,
read models included. Prune the previous day's backup only after
`verify-archive` passes on the new one.

## 11. Rotate tokens

- Operator token: change `MORI_API_TOKEN` in the environment file and restart
  the service; update the publisher's `MORI_PUSH_TOKEN`. A leaked operator token
  can publish and administer, so rotate it immediately.
- A teammate's token: `mori registry access token revoke <cred_id>`, then
  `token mint` again. No restart is needed. A leaked personal token exposes only
  that principal's catalog until revoked.
- A departing teammate: `mori registry access revoke` their grants, or retire
  the principal, which revokes everything at once.

## 12. Upgrade

Pull the new closures, run `mori-migrations up` and `verify` again, and restart.
A binary that adds a projection owner changes a catalog slice; run
`mori ops rebuild adopt project_models --force` on an existing registry when
`verify` reports the slice as changed. The release replay gate normally runs on
the workstation before a release is tagged and is not repeated on the server.
A release that waives it says so in its release notes, as 7.2.0.0 does; rehearse
such an upgrade on a restored clone before applying it to a registry holding
real history.

## The same-machine layout

The shared registry may also be a second database in the workstation's own
PostgreSQL, which is how the publisher rehearses this runbook: `createdb
mori_shared`, migrate it with its own connection string, mint its own identity,
and serve it under the supervisor with an environment file naming that database,
on a port your own tooling does not use, behind the proxy. Your shell keeps the
workstation's connection string, so `mori registry push` moves projects from one
database into the other over HTTP and never reads the shared database directly.

Three consequences. The shared registry is up only while the workstation is;
mori-lite tolerates that because every read command works from its cache. The
shared registry stays headless. And `mori registry access …` must run against the
shared database, so keep a wrapper to make a grant impossible to misdirect:

```bash
alias mori-shared='MORI_PG_CONNECTION_STRING="host=$HOME/path/to/db dbname=mori_shared" mori'
```

## Select En and administer permissions

After exporting and reconciling Phase 1 grants, run the normal database migration
runner and start the registry with `MORI_ACCESS_MODE=en` plus the protected
`MORI_EN_*` settings above. Read and write owner keys must be different. Local
mode remains the default and refuses ambiguous En server settings. Do not repeat
the historical export after cutover; the CLI refuses `export-en` in En mode.

Project decisions are materialized into an indexed visible set before catalog
paging. Missing or stale state returns 503. Watch changes close affected scopes
and refresh them; unrelated principals keep their generation when their visible
set did not change. `MORI_EN_MAX_STALENESS_SECONDS` defaults to 30, with a maximum
of 300. External owner writes propagate through the watch within that freshness
boundary. An owner outage never reactivates local grants.

Permission administrators set `MORI_ACCESS_MODE=en` and `MORI_ACCESS_URL` in the
workstation CLI. Authenticate with `MORI_PUSH_TOKEN`, or the explicit Shomei
service-account `MORI_PUSH_*` settings used for publication. Run the same
`mori registry access grant|revoke|list|check` commands. The server checks live
administer permission on the target before using its separate En write key.
Whole-registry grant listings require registry administration. `--group GROUP_ID`
can replace `--principal` for grant/revoke; group membership stays in En.
Grant/revoke JSON returns owner consistency evidence and a null local grant ID.

Bootstrap registry administration through En's public relationship API using the
object `registry:<receiving registry ID>`, relation `administrator`, and a direct
`principal` subject whose ID is the existing Mori principal ID. The trusted Mori
operator credential remains available for administration. Identity bindings and
personal-token lifecycle remain Mori-owned in both decision modes.

A new project or namespace move stays hidden until its parent relationships are
verified. If a publication commits before the owner write fails, retrying or
restarting the server resumes its persisted admission with the same resource ID.
Retirement closes visibility before cleanup and retains an identity tombstone.
A genuinely new project with the same name needs a new identity.

## Bounded catalog snapshots

New Lite clients require protocol 2. Discovery advertises `[1,2]` by default;
existing V1 clients continue to work during migration. After upgrading clients,
set `MORI_CATALOG_MODE=v2-only` on the registry to advertise only 2 and refuse
`/v1/catalog` bulk downloads with `426 catalog_upgrade_required` before content.
Project DTOs, personal tokens, Shomei identities and Mori references retain their
existing contracts.

A sync captures a coherent, immutable visible snapshot in a short read-only
transaction; no transaction stays open while a laptop downloads. Continuations
and completion revalidate the caller, current access evidence and membership.
A permission change or namespace move can return `409 access_scope_changed`;
start a fresh sync. Expired/completed cursors return `409 sync_session_expired`.
Regrant cannot revive a revoked session. Another principal's unrelated direct
grant preserves this principal's session.

The following protected server settings bound capture and retention:

| Variable | Default | Accepted range |
| --- | ---: | ---: |
| `MORI_SYNC_MAX_PROJECTS` | 20000 | 1–100000 |
| `MORI_SYNC_MAX_BYTES` | 67108864 | 1024–268435456 |
| `MORI_SYNC_CAPTURE_MILLIS` | 30000 | 1–120000 |
| `MORI_SYNC_SESSION_SECONDS` | 300 | 1–3600 |
| `MORI_SYNC_MAX_CONCURRENT` | 8 | 1–32 |
| `MORI_SYNC_MAX_PER_SCOPE` | 2 | 1–8 |
| `MORI_SYNC_MAX_STORED` | 128 | 1–2048 |

Exceeded capacity returns `503 catalog_sync_capacity` before a partial snapshot
can activate. Retry after capacity or expiry clears, or adjust the operator limit.
Startup closes old sessions; completed sessions discard payloads, and expired
sessions are removed when new sessions are reserved. Apply the catalog-session
migration through the normal migration runner. The client keeps checkout bindings
outside the disposable catalog and blocks it after a known authorization refusal;
ordinary outages preserve the last authorized export for explicit offline reads.
