The `ddd` extension lets a project record its Domain-Driven Design model in
`mori/ddd.dhall`: subdomains, bounded contexts, aggregates, context mappings,
message flows, ubiquitous-language glossary terms, and optional review metadata.

Every modeling concern is optional and empty by default. A glossary-only model,
a strategic-design-only model, a tactical-design-only model, and an empty
`Ddd.DddModel::{=}` are all valid.

## When to use it

Use the DDD extension when a project needs a shared model of its domain:

- Ubiquitous language: agreed terms and aliases.
- Strategic design: subdomains, bounded contexts, and context mappings.
- Tactical design: aggregates, commands, emitted events, and invariants.
- Cross-context interactions: ordered message flows.
- Model health: review date, coverage percentage, notes, and collaborators.

## Getting started

The schema-aware bootstrap command launches an agent session with the pinned
schema, your current `mori/ddd.dhall`, and the validate/register workflow:

```bash
mori agent bootstrap-ddd
```

If the file is pinned to a different schema commit than the binary, migrate it
first:

```bash
mori schema migrate --apply --file mori/ddd.dhall
```

You can inspect the pinned DDD schema at any time:

```bash
mori ddd print-schema
```

## Configuration

Create `mori/ddd.dhall` in the project directory. The extension follows the
same `{ Input, Type, default, mk }` bundle convention as the core schema, so the
`::` record-completion form supplies omitted defaults.

```dhall
let Ddd = ../schema/extensions/ddd/package.dhall

in  Ddd.DddModel::{
    , domain = Some "Logistics"
    , subdomains =
      [ Ddd.Subdomain::{
        , key = "ordering"
        , name = "Ordering"
        , kind = Ddd.SubdomainKind.Core
        , evolution = Some Ddd.WardleyStage.Product
        }
      ]
    , contexts =
      [ Ddd.BoundedContext::{
        , key = "checkout"
        , name = "Checkout"
        , purpose = Some "Turn a cart into a confirmed order."
        , subdomain = Some "ordering"
        }
      ]
    , aggregates =
      [ Ddd.Aggregate::{
        , key = "order"
        , name = "Order"
        , context = Some "checkout"
        , commands = [ "PlaceOrder", "CancelOrder" ]
        , events = [ "OrderPlaced", "OrderCancelled" ]
        , invariants = [ "an order has at least one line item" ]
        , size = Some Ddd.AggregateSize.Medium
        , throughputPerDay = Some 1200
        }
      ]
    , mappings =
      [ Ddd.ContextMapping::{
        , upstream = "checkout"
        , downstream = "fulfillment"
        , pattern = Ddd.RelationshipPattern.PublishedLanguage
        , teamRelationship = Some Ddd.TeamRelationship.UpstreamDownstream
        }
      ]
    , flows =
      [ Ddd.MessageFlow::{
        , key = "place-order"
        , name = "Place an order"
        , steps =
          [ Ddd.FlowStep::{
            , order = 1
            , message = "PlaceOrder"
            , kind = Ddd.MessageKind.Command
            , from = "customer"
            , to = "checkout"
            }
          ]
        }
      ]
    , glossary =
      [ Ddd.GlossaryTerm::{
        , term = "Order"
        , definition = "A customer's request to purchase one or more items."
        , aliases = [ "purchase" ]
        }
      ]
    }
```

Projects outside the mori repository should use the pinned URL import printed by
`mori ddd print-schema` or prepared by `mori agent bootstrap-ddd`.

## Schema reference

| Field | Type | Meaning |
|-------|------|---------|
| `domain` | `Optional Text` | Overall domain name |
| `subdomains` | `List Subdomain` | Business areas |
| `contexts` | `List BoundedContext` | Model-consistency boundaries |
| `aggregates` | `List Aggregate` | Tactical consistency clusters |
| `mappings` | `List ContextMapping` | Relationships between contexts |
| `flows` | `List MessageFlow` | Ordered cross-context scenarios |
| `glossary` | `List GlossaryTerm` | Ubiquitous-language terms |
| `verification` | `Optional Verification` | Review and coverage metrics |
| `collaborators` | `List Collaborator` | Teams or people and their contexts |
| `reactors` | `List Reactor` | Stateless, idempotent event reactions |
| `processManagers` | `List ProcessManager` | Correlated coordinators owning durable state |
| `durableWorkflows` | `List DurableWorkflow` | Versioned, journal-resumed workflows |

Important nested records:

- `Subdomain`: `key`, `name`, `kind`, optional `description`, optional `evolution`.
- `BoundedContext`: `key`, `name`, optional `purpose`, optional `subdomain`, optional `subdomainRef`, optional `status`, `supersedes`, `supersedesRefs`.
- `Aggregate`: `key`, `name`, optional `context`, optional `description`, `commands`, `events`, `invariants`, optional `size`, optional `throughputPerDay`.
- `ContextMapping`: `upstream`, optional `upstreamRef`, `downstream`, optional `downstreamRef`, `pattern`, optional `teamRelationship`, optional `notes`.
- `MessageFlow`: `key`, `name`, optional `description`, ordered `steps`.
- `GlossaryTerm`: `term`, `definition`, optional `context`, `aliases`, `replaces`.
- `Collaborator`: `key`, `name`, optional `role`, `contexts`.
- `Verification`: optional `lastReviewed`, optional `coveragePercent`, optional `notes`.

The main unions are `SubdomainKind`, `RelationshipPattern`,
`TeamRelationship`, `MessageKind`, `WardleyStage`, `AggregateSize`, and
`ContextStatus` (`Active` | `Emerging` | `Deprecated` | `Sunset`).
`RelationshipPattern` includes an `Other : Text` arm for project-specific
patterns.

Every `*Ref` field above is an optional typed `MoriRef` companion to a bare text
key. The bare key stays authoritative and the companion carries the exact
identity; when both are present they must agree, or validation fails.

Which companion may cross a project boundary is **not** uniform, and the split
is deliberate:

| Companion | May target another project? |
|-----------|------------------------------|
| `subdomainRef`, aggregate `contextRef` | **No** — ownership and membership describe one model's internal structure |
| `supersedesRefs`, `upstreamRef`, `downstreamRef` | **Yes** — succession and strategic mapping describe fleet-wide evolution and collaboration |
| coordination `participantRefs`, `flowRefs` | Yes |
| coordination owner `contextRef` | No — the owning context is local |
| `implementationRef` | Any built-in artifact kind — runtime evidence can be a package, doc, or other registered fact |

Two rules catch most authoring mistakes:

- A `supersedesRefs` entry must be of kind `DddContext`, **and** its key must
  also appear in the plain `supersedes` list. A typed companion whose key is
  missing from the list is rejected by name.
- A plain `supersedes` key with no local target stays valid — the superseded
  context may legitimately live outside this document.

See `mori help ddd` for the complete key →
companion table and the kind each companion accepts.

### Lifecycle and succession

A bounded context can record where it sits in a migration rather than just
existing. `status` defaults to `Active` when absent, so models written before
lifecycle support keep loading unchanged.

```dhall
, contexts =
  [ Ddd.BoundedContext::{
    , key        = "checkout"
    , name       = "Checkout"
    , status     = Some Ddd.ContextStatus.Emerging
    , supersedes = [ "legacy-checkout" ]
    }
  ]
```

`GlossaryTerm.replaces` does the same for vocabulary — the older terms a term
supersedes — and `mori ddd search --term` matches against replaced terms as
well as the term and its aliases.

### Coordination mechanisms

Three record kinds describe *runtime-neutral* coordination. Choose from
behaviour and correctness ownership, never from an implementation type name:

1. **`Reactor`** — an event-triggered, stateless, idempotent reaction. Owns no
   per-instance durable state and no deadline. Required beyond the common
   fields: `trigger`, `actions`, `idempotencyStrategy`. Carries
   `ownsDurableState` and `ownsTimers`, both of which **must be `False`**.
2. **`ProcessManager`** — one correlated instance owns durable state, reacts to
   events by issuing commands, and may own timers, retries, dead-letter policy,
   and operator repair. Required: `durableState`, `correlationKeys`,
   `correlationRule`, `transactionBoundary`, `idempotencyStrategy`,
   `retryPolicy`, `deadLetterPolicy`, `repairProcedure`, `replayEvidence`.
   "Saga" is a contextual synonym for this pattern, not a fourth kind.
3. **`DurableWorkflow`** — a versioned definition resumes an imperative
   continuation from a journal. Required: `definitionId`, `definitionVersion`,
   `journal`, `steps`, `terminalPolicy`, `versioningPolicy`, `replayEvidence`,
   `recoveryProcedure`; optional `externalWaits`, `timers`, `wakeSources`,
   `progressMechanisms`.

All three share a common head: `key`, `name`, `context`, optional `contextRef`,
optional `description`, `consumes`/`emits`, `participants`/`participantRefs`,
optional `implementation`/`implementationRef`, `flows`/`flowRefs`, and optional
`status`.

Supporting records: `CoordinationMessage` (`message`, `kind`),
`CoordinationTimer` (`key`, `name`, optional `description`, `deadline`,
`emits`), `WorkflowJournal` (`name`, `persistence`, optional `retention`),
`DurableWorkflowStep` (`key`, `name`, optional `description`,
`idempotencyStrategy`), and `WorkflowExternalWait` (`key`, `name`, optional
`description`, `callbackIdentity`, `wakeSource`).

A `MessageFlow` remains an ordered explanatory narrative — it does not become a
coordinator merely because it has several participants. Equally, a runtime class
named "Workflow" is not necessarily a `DurableWorkflow`.

Validation enforces the ladder, not just the shape: a reactor's `trigger` must
be an `Event` and must also appear in `consumes`, its `actions` must be
non-empty, and it may not set `ownsDurableState` or `ownsTimers`. Timer keys,
step keys, and external-wait keys must each be unique within their owner.

## Browse locally

Local browse commands read `mori/ddd.dhall` directly and do not require a
registry database.

```bash
mori ddd subdomains
mori ddd subdomains --kind core
mori ddd contexts
mori ddd contexts --subdomain ordering
mori ddd aggregates
mori ddd aggregates --context checkout
mori ddd mappings
mori ddd mappings --pattern published-language
mori ddd flows
mori ddd flows place-order
mori ddd glossary
mori ddd glossary order
mori ddd glossary --context checkout
mori ddd collaborators
mori ddd collaborators --context checkout
mori ddd verification
mori ddd coordination
```

`mori ddd contexts --status deprecated` filters by lifecycle status.

Filters are case-insensitive. Pattern and kind filters also ignore hyphens and
underscores, so `anticorruption-layer` matches `AnticorruptionLayer`.

### Inspecting coordination

`mori ddd coordination` is one typed view over all three coordination kinds. In
local mode it reads `mori/ddd.dhall` (or `--config PATH`); `--registry`,
`--project`, or `--group` switch it to the registry. The filters compose:

```bash
mori ddd coordination --kind reactor          # reactor | process-manager | durable-workflow
mori ddd coordination --context checkout      # owning context key or canonical ref
mori ddd coordination --participant payments  # participant context
mori ddd coordination --status active         # active | emerging | deprecated | sunset
mori ddd coordination --has-timers            # owns at least one timer
mori ddd coordination --has-durable-state     # owns durable coordination state
mori ddd coordination --message PaymentAuthorized --message-kind event \
                      --direction consumes    # consumes | emits | either (default)
mori ddd coordination --json                  # deterministic snake_case JSON
```

### Canonical identities

Every coordination mechanism is a first-class project artifact with its own
`mori://` identity, its own event history, and its own relational row — not a
nested field inside the model's JSON:

```text
mori://acme/orders/ddd/reactors/reserve-inventory
mori://acme/orders/ddd/process-managers/order-fulfillment
mori://acme/orders/ddd/durable-workflows/refund-compensation
```

The typed reference kinds are `DddReactor`, `DddProcessManager`, and
`DddDurableWorkflow`, so these targets participate in
`mori validate --check-refs` alongside every other kind.

These declarations have **no file of their own**. `mori path` reports the
owning project plus name, context, lifecycle, timers, and durable-state
summary, then returns the project root rather than inventing an artifact path:

```bash
mori path mori://acme/orders/ddd/process-managers/order-fulfillment
```

### JSON contract

`mori ddd coordination --json` emits a stable version-1 document:

| Key | Contents |
|-----|----------|
| `version` | Contract version, currently `1` |
| `filters` | Every predicate echoed back, `null` when unset |
| `scope` | `mode` (`local` or `registry`), `projects`, `group` |
| `results` | One object per matching mechanism |

Each result carries the common fields — `kind`, `key`, `name`, `context`,
`context_ref`, `description`, `consumes`, `emits`, `participants`,
`participant_refs`, `implementation`, `implementation_ref`, `flows`,
`flow_refs`, `status`, `has_timers`, `has_durable_state`, `canonical_ref` —
plus a kind-specific `details` object.

`consumes` and `emits` are arrays of `{ message, kind }` objects. That is what
makes `--message` and `--message-kind` an **exact pair** match rather than two
independent predicates: a declaration that consumes `PaymentAuthorized` as an
`Event` does not satisfy `--message PaymentAuthorized --message-kind command`
just because some other message elsewhere is a command.

All predicates are ANDed. `--has-timers` and `--has-durable-state` constrain to
true; omitting them applies no boolean constraint. An empty match is
**successful** and renders an empty `results` list. Local `--config` cannot be
combined with a registry scope, and `--group` cannot be combined with
`--project`.

## Cross-project search

Registration stores the model in the generic extension JSONB store, and an
**inline** projection fans it out into twelve normalized `mori.ddd_*` tables —
`ddd_models`, `ddd_subdomains`, `ddd_contexts`, `ddd_aggregates`,
`ddd_context_mappings`, `ddd_flows`, `ddd_flow_steps`, `ddd_glossary`,
`ddd_collaborators`, `ddd_reactors`, `ddd_process_managers`, and
`ddd_durable_workflows` — in the same transaction — so `mori ddd search` can answer relational questions
across every registered project as soon as `mori register` returns. No daemon is
involved.

```bash
mori ddd search --pattern published-language
mori ddd search --emits OrderPlaced
mori ddd search --context checkout
mori ddd search --term invoice
mori ddd search --status deprecated                     # contexts by lifecycle status
mori ddd search --project acme/billing
mori ddd search --project acme/billing --project acme/orders
mori ddd search --group commerce
mori ddd search --json
```

Repeat `--project` to widen the scope; `--group` selects one named registry
group and cannot be combined with `--project`. `--term` matches a term, its
aliases, **and** the older terms it replaces.

Use `mori extension query ddd` when you want one project's stored model from
the generic extension table. Use `mori ddd search` when you want relational
queries across the registry.

### Rendering a context map

`mori ddd map` renders the bounded contexts and context mappings from the same
registry scopes as a diagram — Mermaid by default, with DOT and JSON for other
tools:

```bash
mori ddd map --group commerce
mori ddd map --project acme/orders --project acme/payments --format dot
mori ddd map --group commerce --format json
```

Superseded contexts are drawn as a dashed edge from the successor back to its
predecessor, so a migration in progress reads as a migration rather than as two
unrelated contexts. Lifecycle status also controls node styling.

Contexts are grouped first by project and then by subdomain. Their canonical
`mori://…/ddd/contexts/…` refs are the graph identities, so equal context keys
in different projects stay distinct.

A typed mapping endpoint resolves exactly. An endpoint outside the selected
scope, a missing key, or an **ambiguous** untyped key stays visible as an
external node — mori never guesses which context was meant and never drops the
mapping assertion.

All three formats encode the same node and edge set, and repeated runs are
byte-identical, so the output is safe to commit and diff.

#### JSON contract

Snake_case throughout:

| Key | Fields |
|-----|--------|
| `scope` | `kind` — `all`, `projects`, or `group` |
| `projects` | `canonical_ref`, `namespace`, `name`, `subdomains` |
| `nodes` | `id`, `canonical_ref`, `key`, `name`, `project`, `subdomain`, `status`, `external` |
| `edges` | `kind`, `source`, `target`, `label`, `declaring_project` |

`edges.kind` is `mapping` or `supersession`. For a resolved context, `nodes.id`
is its canonical context URI. External nodes come in two shapes:

- **typed** — the endpoint named a canonical ref outside the selected scope;
  `id` and `canonical_ref` are both that URI.
- **plain** — the endpoint named a key that matched no in-scope context, or
  matched more than one; `id` is `external:ddd-context-key:<key>` and
  `canonical_ref` is `null`.

Either way `external` is `true` and `project`, `subdomain`, and `status` are
`null`. Key on `external` rather than on the shape of `id`.

The database-backed subcommands are `mori ddd search`, `mori ddd map`, and
`mori ddd coordination` in registry mode. Everything else reads
`mori/ddd.dhall` directly and needs no database.

## Maintenance

Existing mk-form DDD files keep loading when new optional fields are added
because the bundle default supplies the missing fields. To normalize an older
file, run:

```bash
mori schema migrate --apply --file mori/ddd.dhall
```

To sweep registered projects, use:

```bash
mori registry upgrade-schema
```
