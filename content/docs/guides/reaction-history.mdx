View and inspect automation reaction execution history. Reactions are
triggered when VCS events match selectors defined in your automation
config (`mori.automation.dhall`). Scheduled reactions extend the
lifecycle with `scheduled`, `skipped`, and `cancelled` states — this
guide covers both immediate and scheduled reactions.

## Commands

| Command | Description |
|---|---|
| `mori reaction list` | List recent reactions |
| `mori reaction show` | Show full details for a single reaction |
| `mori reaction cancel` | Cancel a pending scheduled reaction |
| `mori reaction scheduled list` | List pending scheduled reactions |
| `mori reaction scheduled show` | Show details of one pending scheduled reaction |
| `mori reaction recover` | Unstick a reaction stuck in `status=triggered` |

## List

```bash
mori reaction list [--limit N] [--status STATUS] [--name NAME]
```

Shows a table of recent reactions with their status, name, triggering event
type, duration, and start time.

### Options

| Option | Description | Default |
|---|---|---|
| `-n, --limit N` | Maximum rows to show | `20` |
| `--status STATUS` | Filter by status: `triggered`, `completed`, `failed`, `scheduled`, `skipped`, `cancelled` | — |
| `--name NAME` | Filter by reaction name | — |

### Examples

```bash
mori reaction list                       # Show last 20 reactions
mori reaction list -n 50                 # Show last 50 reactions
mori reaction list --status failed       # Show only failed reactions
mori reaction list --status scheduled    # Show only pending scheduled reactions
mori reaction list --name sync-registry  # Show reactions for sync-registry
```

`--status` and `--name` can be combined.

## Show

```bash
mori reaction show <REACTION_ID>
```

Displays full details for a single reaction, including the triggering stream,
position, timestamps, duration, and error message (if failed). For failed
`RunCommand` actions, `show` also prints the command's captured stdout and
stderr in dedicated `Stdout:` and `Stderr:` blocks (persisted on
`mori.reaction_history` per action result; non-command actions like `Notify`,
`EmitEvent`, `Schedule`, and `Signal` leave both blocks empty).

For scheduled reactions, `show` also prints `scheduled_at`, `run_at`, the
coalesce key, and the queue message id. For skipped reactions, it prints
the idempotency check's exit code and stderr. For cancelled reactions, it
prints the cancellation reason.

The reaction ID is a TypeID starting with `rxn_` — copy it from the ID
column of `mori reaction list`.

### Example

```bash
mori reaction list                  # Find the reaction ID
mori reaction show rxn_01hy3x...   # Show full details
```

## Scheduled List

```bash
mori reaction scheduled list
mori reaction scheduled list --repo prj_01HZ...
mori reaction scheduled list --automation mori.automation
mori reaction scheduled list --json
```

Lists scheduled reactions currently waiting on the `scheduled_reactions`
pgmq queue. The view is backed by the `mori.pending_scheduled_reactions`
projection and shows the `run_at` target, coalesce key (if any), and
automation name for each pending reaction.

### Options

| Option | Description |
|---|---|
| `--repo REPO_ID` | Filter to a single repository (repo TypeID) |
| `--automation NAME` | Filter by automation name (the basename of the config file, e.g. `mori.automation`) |
| `--json` | Emit JSON instead of a table |

## Scheduled Show

```bash
mori reaction scheduled show <REACTION_ID>
mori reaction scheduled show <REACTION_ID> --json
```

Shows full details for a single pending scheduled reaction. Joins the
pending row, the `reaction_history` row, and the `ReactionScheduled` event
so the idempotency check (command, args, timeout, `skipOnExit`) is
surfaced.

## Cancel

```bash
mori reaction cancel <REACTION_ID> [--reason TEXT]
```

Cancels a pending scheduled reaction. Looks up the pgmq `msg_id` from the
pending projection, deletes the queue message, then emits
`ReactionCancelled`. The projection sees the event on its next poll and
removes the row from `mori.pending_scheduled_reactions`.

### Options

| Option | Description |
|---|---|
| `--reason TEXT` | Free-form reason recorded on the `ReactionCancelled` event (default: `cancelled by user`) |

> **Race-condition note.** If the worker pops the message just before
> `cancel` runs, the pgmq delete returns "already consumed" and the
> command prints a warning but still emits `ReactionCancelled`. The
> decider makes subsequent `CompleteReaction` and `FailReaction`
> transitions from the cancelled state into no-ops, so the cancellation
> is harmless if the reaction completed first.

## Recover

```bash
mori reaction recover <REACTION_ID> [--retry]
```

Unsticks a reaction that is stuck in `status=triggered`. Older daemon
builds (before the executor wrapped its action loop in an exception
boundary) could halt the `mori-reaction-executor` subscription on a
spawn-time failure; the reaction row stayed `triggered` forever and no
further reactions on the same target advanced.

**Default behavior:**

1. Marks the stuck row `failed` with the canonical error message
   `manually recovered via mori reaction recover`.
2. Advances the `mori-reaction-executor` subscription's checkpoint past
   the stuck event so the next reaction fires normally.

With `--retry`, additionally re-emits a fresh `ReactionTriggered` event
carrying the original actions under a new reaction ID. Use this once you
have fixed the root cause (PATH, missing binary, bad cwd) and want the
action to run again.

The command refuses to operate on rows already in `completed` or `failed`
state (exit code 2, "nothing to recover"). It is idempotent on
non-triggered rows.

> **Safety.** `recover` updates the `checkpoints` table directly. Running
> it while the daemon is actively processing the same subscription can
> race with the live consumer. It is safe against a genuinely stuck
> subscription (which by definition is not advancing), but stop the
> daemon first if unsure.

### Example

```bash
mori reaction recover rxn_01hy3x...           # Skip the stuck event
mori reaction recover rxn_01hy3x... --retry   # Skip and re-fire
```

## Status Values

| Status | Description |
|---|---|
| `triggered` | The reaction was matched and dispatched but has not finished executing yet. |
| `completed` | All actions in the reaction executed successfully. |
| `failed` | One or more actions failed. Use `mori reaction show` to see the error message and any captured stdout/stderr. |
| `scheduled` | The reaction has been enqueued on the `scheduled_reactions` pgmq queue and is waiting for its `run_at` to elapse. |
| `skipped` | A scheduled reaction was popped, but its idempotency check signalled the work was no longer needed. |
| `cancelled` | A pending scheduled reaction was cancelled before it ran, either by `mori reaction cancel` or by the coalesce-key debounce projection. |

## Schedule Lifecycle

Scheduled reactions extend the lifecycle of an immediate reaction
(`Triggered → Completed | Failed`) with three new terminal states:

```
            ┌─→ Triggered → Completed | Failed
Initial ────┤
            └─→ Scheduled → Skipped (idempotency check said skip)
                          | Cancelled (cancel cli or debounce)
                          | Triggered → Completed | Failed (ran on time)
```

See [Automation › Scheduled Reactions](/docs/guides/automation#scheduled-reactions)
for how to configure `schedule` on a reaction, the ISO 8601 `after`
duration syntax, the optional idempotency check, and the `coalesceKey`
debounce.
