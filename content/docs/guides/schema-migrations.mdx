When the mori schema evolves — for example, adding a new required field to
`mori.dhall` — existing config files need to be updated. The `mori schema
migrate` command detects what changed and can apply updates automatically.

---

## How It Works

Migrations are **structural**. A rule selects its targets from the parsed Dhall
AST and identifies each replacement through a parser-owned **source span** — a
half-open byte range plus the text to put there. The engine checks that every
edit is in bounds and non-overlapping, applies them to the original source in
descending offset order, and re-parses the complete result before returning it.

This is what makes an edit provable rather than plausible. Substring searches and
brace counting can produce a wrong-but-still-parseable change when a manifest
contains a single-line record, a brace inside a string or comment, or a
field-like word in unrelated prose; selecting the syntax node cannot.

Because only the spans it edits are rewritten, **every byte outside an edited
span is preserved** — comments, blank lines, and your formatting all survive.
Full-file pretty printing is deliberately not a migration output mechanism:
Dhall's AST keeps comments only in selected trivia fields, so reprinting a whole
expression would silently drop them.

Each migration is **content-based**: it checks whether the expected fields are
already present in your file. There is no version number to track. This makes
migrations idempotent — running `migrate` twice is always safe, and structural
preconditions make an already-migrated file a no-op rather than a second edit.

A rule is **all-or-nothing**. A fatal parse, span, overlap, or re-parse error
applies none of that rule, so a failed step can never leave a half-edited file
behind; the failure is reported and later migrations still run against the
un-corrupted source.

### Ambiguous targets do not block safe ones

Some structural migrations have a mixed safety boundary. Lifting a legacy
per-action `Schedule` wrapper into the reaction-level `schedule` field is
unambiguous when a reaction has exactly one such action, and needs human
judgement when it has several or mixes action kinds.

Rather than refusing the whole file, the migrator names the ambiguous targets —
by reaction name — for manual review, and migrates the safe siblings in the same
file. See
[Automation › Migrating a legacy `Schedule` wrapper](/docs/guides/automation#migrating-a-legacy-schedule-wrapper).

## Quick Start

### Check for needed migrations

```bash
mori schema migrate
```

If your `mori.dhall` needs updates, you will see:

```
Schema Migration Check
━━━━━━━━━━━━━━━━━━━━━

Checking mori.dhall...

  ✗ Project schema import is bare — rewrite to Schema.Project::{…}
    Wraps the root record in the new record-completion form.
  ✗ Package.apiSource — required field
    Default: None Schema.ApiSource.Type

2 migration(s) needed.

Run `mori schema migrate --apply` to apply.
Run `mori schema migrate --dry-run` to preview.
```

If everything is up to date:

```
Schema Migration Check
━━━━━━━━━━━━━━━━━━━━━

Checking mori.dhall...

  ✓ All migrations already applied.

mori.dhall is up to date.
```

### Preview changes

```bash
mori schema migrate --dry-run
```

```
Dry run — no files will be modified.

Would apply to mori.dhall:
  + rewrite-to-mk-form
  + Package.apiSource = None Schema.ApiSource.Type

2 change(s) would be applied.
```

### Apply changes

```bash
mori schema migrate --apply
```

```
Applying migrations to mori.dhall...

  ✓ Added rewrite-to-mk-form
  ✓ Added Package.apiSource = None Schema.ApiSource.Type

2 change(s) applied.
Run `mori validate` to verify.
```

After applying, run `mori validate` to confirm the file parses correctly against
the current schema.

## Options

| Flag | Description |
|------|-------------|
| _(no flags)_ | Check-only mode — report what needs migrating |
| `--apply` | Apply all needed migrations and write the file |
| `--dry-run` | Show what `--apply` would do without writing |
| `--file PATH` | Target a specific file (default: `mori.dhall`) |

## Current Migrations

Migrations run in the order listed below. The mk-form rewrite runs first so that
subsequent field-level migrations operate on a file already in `::` form.

### `rewrite-to-mk-form`

Rewrites a legacy bare-record `mori.dhall` into the `Schema.Project::{…}` form
using Dhall's record-completion syntax. This is the most important migration:
once your file uses `::`, additive schema changes are absorbed by
`Schema.Project.default` and future field additions stop breaking your config.

**What it does:**

1. Rewrites `in  {` → `in  Schema.Project::{` at the root.
2. Wraps inner record literals (e.g. `project = { … }`, each entry in `repos = [ … ]` / `packages = [ … ]`) in the matching `Schema.<Record>::{…}` completion, eliding fields that equal the published default.
3. Rewrites every `List Schema.<Record>` / `None Schema.<Record>` type annotation for refactored records to its `.Type`-qualified form (e.g. `List Schema.Repo` → `List Schema.Repo.Type`, `None Schema.ApiSource` → `None Schema.ApiSource.Type`).

**Before:**

```dhall
let Schema = https://raw.githubusercontent.com/shinzui/mori-schema/…/package.dhall sha256:…

in  { project = { name = "my-project", … }
    , repos = [ { name = "main", github = Some "myorg/my-project", … } ]
    , packages = [ { name = "core", …, docs = [] : List Schema.DocRef } ]
    , …
    }
```

**After:**

```dhall
let Schema = https://raw.githubusercontent.com/shinzui/mori-schema/…/package.dhall sha256:…

in  Schema.Project::{ project = Schema.ProjectIdentity::{ name = "my-project", … }
    , repos = [ Schema.Repo::{ name = "main", github = Some "myorg/my-project" } ]
    , packages = [ Schema.Package::{ name = "core" } ]
    , …
    }
```

See `mori help project-config` for the full mk-pattern reference with more
examples, and the [Schema Guide](/docs/schema-guide) for details on which fields
can be elided.

### Field-level migrations

These add required fields introduced in newer schema versions. Each inserts a
sensible default after a known anchor field; if the field already exists, the
migration is skipped.

| Migration | Field | Record | Default |
|-----------|-------|--------|---------|
| `add-project-origin` | `origin` | Project | `Schema.Origin.Own` |
| `add-project-skills` | `skills` | Project | `[] : List Schema.Skill.Type` |
| `add-project-subagents` | `subagents` | Project | `[] : List Schema.Subagent.Type` |
| `add-package-lifecycle` | `lifecycle` | Package | `None Schema.Lifecycle` |
| `add-package-runtime-environment` | `runtimeEnvironment` | Package | `None Schema.RuntimeEnvironment` |
| `add-package-api-source` | `apiSource` | Package | `None Schema.ApiSource.Type` |
| `add-project-templates` | `templates` | Project | `[] : List Schema.SeihouTemplate.Type` |
| `add-cookbook-entry-tags` | `tags` | CookbookEntry | `[] : List Text` |

Package-level migrations (`add-package-*`) apply to **every** package in your
file, not just the first one. The cookbook migration only runs when the target
is `mori/cookbook.dhall`.

## When to Run Migrations

Run `mori schema migrate` after upgrading to a new version of the mori CLI. The
recommended workflow:

1. Upgrade the CLI (`cabal install` or `nix build`)
2. Upgrade the schema import: `mori schema upgrade`
3. Check for migrations: `mori schema migrate`
4. Preview: `mori schema migrate --dry-run`
5. Apply: `mori schema migrate --apply`
6. Verify: `mori validate`

Steps 2 and 3–5 are independent — schema upgrade updates the remote import URL
and hash, while migrations add or modify fields in your config. Both may be
needed after a CLI upgrade.

## Migrating Multiple Projects

Use `--file` to target a specific config file:

```bash
mori schema migrate --apply --file path/to/project/mori.dhall
```

For bulk migration across **every** project in your local registry, including
extension files (`mori/cookbook.dhall`, `mori/tech-radar.dhall`), use
[`mori registry upgrade-schema`](/docs/commands/registry#mori-registry-upgrade-schema)
instead. It handles schema-import bumps, migration application, and per-project
validation in a single pass, with `--dry-run`, `--filter`, and `--commit` flags.

For ad-hoc multi-file runs, shell tools still work:

```bash
find ~/projects -name "mori.dhall" -exec mori schema migrate --apply --file {} \;
```

## Troubleshooting

### Migration reports "ApplyFailed"

Common causes:

1. **Target node not found.** The rule could not select the syntax node it
   anchors to — usually because the surrounding record is not shaped the way the
   rule expects, or the file is missing the fields it keys off.
2. **Overlapping or out-of-bounds edits.** The rule produced an edit set the
   engine refused to apply. None of that rule was applied.
3. **Result did not re-parse.** The engine re-parses the complete edited source
   before returning it. If that fails, the whole rule is discarded and later
   migrations still run against the un-corrupted source. The error message
   includes the Dhall parse error.

**Fix:** add the field manually following the guidance in the error message, then
run `mori validate`.

### File already has the field but in a different position

The migration selects fields structurally, not by position. If `origin` already
exists in the target record, the migration reports it as already applied
regardless of where in the record it appears — and, because the check is
structural, a field-like word inside a comment or string will not be mistaken
for it.

### An extension file was refused

Unknown `mori/*.dhall` extension files are refused rather than guessed to be
project files. Classification is explicit: checklist, upstream-issues, cookbook,
tech-radar, and the other known extension shapes are recognized by name, and
anything else is left alone rather than migrated on a hunch.

### Migration applied but `mori validate` fails

The migration inserts fields with sensible defaults, but if your schema import
is outdated, the new field's type may not exist yet. Run `mori schema upgrade`
first to update the schema import, then re-validate.

### Type annotations still show `List Schema.Repo` without `.Type`

If the `rewrite-to-mk-form` migration ran but some annotations still lack the
`.Type` suffix, they reference a type that is not in the refactored-records list
(e.g. `Lifecycle`, `RuntimeEnvironment`, `Dependency`). Those types are still
bare in the upstream schema — no `.Type` suffix is needed.
