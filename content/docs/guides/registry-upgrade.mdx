title: Registry Schema Upgrade
description: Sweep a mori-schema bump across every registered project at once

---

`mori schema upgrade` and `mori schema migrate` operate on one project — the one
in the current directory. `mori registry upgrade-schema` runs that same pipeline
across every project in the local registry, so a schema bump does not require
visiting each checkout by hand.

## Choose and preview the work

The sweep checks the manifest, known native extensions, and resolved automation
sources. A current `mori.dhall` does not hide a stale named automation or a
missing registered source.

```bash
mori registry upgrade-schema --dry-run
mori registry upgrade-schema --filter 'shinzui/*' --dry-run
mori registry upgrade-schema --filter 'acme/billing-api' --all --dry-run
```

| Flag | Description |
|------|-------------|
| `--filter GLOB` | Narrow qualified project names with `*` and `?` |
| `--all` | Also include projects with no pending work; default: work or source problems only |
| `--dry-run` | Discover and parse sources, then report exact paths without changing files, validation state, the Git index, or commits |
| `--allow-dirty` | Permit rewrites in a dirty working tree |
| `--commit` | Create a Conventional Commit with only files changed by the sweep |

Matching is over the full qualified name. The report begins with `Considering N
of M registered projects`, including the unfiltered registry count. There is no
`--group` selector; [registry exec](/docs/guides/registry-exec) can run a
per-project schema command over a group.

## Resolve the same sources the daemon uses

Active automation registrations are authoritative. Only when none exist does
the sweep use the conventional `mori.automation.dhall` fallback. Directories
expand to their sorted direct `.dhall` children. Missing or empty registered
sources stay visible and never cause a different fallback to be migrated.
See [Status](/docs/guides/status#how-automation-sources-are-resolved).

For each selected project, the driver upgrades the main schema pin, applies
field migrations, and validates the manifest. It then applies file-kind
migrations to native extensions and resolved automation files, using
`--kind automation` for named files. After migration, it reloads a file config
for full semantic validation or a directory as one merged config.

Installed declarative extensions keep their own schema pins; a Mori-schema
sweep does not repin them.

## Apply and review

```bash
mori registry upgrade-schema --filter 'acme/*'
mori registry upgrade-schema --filter 'acme/*' --commit
```

Without `--commit`, changes stay unstaged for review. Dirty projects are skipped
before automation writes unless `--allow-dirty` is supplied. Missing checkouts
or manifests are skipped with a reason. Pin state is read from disk rather than
assumed from registry metadata.

In non-commit mode an explicit registration can point outside the project's
Git worktree; its absolute path appears in the report. With `--commit`, every
automation source and member must resolve inside that worktree. External paths
and symlink escapes cause the project to be skipped before any write.

## Read the report

| Project status | Meaning |
|----------------|---------|
| `already current` | No discovered entry point needs work |
| `would apply` | Preview found work for an apply |
| `upgraded` | The pipeline succeeded |
| `skipped: <why>` | Expected inability to operate, such as a dirty or missing checkout |
| `failed: <why>` | Upgrade, migration, or validation failed |

Extensions and named automations have separate indented bullet groups.
Automation bullets say `no change`, `would migrate`, `migrated`, `skipped`, or
`failed`. Automation load, merge, decode, or semantic-validation failure makes
the project fail. Extension failure keeps its historical auxiliary behavior
and does not change the project's own status. One project's failure does not
stop the rest of the sweep.
