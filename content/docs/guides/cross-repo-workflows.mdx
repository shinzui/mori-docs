Cross-repo workflows let a change in one repository automatically trigger
actions in other repositories on the same machine. When a schema changes in
`schema-repo`, mori can automatically run codegen in `payment-service` and
`billing-service` — with full tracing of what happened and whether it succeeded.

This builds on [Automation](/docs/guides/automation) and the [Local Registry](/docs/concepts/local-registry).

---

## How It Works

Mori uses **workflow signals** — typed, correlated events that propagate across
repository boundaries through the event store. The flow:

1. A VCS event (commit, tag) matches a selector in the source repo
2. The source repo's reaction emits a **Signal** action
3. Mori checkpoints the emission, resolves targets, and creates one durable delivery per target
4. A successful delivery receipt triggers each matching target reaction
5. A **workflow projection** tracks the entire chain for observability

No repos call each other directly. They emit facts; other repos react.

---

## Prerequisites

- [Automation](/docs/guides/automation) set up in both source and target repos
- All repos registered in the local registry (`mori register`)
- Every target Project record is linked to a RepoId by `mori observe` or
  `mori automate register`; delivery never reads a checkout-local `mori/repo-id`
- Database migrations run (the `mori.workflows` and `mori.workflow_steps` tables)

## Configuration

### Source Repo: Emitting Signals

Add a `Signal` action to a reaction in the source repo's `mori.automation.dhall`:

```haskell
let EventSelector = ./schema/automation/EventSelector.dhall
let ReactionAction = ./schema/automation/ReactionAction.dhall

in  { events =
      [ EventSelector.ChangesetSelector
          { name = "openapi-changed"
          , paths = [ "openapi.yaml", "openapi/**" ]
          , branches = [ "main" ]
          , messagePatterns = [] : List Text
          }
      ]
    , reactions =
      [ { name = "notify-clients"
        , on = [ "openapi-changed" ]
        , actions =
          [ ReactionAction.Signal
              { signalType = "SchemaChanged"
              , targets = [ "payment-service", "billing-service" ]
              , payload = [ { mapKey = "schema", mapValue = "openapi.yaml" } ]
              }
          ]
        }
      ]
    , execution = { allowLocal = True, allowCI = False, maxConcurrency = None Integer }
    }
```

The `Signal` action fields:

| Field | Type | Description |
|-------|------|-------------|
| `signalType` | `Text` | Domain-meaningful name (e.g., `"SchemaChanged"`, `"ArtifactPublished"`) |
| `targets` | `List Text` | Project names from the registry, or `"*dependents*"` (see below) |
| `payload` | `List { mapKey, mapValue }` | Key-value data forwarded to targets |
| `payloadJson` | `Optional Text` | A structured JSON document, validated when the config loads |
| `cascade` | `Optional SignalCascade` | Opt in to bounded dependency-ordered execution; valid only with exactly `targets = [ "*dependents*" ]` |

#### Structured payloads

`payload` stays supported and unchanged. Reach for `payloadJson` when the target
needs nested fields or typed JSON scalars rather than flat strings:

```dhall
Schema.ReactionAction.Signal Schema.SignalAction::{
  signalType = "SchemaChanged"
, targets = [ "*dependents*" ]
, payload = [ { mapKey = "schema", mapValue = "openapi.yaml" } ]
, payloadJson = Some "{\"verdict\":{\"category\":\"Breaking\"}}"
}
```

Both payload forms travel with the delivery, so you can add `payloadJson` for
new consumers without breaking targets that read the flat `payload`. The JSON is
validated at config load time, not at dispatch time — a malformed document is a
config error, not a runtime surprise.

### Target Repo: Receiving Signals

Add a `SignalSelector` to the target repo's `mori.automation.dhall`:

```haskell
let EventSelector = ./schema/automation/EventSelector.dhall
let ReactionAction = ./schema/automation/ReactionAction.dhall

in  { events =
      [ EventSelector.SignalSelector
          { name = "schema-updated"
          , signalTypes = [ "SchemaChanged" ]
          , sourceProjects = [ "shinzui/schema-repo" ]
          }
      ]
    , reactions =
      [ { name = "regenerate-client"
        , on = [ "schema-updated" ]
        , actions =
          [ ReactionAction.RunCommand
              { command = "make"
              , args = [ "generate-client" ]
              , workingDir = None Text
              , timeout = Some +120
              , env = [] : List { mapKey : Text, mapValue : Text }
              }
          ]
        }
      ]
    , execution = { allowLocal = True, allowCI = False, maxConcurrency = None Integer }
    }
```

## Signal Selectors

The `SignalSelector` fields:

| Field | Type | Behavior |
|-------|------|----------|
| `name` | `Text` | Unique selector name |
| `signalTypes` | `List Text` | Signal type **globs** to match. Empty = match all. |
| `sourceProjects` | `List Text` | Source project names to match, qualified as `namespace/name` (e.g., `"shinzui/schema-repo"`). Exact match; bare project names will not match. Empty = match all. |
| `payloadPredicates` | `List SignalPayloadPredicate` | Payload tests, combined with AND. Empty = match all. |

`signalTypes` entries are globs, so `"Schema*"` matches `SchemaChanged` and
`SchemaDeprecated` alike. `sourceProjects` stays an exact qualified-name match —
project identity is not something you want to fuzzy-match.

### Payload predicates

A predicate narrows a selector by what the signal *says*, not just what it is:

```dhall
Schema.EventSelector.SignalSelector Schema.SignalSelector::{
  name = "breaking-schema-changes"
, signalTypes = [ "Schema*" ]
, sourceProjects = [ "shinzui/schema-repo" ]
, payloadPredicates =
    [ Schema.SignalPayloadPredicate::{
        path = "verdict.category"
      , test = Schema.SignalPayloadPredicate.PredicateTest.Equals "Breaking"
      }
    ]
}
```

| Field | Type | Behavior |
|-------|------|----------|
| `path` | `Text` | Dot-separated path descending through JSON objects |
| `test` | `PredicateTest` | `Equals Text`, `Prefix Text`, or `Exists` |

| Test | Matches |
|------|---------|
| `Equals text` | A string, number, or boolean whose canonical text is exactly `text` |
| `Prefix text` | A string, number, or boolean whose canonical text starts with `text` |
| `Exists` | Any present value, including JSON `null` |

Objects, arrays, and `null` never satisfy `Equals` or `Prefix` — only `Exists`.
A one-segment path falls back to the flat `payload` map when the structured
lookup misses, so a predicate on `"schema"` works against either payload form.
Multiple predicates are combined with AND.

## Target Consent

A target project may restrict which sources are allowed to signal it. Declare
the allowlist on the *target's* `Automation` record:

```dhall
Schema.Automation::{
  consent = Some Schema.SignalConsent::{
    allowSignalsFrom = [ "shinzui/schema-repo", "trusted-team" ]
  }
}
```

Entries are either a qualified project (`namespace/name`) or a bare namespace,
which admits every project in it.

| Declaration | Effect |
|-------------|--------|
| No `consent` field | Allow all sources — the historical behavior |
| `allowSignalsFrom = [ … ]` | Allow only the listed projects and namespaces |
| `allowSignalsFrom = [] : List Text` | Deny every source |

A refusal is recorded as a **terminal failed delivery** with a `consent:` reason
and is never retried — the sender does not get to keep knocking. Inspect
refusals with [`mori signal list --failed`](/docs/commands/signal).

## Delivery Safety Bounds

The *emitting* config bounds how wide and how deep its signals may propagate:

```dhall
Schema.Automation::{
  signalBounds = Some Schema.SignalBounds::{
    maxFanOut = 10
  , maxChainDepth = 4
  }
}
```

| Field | Default | Behavior |
|-------|---------|----------|
| `maxFanOut` | `25` | Maximum resolved targets for one emission |
| `maxChainDepth` | `8` | Maximum depth of a signal chain |

Fan-out is **all-or-nothing**: exceeding the cap creates a visible failed
delivery for every resolved target and delivers to none, so you never get a
half-fanned-out workflow that looks partially successful.

Chains carry ancestor content digests, which gives two distinct protections.
Repeating equivalent signal content fails with a *cycle* reason — a loop is
caught immediately rather than after eight hops. Content that changes on every
hop cannot be recognized as a cycle, so it is stopped by `maxChainDepth`
instead.

This matters most with `*dependents*`: dynamic resolution means the target count
is whatever the dependency graph says today, and a bound is what keeps a new
dependent from silently widening every emission.

## Dynamic Targets: `*dependents*`

Instead of naming every target explicitly, use `"*dependents*"` to resolve the
same distinct qualified projects returned by
`mori registry dependents <source-project>`:

```haskell
ReactionAction.Signal
  { signalType = "SchemaChanged"
  , targets = [ "*dependents*" ]
  , payload = [ { mapKey = "schema", mapValue = "openapi.yaml" } ]
  }
```

Mori queries the authoritative reverse-dependency read model at dispatch time.
Package dependencies, project dependencies, and pinned imports all participate.
Stored resolved targets take precedence, literal names still let unresolved or
external libraries answer the query, the source project is excluded, and target
names are deduplicated.

A valid expansion may find nobody. Mori checkpoints an honest zero-delivery
emission, and `mori signal list` warns on stderr about recent `*dependents*`
emissions that resolved to zero targets.

You can mix dynamic and explicit targets — they are deduplicated:

```haskell
, targets = [ "*dependents*", "extra-service" ]
```

That mixed form is an ordinary one-hop fan-out. It cannot opt into cascade mode.

### Ordered dependency cascades

Inspect the current bounded graph and waves before authorizing work:

```bash
mori registry dependents shinzui/schema-repo --transitive --waves
mori registry dependents shinzui/schema-repo --transitive --waves --json
```

Transitive mode selects `regular` edges by default. Repeat `--scope` for an intentional union,
lower `--max-depth` when appropriate, and add `--packages` to inspect edge provenance.

```dhall
Schema.ReactionAction.Signal Schema.SignalAction::{
  signalType = "UpgradeDependency"
, targets = [ "*dependents*" ]
, payload = [ { mapKey = "version", mapValue = "5.0.0" } ]
, cascade = Some Schema.SignalCascade::{
    scopes = [ Schema.DependencyScope.Regular ]
  , maxDepth = 32
  }
}
```

Mori validates and checkpoints the transitive graph before starting the Workflow. Only targets
whose frozen upstreams succeeded receive SignalDelivery rows. A failure blocks descendants while
independent branches continue, and the Workflow closes `partial` after all runnable work finishes.
Waiting and blocked targets have no delivery to retry.

The registry command is a live preflight; a Workflow trace is immutable execution evidence.
Changing the registry after dispatch can change a later preflight, but not an in-flight or
historical run. Without `cascade`, `"*dependents*"` retains its compatible one-hop behavior.

## Event Flow

```
1. Developer commits openapi.yaml in schema-repo

2. mori automate ingest git (schema-repo)
   → ChangesetObserved written to repository-{schema-repo-id}-{date}

3. mori-automation-router subscription matches "openapi-changed" selector
   → Triggers "notify-clients" reaction
   → Writes ReactionTriggered to reaction-{rxn-id}

4. mori-reaction-executor-store picks up the reaction
   → Sees Signal action with targets ["payment-service", "billing-service"]
   → Records a digest-keyed SignalEmission checkpoint before dispatch
   → Resolves targets via the registry and starts Workflow wf_xxxx
   → Creates one pending SignalDelivery stream per resolved target

5. mori-signal-delivery-worker resolves payment-service's repository identity
   → Records SignalDeliverySucceeded (or retry/failed/expired state)

6. mori-signal-trigger-router picks up SignalDeliverySucceeded
   → Marks the exact Workflow target step delivered
   → Matches "schema-updated" SignalSelector
   → Applies the target automation's common immediate/scheduled/queued policy
     to the "regenerate-client" reaction

7. When eligible, mori-reaction-executor-store runs `make generate-client`
   → Writes ReactionCompleted or ReactionFailed

8. Workflow completion detects all steps done
   → Writes WorkflowCompleted to workflow-{wf-id}
```

## CLI Commands

### List recent workflows

```bash
mori workflow list
```

```
Recent Workflows
================
ID                      SIGNAL          SOURCE                  REACTION         TARGETS  STATUS       STARTED
wf_01h455vb4pex5vs...  SchemaChanged   shinzui/schema-repo     notify-clients         2  ✓ completed  2026-03-06 10:15:32 UTC
wf_01h455vb4pex5vs...  ConfigUpdated   shinzui/config-repo     publish-config         1  ✗ failed     2026-03-06 09:30:15 UTC
```

`SOURCE` carries the qualified `namespace/name` of the upstream project that
emitted the signal. `REACTION` carries the upstream reaction name (the
reaction in the source repo whose `Signal` action fired) — a separate column
because the same project commonly hosts multiple signal-emitting reactions.

Limit the number of results:

```bash
mori workflow list -n 5
```

### Show active workflows

```bash
mori workflow status
```

Shows workflows with steps still in progress (pending or delivered but not
yet completed). Includes step details for each active workflow.

### Trace a workflow

```bash
mori workflow trace wf_01h455vb4pex5vsknk084sn02q
mori workflow trace wf_01h455vb4pex5vsknk084sn02q --flat
mori workflow trace wf_01h455vb4pex5vsknk084sn02q --json
mori workflow trace wf_01h455vb4pex5vsknk084sn02q --mermaid
mori workflow trace wf_01h455vb4pex5vsknk084sn02q --max-depth 8
```

By default, `trace` renders the **complete causal chain**, not just one
workflow: it walks up to the chain root and renders every descendant workflow
and target step as a tree. You can start from any workflow in the chain and get
the same picture, which is the point — you rarely know which link you happen to
be holding.

| Flag | Behavior |
|------|----------|
| `--flat` | Show only the requested workflow, in the original detail view below |
| `--json` | Emit the nested chain document as JSON |
| `--mermaid` | Emit the chain as a Mermaid `flowchart LR` diagram |
| `--max-depth N` | Bound ancestor and descendant traversal (default: `32`) |

The HTTP equivalent is `GET /v1/workflows/<WORKFLOW_ID>/chain`; JSON field names
there follow the API's snake_case convention. See
[`mori serve`](/docs/commands/serve).

Cascade traces additionally publish `workflow_kind`, the versioned frozen root, scopes, graph
limits and edges, plus every step's `wave_index`, `upstreams`, and `blocked_by`. Mermaid draws the
source root as already satisfied and uses the frozen provider-to-consumer edges, with distinct
failed and blocked styles. The Workflow, steps, and chain HTTP endpoints expose the same facts;
trace never re-runs the registry query.

History recorded before workflow parent correlation was introduced has no
reconstructible chain edge. Those workflows are shown honestly as independent
roots rather than guessed into a tree. Tracing covers the Kiroku functional
automation path; the removed legacy MessageDB path is not supported.

`Source Project` is the qualified upstream project (matching `SOURCE` from
`mori workflow list`); `Source Reaction` is the reaction in that project
whose `Signal` action emitted this workflow. `Targets` and the `TARGET`
column echo back whatever target names the source-repo `Signal` action
listed — bare names work as long as `mori register` has populated the
registry, since `targets` is resolved by the dispatcher via the dependency
graph rather than matched against `sourceProjects`.

### Inspect deliveries

Where `mori workflow` shows the causal chain, `mori signal` shows the durable
delivery records underneath it:

```bash
mori signal list
mori signal list --failed
```

Each row carries the delivery id, signal type, source → target, state
(`pending`, `delivered`, `failed`, `expired`), retry count, and the failure
reason when there is one. This is where a consent refusal or a fan-out breach
surfaces. See [`mori signal`](/docs/commands/signal).

## Subscriptions

When `mori automate run` starts, it runs four concurrent subscriptions:

| Subscription | Category | Purpose |
|-------------|----------|---------|
| `mori-automation` | `repository` | Match selectors, trigger reactions |
| `mori-reaction-executor` | `reaction` | Execute triggered actions (including signal dispatch) |
| `mori-registry` | `project` | Populate registry read model |
| `mori-workflow` | `workflow` | Maintain `mori.workflows` and `mori.workflow_steps` projections |

Plus a shibuya worker for scheduled actions.

## Troubleshooting

### Signal target not found

```
target not found: payment-service
```

The target project isn't registered in the local registry. Run:

```bash
cd /path/to/payment-service
mori register
```

### No repo-id for target

```
no repo-id for target: payment-service
```

The target project directory doesn't have a `mori/repo-id` file. Run
`mori automate ingest git` or `mori init` in the target project to create one.

### No workflows found

If `mori workflow list` returns no results:

1. Verify the `mori.workflows` table exists (run migrations)
2. Verify the `mori-workflow` subscription is running (`mori automate run`)
3. Check that signal dispatch is working — look for `WorkflowSignalEmitted` events in the source repo's stream
4. Verify the target's `SignalSelector.sourceProjects` filter uses the
   **qualified** upstream project name (`namespace/name`, e.g.
   `shinzui/schema-repo`). Bare project names will silently match nothing —
   `WorkflowSignalReceived` events carry the source project as
   `namespace/name`, so a bare-name filter has no chance of matching.

### Signal delivered but the target never reacted

Check the delivery record first:

```bash
mori signal list --failed
```

A `consent:` reason means the target's `allowSignalsFrom` does not admit this
source — add the source project or its namespace to the target's
[`consent`](#target-consent), or remove the declaration to allow all.

A fan-out, depth, or cycle reason means the emission breached
[`signalBounds`](#delivery-safety-bounds). A cycle reason in particular means the
same signal content came back around; raising the bound will not help, the loop
needs breaking.

If the delivery shows `delivered` but no reaction ran, the target's selector did
not match. Re-check `signalTypes` (globs, so `"Schema*"` and `"SchemaChanged"`
behave differently from a typo) and any `payloadPredicates` — a predicate on a
path the payload does not carry silently narrows the selector to nothing.

### `*dependents*` resolves to no targets

The authoritative query found no package, project, or pinned-import edge back
to the source. Verify the exact query with:

```bash
mori registry dependents <namespace/source-project>
mori signal list
```

The first command shows the edges used for dynamic targeting. The second warns
about recent zero-target dependent emissions even though there is no failed
delivery row.
