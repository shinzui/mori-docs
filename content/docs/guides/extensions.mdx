Mori's extension system lets you attach structured metadata to projects beyond
what the core schema provides. Extensions are project-scoped Dhall configs
stored in the `mori/` directory and registered alongside the project in the
local registry. Six built-in extension catalogs ship with the CLI:
**tech radar**, **cookbook**, **checklist**, **upstream issues**,
**agent plans**, and **DDD** (Domain-Driven Design).

Most extensions expose a `list` / `show` / `print-schema` command surface and a
cross-project `mori extension query <name>`. Two go further: **agent plans**
(`mori plans ...`) and **DDD** (`mori ddd ...`) also fan their data out into
dedicated relational tables and expose richer cross-project search.

## How Extensions Work

An extension is a named metadata type registered in the event store. Projects
opt in by placing a Dhall config file in `mori/`, such as
`mori/tech-radar.dhall`, `mori/cookbook.dhall`, `mori/checklist.dhall`, or
`mori/upstream-issues.dhall`, `mori/agent-plans.dhall`, or `mori/ddd.dhall`.
When you run `mori register --local`, extension data is automatically detected
and registered alongside the project.

## Managing Extension Types

### Define an extension

```bash
mori extension define tech-radar \
  --description "Preferred packages by language and category" \
  --schema-ref schema/extensions/tech-radar/
```

| Flag | Required | Purpose |
|------|----------|---------|
| `--description` / `-d` | Yes | Human-readable description |
| `--schema-ref` | No | Path to the extension's Dhall schema directory |

### List active extensions

```bash
mori extension list
```

```
Extensions
NAME             DESCRIPTION                                      SCHEMA REF
tech-radar       Preferred packages by language and category       schema/extensions/tech-radar/
cookbook          Code examples, patterns, and guides               schema/extensions/cookbook/
checklist         Structured procedures for humans and agents       schema/extensions/checklist/
upstream-issues   Known upstream defects and local workarounds      schema/extensions/upstream-issues/
```

### Retire an extension

```bash
mori extension retire tech-radar
mori extension retire tech-radar --force   # skip confirmation
```

Retiring soft-deletes the extension type. Existing data remains in the event
store but is no longer queryable.

### Query extension data

Query extension entries across all registered projects:

```bash
mori extension query cookbook
mori extension query cookbook --project my-service
mori extension query cookbook --topic database --content-type sample-code
mori extension query checklist
mori extension query upstream-issues --json
mori extension query cookbook --json
```

| Flag | Purpose |
|------|---------|
| `--project` / `-p` | Filter to a specific project (name or namespace/name) |
| `--topic` | Filter cookbook entries by topic |
| `--content-type` | Filter cookbook entries by content type |
| `--json` | JSON output |

Filters are case-insensitive. Content type filters normalize hyphens and
underscores (`sample-code` and `samplecode` both work).

## Tech Radar

The tech radar extension captures preferred packages by language and category,
with adoption levels (Adopt, Trial, Assess, Hold), optional alternatives, and
an optional `project` URI pointing at a registered implementation.

### Configuration

Create `mori/tech-radar.dhall` in your project:

```dhall
let TechRadar = ./schema/extensions/tech-radar/package.dhall

in  TechRadar.TechRadar::{
    , recommendations =
      [ TechRadar.Recommendation::{
        , package = "effectful"
        , language = TechRadar.Language.Haskell
        , category = TechRadar.Category.Effects
        , level = TechRadar.AdoptionLevel.Adopt
        , reason = Some "Production-ready, good performance, extensible"
        , alternatives = [ "polysemy", "fused-effects" ]
        }
      , TechRadar.Recommendation::{
        , package = "aeson"
        , language = TechRadar.Language.Haskell
        , category = TechRadar.Category.Serialization
        , level = TechRadar.AdoptionLevel.Hold
        , reason = Some "Moving to json-syntax for better error messages"
        , alternatives = [ "json-syntax" ]
        }
      ]
    }
```

Each extension ships a `package.dhall` re-export with the same `{ Input, Type,
default, mk }` bundle shape as the core schema, so the same record-completion
idiom (`TechRadar.Recommendation::{ … }`) applies. Fields that equal the
published default can be elided.

The optional `project` field accepts a `mori://<namespace>/<name>` URI:

```dhall
, project = Some "mori://shinzui/hasql-kit"
```

### List recommendations

```bash
mori tech-radar list
mori tech-radar list --language Haskell
mori tech-radar list --category Database
mori tech-radar list --config path/to/tech-radar.dhall
mori tech-radar search --level Adopt --category Database
mori tech-radar search --recommends mori://shinzui/hasql-kit
mori tech-radar search --json
```

```
Tech Radar
LANGUAGE    CATEGORY        PACKAGE       LEVEL
Haskell     Effects         effectful     Adopt
Haskell     Serialization   aeson         Hold
```

Adoption levels are color-coded: Adopt (green), Trial (yellow), Assess (blue),
Hold (red).

| Flag | Default | Purpose |
|------|---------|---------|
| `--config` | `mori/tech-radar.dhall` | Config file path |
| `--language` | (all) | Filter by language |
| `--category` | (all) | Filter by category |

`mori tech-radar list` and `show` read the current project's
`mori/tech-radar.dhall` directly. `mori tech-radar search` queries the registry
projection across all registered projects.

### Show package details

```bash
mori tech-radar show effectful
```

```
Tech Radar Recommendation
  Package:       effectful
  Language:       Haskell
  Category:       Effects
  Level:          Adopt
  Reason:         Production-ready, good performance, extensible
  Alternatives:   polysemy, fused-effects
```

### Print schema

```bash
mori tech-radar print-schema
```

Outputs the Dhall type definitions for the tech-radar extension (TechRadar,
Recommendation, AdoptionLevel, Category).

## Cookbook

The cookbook extension provides structured metadata for code examples, patterns,
and guides. It enriches the basic `DocRef` cookbooks with content types, topics,
related packages, and language tags so agents can find relevant material without
reading every file.

### Configuration

Create `mori/cookbook.dhall` in your project:

```dhall
let Cookbook = ./schema/extensions/cookbook/package.dhall

in  Cookbook.CookbookCatalog::{
    , entries =
      [ Cookbook.CookbookEntry::{
        , key = "hasql-queries"
        , title = "How to Write Hasql Queries"
        , contentType = Cookbook.ContentType.SampleCode
        , topics = [ Cookbook.Topic.Database ]
        , packages = [ "hasql", "hasql-pool" ]
        , language = Cookbook.Language.Haskell
        , audience = Cookbook.Audience.Module
        , location = Cookbook.Location.LocalFile "docs/hasql-queries.md"
        , description = Some "Query patterns, connection management, transactions"
        , tags = [ "async", "performance-critical" ]
        }
      , Cookbook.CookbookEntry::{
        , key = "effectful-patterns"
        , title = "Effectful Patterns"
        , contentType = Cookbook.ContentType.Pattern
        , topics = [ Cookbook.Topic.Effects ]
        , packages = [ "effectful" ]
        , language = Cookbook.Language.Haskell
        , audience = Cookbook.Audience.Module
        , location = Cookbook.Location.LocalFile "docs/effectful-patterns.md"
        , description = Some "Effect definitions, interpreters, testing"
        }
      ]
    }
```

**New in 2026-04:** the optional `tags` field (`List Text`) captures
cross-cutting tags independent of the fixed `Topic` enum (e.g., `"async"`,
`"performance-critical"`). Existing catalogs can be brought forward with:

```bash
mori schema migrate --apply --file mori/cookbook.dhall
```

The same migrate command also runs `upgrade-cookbook-extension-import`,
which keeps the file's `let Cookbook = …` binding in sync with the root
`Schema` pin. The cookbook-only types (`CookbookCatalog`, `CookbookEntry`,
`ContentType`, `Topic`) live exclusively under the `Cookbook` binding —
the root `Schema` does not re-export them. Files using legacy conventions
(un-hashed direct imports of `extensions/cookbook/ContentType.dhall` /
`Topic.dhall`, a stale-pinned `Cookbook` binding, or no extension binding
at all) are rewritten to the canonical hashed `let Cookbook = …` form,
with all `Schema.{CookbookCatalog,CookbookEntry,ContentType,Topic}` and
bare `ContentType.` / `Topic.` references rewritten through the
`Cookbook` binding. Local-path imports (test fixtures using
`../schema/extensions/cookbook/package.dhall`) are left alone.

To sweep every registered project's `mori/cookbook.dhall` at once, use
the bulk upgrader:

```bash
mori registry upgrade-schema
```

For cookbook files, the bulk pipeline runs both
`add-cookbook-entry-tags` and `upgrade-cookbook-extension-import`; the
dry-run reports `would migrate` for each cookbook file that any of these
passes needs to touch.

Migration rules select Dhall syntax nodes and splice exact source spans, so
comments and formatting outside an edited span are preserved, and overlapping
edits or output that does not parse are rejected before any file is written.
Unknown `mori/*.dhall` extension files are refused rather than guessed to be
project files.

Per-extension failures are reported but do not flip the per-project status —
extension drift is an inconvenience, not a blocker. Re-running is safe:
structural preconditions make files already in mk form a no-op.

See [Schema Migrations](/docs/guides/schema-migrations) for how the
per-extension migration pipeline handles additive field changes.

### List entries

```bash
mori cookbook list
mori cookbook list --topic database
mori cookbook list --content-type sample-code
mori cookbook list --package hasql
mori cookbook list --language Haskell
```

```
Cookbook Catalog
KEY                  TYPE          TOPICS       PACKAGES
hasql-queries        SampleCode    Database     hasql, hasql-pool
effectful-patterns   Pattern       Effects      effectful
```

All filters use AND logic — an entry must match every provided filter. Within
`--topic` and `--package`, matches are OR (any topic/package in the entry).

| Flag | Default | Purpose |
|------|---------|---------|
| `--config` | `mori/cookbook.dhall` | Config file path |
| `--content-type` | (all) | Filter by type (sample-code, instructions, pattern, configuration, template) |
| `--topic` | (all) | Filter by topic (database, api, testing, effects, etc.) |
| `--package` | (all) | Filter by related package |
| `--language` | (all) | Filter by language |

### Show entry details

```bash
mori cookbook show hasql-queries
```

```
Cookbook Entry
  Key:           hasql-queries
  Title:         How to Write Hasql Queries
  Content Type:  SampleCode
```

### Print schema

```bash
mori cookbook print-schema
```

Outputs the Dhall type definitions for the cookbook extension (CookbookCatalog,
CookbookEntry, ContentType, Topic).

### Cookbook vs. DocRef cookbooks

The `docs` field in `mori.dhall` supports `kind = Cookbook` entries (DocRef
cookbooks). These are simple path references. The cookbook extension adds
structured classification. Both coexist — simple projects can use DocRef alone;
projects needing richer metadata use the extension.

## Checklist

The checklist extension catalogs ordered procedures such as install, deploy,
monitor, onboard, release, and incident workflows. Each step has a kind,
optional command text, success criteria, preconditions, tags, and a `docs` list
of step-specific documentation references. A step's `docs` can use
`DocLocation.Canonical "mori://…"` to point at a registered mori doc.

```bash
mori checklist list
mori checklist list --category deployment
mori checklist list --kind verify
mori checklist show install
mori checklist show install --step enter-devshell
mori checklist print-schema
```

The CLI renders checklist commands; it does not execute step commands.
Registration validates duplicate keys, empty titles, and preconditions that
refer to missing or later steps. `mori validate --check-refs` additionally
resolves each item's canonical `docs` references — and the checklist-level
`sourceDoc` — against the local registry. See
[Checklist](/docs/guides/checklist) for configuration examples.

## Upstream Issues

The upstream-issues extension records known defects in upstream dependencies
with status, workaround links, upstream URLs, revisit triggers, and tags.

```bash
mori upstream-issues list
mori upstream-issues list --dependency hs-opentelemetry-api
mori upstream-issues list --status workaround
mori upstream-issues show hs-otel-resource-attribute-leak
mori upstream-issues print-schema
```

Cross-project queries use the generic extension query command:

```bash
mori extension query upstream-issues
mori extension query upstream-issues --json
```

See [Upstream Issues](/docs/guides/upstream-issues) for configuration examples.

## DDD

The DDD extension records a project's Domain-Driven Design model: subdomains,
bounded contexts, aggregates, context mappings, message flows, glossary terms,
collaborators, and verification metadata.

```bash
mori agent bootstrap-ddd
mori ddd subdomains
mori ddd aggregates --context checkout
mori ddd mappings --pattern published-language
mori ddd search --emits OrderPlaced
mori ddd search --term invoice --json
```

Local `mori ddd` browse commands read `mori/ddd.dhall` directly. `mori ddd
search` uses the registry's relational `mori.ddd_*` projection for
cross-project queries by relationship pattern, emitted event, owning context, or
glossary term.

Use [`mori extension query ddd`](/docs/commands/extension#mori-extension-query)
when you want the generic JSONB extension payload for one project. Use
[`mori ddd search`](/docs/commands/ddd#mori-ddd-search) when you want
relational search across projects.

See [DDD Extension](/docs/guides/ddd) for schema details and a full worked
configuration.

## Registration

Extensions are auto-detected during `mori register --local`. The output shows
which extensions were found:

```bash
mori register --local
```

```
Registered: my-namespace/my-project
  Extensions: cookbook, tech-radar, checklist, upstream-issues, agent-plans, ddd
```

## Cross-Project Queries

Use `mori extension query` to search extension data across all registered
projects. This is useful for finding cookbook entries or tech radar
recommendations across your workspace:

```bash
# Find all cookbook entries about database patterns
mori extension query cookbook --topic database

# Find tech radar recommendations in a specific project
mori extension query tech-radar --project my-service

# Inspect one project's DDD model from the generic extension table
mori extension query ddd --project my-service
```
