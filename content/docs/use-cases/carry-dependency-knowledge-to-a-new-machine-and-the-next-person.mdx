## The scenario

An engineer learns something difficult about an upstream dependency. Months
later, a teammate on another machine needs the same answer. Mori treats the
dependency as a registered wrapper project: source code on disk, curated docs,
typed findings, provenance, and a qualified name that consumers can declare.

## How it works

1. The wrapper keeps a local copy of upstream source and can declare the upstream it tracks as a typed reference.
2. Consumers depend on the wrapper by name. The [local registry](/docs/concepts/local-registry) resolves its path for each machine, so durable documents do not encode checkout layouts.
3. [`mori registry docs`](/docs/commands/registry) and catalog search find the team's guidance from any registered project. See the [corpus learning guide](/docs/guides/corpus-learning).

The wrapper, named resolution, catalogs, and navigation are delivered. A
[shared registry](/docs/guides/shared-registry) and [mori-lite](/docs/guides/lite)
now implement portable index publication and offline reading without a local
PostgreSQL server. The catalog carries metadata; clone the repositories for
source and document files.

The source still marks **registry sync between machines** and the
**low-friction read tier** as **planned**, coordinated by
`mori://shinzui/mori/masterplans/39-onboard-the-team-on-a-shared-registry-with-a-push-from-the-workstation-and-a-lightweight-read-only-client`.
Implementation children are complete, but standalone installation on a machine
without Nix and the two-person pilot remain adoption gates. The concept stays
**draft**; available commands do not close those gates. See
[UC-5](/docs/use-cases/ground-a-coding-agent-in-declared-project-knowledge)
for agent grounding.
