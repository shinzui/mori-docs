## The scenario

An agent or engineer opening an unfamiliar repository needs to learn its
purpose, dependencies, dependency source and docs, and local conventions.
Mori makes those answers queries over declared project knowledge rather than
facts assembled for a one-off prompt.

## How it works

1. [`mori show`](/docs/commands/show) and [`mori status`](/docs/commands/status) read the project manifest.
2. [`mori deps locate`](/docs/commands/deps) and [`mori registry docs`](/docs/commands/registry) resolve dependency source and curated docs by qualified project name.
3. Registry concept search and typed catalogs find examples and knowledge with producer and trust provenance.
4. [`mori agent context <role>`](/docs/commands/agent#mori-agent-context) assembles JSON for a role; `mori://` references can be resolved with [`mori path`](/docs/commands/path).

The manifest, registry, catalogs, and role context are delivered. Three
features remain **discovered**:

- Protocol-neutral agent access beyond the current agent-specific integration,
  tracked by `mori://shinzui/mori/okf/improvement-requests/concepts/IR-13`.
  [HTTP reference resolution](/docs/guides/api#portable-reference-resolution) is available,
  but it does not complete that broader grounding interface.
- Checking whether curated references still point to current material.
- Labelling prompt content with its project origin, granting permissions by agent
  mode, and recording the effective permissions and context provenance in each
  session, tracked by `mori://shinzui/mori/okf/improvement-requests/concepts/IR-33`.

[UC-6](/docs/use-cases/carry-dependency-knowledge-to-a-new-machine-and-the-next-person)
covers how this knowledge is stored and carried forward.
