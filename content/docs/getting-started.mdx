## Prerequisites

**Required:**

- PostgreSQL with mori's database migrations applied. The current event runtime
  uses the keiro/kiroku stack, plus pgmq-backed queues for deferred work.
- The `mori` CLI built and on your PATH (`cabal install mori-cli`)
- A `MORI_PG_CONNECTION_STRING` environment variable pointing to your database:

```bash
export MORI_PG_CONNECTION_STRING="host=localhost port=5432 dbname=mori_dev"
```

Some migration and compatibility paths still read legacy MessageDB history. The
current `mori doctor` baseline check therefore verifies both PostgreSQL
connectivity and the legacy `message_store` schema. See [`mori history`](/docs/commands/history)
for the MessageDB-to-kiroku migration command surface.

**Verify your setup:**

```bash
mori doctor
```

Expected output:

```
mori v0.1.0

PostgreSQL connection... [OK]
MessageDB installation... [OK]

All checks passed.
```

If either check shows `[FAIL]`, fix the indicated issue before continuing.

## 1. Initialize a Project

Navigate to your project's git repository and run:

```bash
mori init
```

This creates two things:

- `mori.dhall` — your project identity manifest
- `mori/` — a directory for local configuration

The project name defaults to the current directory name. To override:

```bash
mori init --name payments
```

Output:

```
Created mori.dhall for project 'payments'
Created mori/ directory
```

### The generated `mori.dhall`

If your repository has a `schema/` directory (e.g., you've cloned the mori schema), the scaffold uses typed imports:

```dhall
let Schema = ./schema/package.dhall

in  Schema.Project::{
    , project = Schema.ProjectIdentity::{
      , name = "payments"
      , namespace = "default"
      , type = Schema.PackageType.Application
      , language = Schema.Language.Haskell
      }
    }
```

The scaffold uses Dhall's record-completion syntax (`Schema.Project::{ … }`) so
that fields you don't set fall back to the schema's published defaults — adding
new optional fields upstream is a no-op for existing configs. Empty list fields
(`repos`, `packages`, `docs`, …) are omitted rather than spelled as
`[] : List Schema.<Record>` because the default already supplies an empty list.

Otherwise, the scaffold inlines the full Dhall type definitions.

### Key fields to customize

Edit `mori.dhall` to describe your project:

```dhall
let Schema = ./schema/package.dhall

in  Schema.Project::{
    , project = Schema.ProjectIdentity::{
      , name = "payments"
      , namespace = "acme"
      , type = Schema.PackageType.Application
      , description = Some "Core payments service"
      , language = Schema.Language.Haskell
      , domains = [ "Payments", "Billing" ]
      , owners = [ "fintech-platform" ]
      }
    , repos =
      [ Schema.Repo::{ name = "main", github = Some "acme/payments" }
      ]
    , packages =
      [ Schema.Package::{
        , name = "payments-core"
        , type = Schema.PackageType.Library
        , language = Schema.Language.Haskell
        , path = Some "payments-core"
        , description = Some "Core domain logic"
        , visibility = Schema.Visibility.Internal
        , dependencies =
          [ Schema.Dependency.ByName "effectful"
          , Schema.Dependency.ByName "aeson"
          ]
        }
      , Schema.Package::{
        , name = "payments-service"
        , type = Schema.PackageType.Application
        , language = Schema.Language.Haskell
        , path = Some "payments-service"
        , description = Some "HTTP API server"
        , visibility = Schema.Visibility.Internal
        , runtime = Schema.Runtime::{ deployable = True, exposesApi = True }
        , dependencies =
          [ Schema.Dependency.ByName "payments-core" ]
        , config =
          [ Schema.ConfigItem::{
            , key = "DATABASE_URL"
            , type = Schema.ConfigValueType.Url
            , description = Some "PostgreSQL connection string"
            , sourceHint = Some (Schema.ConfigSourceHint.EnvVar "DATABASE_URL")
            , example = Some "postgres://localhost:5432/payments"
            }
          ]
        }
      ]
    , dependencies = [ "effectful", "aeson", "hasql" ]
    }
```

**Available types for key fields:**

| Field | Options |
|---|---|
| `type` | `Application`, `Library`, `Client`, `Worker`, `Tool`, `Other` |
| `language` | `Haskell`, `TypeScript`, `JavaScript`, `Python`, `Go`, `Rust`, `Java`, `Kotlin`, `Swift`, `Ruby`, `Elixir`, `Clojure`, `Scala`, `Dhall`, `Nix`, `SQL`, `Shell`, `Other` |
| `lifecycle` | `Active`, `Experimental`, `Deprecated`, `Archived` |
| `visibility` | `Public`, `Internal`, `Private` |

## 3. Register in the Local Registry

Register your project in the event-sourced local registry:

```bash
mori register --local
```

First registration:

```
Project registered: acme/payments
```

If you change `mori.dhall` and re-register, mori computes a granular diff and emits only the specific change events (e.g., type changed, dependency added, dependency removed):

```
Project updated: acme/payments
```

If nothing changed:

```
Project up to date: acme/payments
```

Registration is idempotent — running it multiple times with the same config produces no duplicate events.

## 4. Dependency Management

### Declare dependencies

Project-level dependencies are listed by name in `mori.dhall`:

```haskell
, dependencies = [ "effectful", "aeson", "hasql" ]
```

Package-level dependencies use the `Dependency` type:

```haskell
, dependencies =
  [ Schema.Dependency.ByName "effectful"
  , Schema.Dependency.ByName "aeson"
  ]
```

### Resolve dependencies

Check which declared dependencies are registered in the local registry:

```bash
mori deps resolve
```

```
  [found]     effectful
  [found]     aeson
  [not found] hasql
```

JSON output:

```bash
mori deps resolve --json
```

```json
[
  {"name": "effectful", "found": true, "projectId": "...", "packagePath": "..."},
  {"name": "aeson", "found": true, "projectId": "...", "packagePath": "..."},
  {"name": "hasql", "found": false, "projectId": null, "packagePath": null}
]
```

### Locate a specific dependency

```bash
mori deps locate effectful
```

```
Dependency: effectful
  Project ID: <projectId>
  Path: <packagePath>
```

### Explain a dependency's resolution

Get the full resolution trace including the owning project:

```bash
mori deps explain effectful
```

```
Dependency: effectful
  Resolution: found in local registry
  Project: acme/shared-libs
  Project ID: <projectId>
  Project Path: <path>
  Package Path: <packagePath>
  Registered: 2026-01-15T10:30:00Z
  Packages: shared-core (Library, Haskell), shared-service (Application, Haskell)
```

All `deps` subcommands accept `--json` for structured output.

## 5. Agent Context

Agent hints tell AI coding assistants which parts of your project are relevant to specific roles.

### Declare agent hints

Add agents to your `mori.dhall`:

```haskell
    , agents =
      [ { role = "backend"
        , description = Some "Backend development agent"
        , includePaths = [ "payments-core/", "payments-service/" ]
        , excludePaths = [ "node_modules/", ".stack-work/" ]
        , relatedPackages = [ "payments-core", "payments-service" ]
        }
      , { role = "ops"
        , description = Some "Operations and deployment"
        , includePaths = [ "deploy/", "infra/" ]
        , excludePaths = [] : List Text
        , relatedPackages = [ "payments-service" ]
        }
      ]
```

### List configured roles

```bash
mori agent list
```

```
backend - Backend development agent
ops - Operations and deployment
```

### Generate agent context

Build a structured context JSON for a specific role (resolves dependencies from the registry):

```bash
mori agent context backend
```

This outputs a JSON object with the role's include/exclude paths, related packages, and resolved dependency information — ready to feed into an AI coding agent.

## 6. Automation: Configuration

Create `mori.automation.dhall` in your project root. This file declares which repository events to watch and how to react.

### Minimal working example

```haskell
let EventSelector = ./schema/automation/EventSelector.dhall
let ReactionAction = ./schema/automation/ReactionAction.dhall

in  { events =
      [ EventSelector.ChangesetSelector
          { name = "src-changes"
          , paths = [ "src/**" ]
          , branches = [ "main" ]
          , messagePatterns = [] : List Text
          }
      ]
    , reactions =
      [ { name = "lint-on-change"
        , on = [ "src-changes" ]
        , actions =
          [ ReactionAction.RunCommand
              { command = "make"
              , args = [ "lint" ]
              , workingDir = None Text
              , timeout = None Integer
              , env = [] : List { mapKey : Text, mapValue : Text }
              }
          ]
        }
      ]
    , execution =
      { allowLocal = True
      , allowCI = False
      , maxConcurrency = None Integer
      }
    }
```

### EventSelector types

**ChangesetSelector** — matches commits by file paths, branch, and commit message:

```haskell
EventSelector.ChangesetSelector
  { name = "api-changes"
  , paths = [ "src/api/**", "openapi.yaml" ]
  , branches = [ "main", "release/*" ]
  , messagePatterns = [ "feat:*", "fix:*" ]
  }
```

- `paths`: glob patterns matched against touched files (empty = match all)
- `branches`: branch name patterns (empty = match all)
- `messagePatterns`: commit message patterns (empty = match all)

**RefSelector** — matches branch/tag pointer changes:

```haskell
EventSelector.RefSelector
  { name = "release-tags"
  , refPatterns = [ "v*", "release/*" ]
  , kinds = [ "tag" ]
  }
```

- `refPatterns`: ref name patterns
- `kinds`: `"branch"`, `"tag"`, or empty for all

### ReactionAction types

**RunCommand** — execute a shell command:

```haskell
ReactionAction.RunCommand
  { command = "cargo"
  , args = [ "test", "--workspace" ]
  , workingDir = Some "./backend"
  , timeout = Some +300
  , env = [ { mapKey = "RUST_LOG", mapValue = "info" } ]
  }
```

**EmitEvent** — record an event-emission intent in the reaction result:

```haskell
ReactionAction.EmitEvent
  { eventType = "DeploymentRequested"
  , streamName = "deployment-payments"
  , eventData = [ { mapKey = "environment", mapValue = "staging" } ]
  }
```

**Notify** — send an HTTP notification (webhook):

```haskell
ReactionAction.Notify
  { url = "https://hooks.slack.com/services/T00/B00/xxxx"
  , method = Some "POST"
  , headers = [ { mapKey = "Content-Type", mapValue = "application/json" } ]
  , bodyTemplate = Some "{\"text\": \"Source changed in payments\"}"
  }
```

**Schedule** — delay an action by a number of seconds:

```haskell
ReactionAction.Schedule
  { delaySeconds = +60
  , action =
      (./schema/automation/ReactionAction.dhall).RunCommand
        { command = "make"
        , args = [ "deploy" ]
        , workingDir = None Text
        , timeout = None Integer
        , env = [] : List { mapKey : Text, mapValue : Text }
        }
  }
```

> **Dhall note:** Integer literals require a `+` prefix for positive values (e.g., `+60`, `+300`). Use `None Integer` for optional integers.

Scheduled actions use the `ScheduledAction` type internally, which supports `RunCommand`, `EmitEvent`, and `Notify` but not nested `Schedule` (no recursive scheduling).

### ExecutionPolicy

Controls where and how actions run:

```haskell
, execution =
  { allowLocal = True      -- run on the local machine
  , allowCI = False         -- block execution in CI
  , maxConcurrency = Some +4  -- at most 4 concurrent actions
  }
```

## 7. Automation: Ingest and Run

### Ingest VCS history

Normalize your git history into the event store:

```bash
mori automate ingest git
```

```
Ingested 42 changesets, 5 refs (47 events written)
```

On subsequent runs, only new commits since the last ingestion are processed:

```bash
mori automate ingest git
```

```
Ingested 3 changesets, 0 refs (3 events written)
```

Ingestion is idempotent — running it multiple times without new commits produces no events.

To ingest from a different repository path:

```bash
mori automate ingest git --path /path/to/repo
```

### Run the reactive engine

Start the long-running automation engine:

```bash
mori automate run
```

```
Starting automation engine...
  Config: mori.automation.dhall
  Config hash: a1b2c3d4...
  Queues initialized.
  Processors initialized. Listening for events...
  Queue workers started.
```

The engine:

1. Loads and observes the automation config (emitting a `MoriAutomationObserved` event with a content hash)
2. Creates pgmq queues for scheduled and queued work
3. Starts concurrent processors and projections:
   - **Automation processor** — matches repository events against selectors and triggers reactions
   - **Executor processor** — executes the triggered reaction actions
   - **Registry projection** — projects project events into the read model
   - **Workflow projection** — maintains workflow state
   - **Extension projections** — maintain plans, DDD, tech-radar, and related catalogs when enabled
4. Starts queue workers for scheduled actions, scheduled reactions, and FIFO queued automations

To use a custom config path:

```bash
mori automate run --config my-automation.dhall
```

Stop the engine with `Ctrl+C` (SIGINT) or SIGTERM — it shuts down gracefully.

## 9. Advanced: Scheduled Actions

Schedule a reaction action to run after a delay using `ReactionAction.Schedule`:

```haskell
let EventSelector = ./schema/automation/EventSelector.dhall
let ReactionAction = ./schema/automation/ReactionAction.dhall
let ScheduledAction = (./schema/automation/ReactionAction.dhall).RunCommand

in  { events =
      [ EventSelector.ChangesetSelector
          { name = "deploy-trigger"
          , paths = [ "deploy/**" ]
          , branches = [ "main" ]
          , messagePatterns = [] : List Text
          }
      ]
    , reactions =
      [ { name = "delayed-deploy"
        , on = [ "deploy-trigger" ]
        , actions =
          [ ReactionAction.Schedule
              { delaySeconds = +300
              , action =
                  ScheduledAction
                    { command = "make"
                    , args = [ "deploy", "staging" ]
                    , workingDir = None Text
                    , timeout = Some +600
                    , env = [] : List { mapKey : Text, mapValue : Text }
                    }
              }
          ]
        }
      ]
    , execution =
      { allowLocal = True
      , allowCI = False
      , maxConcurrency = None Integer
      }
    }
```

**How it works:**

1. When a matching event is detected, the reaction enqueues the action onto a pgmq queue with the specified delay
2. A shibuya worker polls the queue and executes the action once the delay has elapsed
3. The worker runs alongside the automation subscriptions inside `mori automate run`

## 10. Advanced: Hot-Reload

When `mori automate run` is active, you can modify `mori.automation.dhall` (add selectors, change reactions, etc.). On the next restart of `mori automate run`, mori:

1. Loads the updated config
2. Computes a new content hash
3. Emits a `MoriAutomationObserved` event if the hash changed
4. The automation subscription picks up the new config and starts matching with the updated selectors

This means you can iterate on your automation rules without losing event history — only future events are matched against the new config.

## 11. Complete Example

This walkthrough takes you from zero to a working automation setup.

### Set up the project

```bash
# Start in your project directory
cd ~/projects/payments

# Initialize mori (assumes schema/ directory exists)
mori init --name payments

# Verify setup
mori doctor
```

### Configure project identity

Edit `mori.dhall`:

```dhall
let Schema = ./schema/package.dhall

in  Schema.Project::{
    , project = Schema.ProjectIdentity::{
      , name = "payments"
      , namespace = "acme"
      , type = Schema.PackageType.Application
      , description = Some "Core payments service"
      , language = Schema.Language.Haskell
      , domains = [ "Payments" ]
      , owners = [ "fintech-platform" ]
      }
    , repos =
      [ Schema.Repo::{ name = "main", github = Some "acme/payments" }
      ]
    , packages =
      [ Schema.Package::{
        , name = "payments-core"
        , type = Schema.PackageType.Library
        , language = Schema.Language.Haskell
        , path = Some "payments-core"
        , description = Some "Core domain logic"
        , visibility = Schema.Visibility.Internal
        , dependencies = [ Schema.Dependency.ByName "aeson" ]
        }
      ]
    , dependencies = [ "aeson" ]
    , agents =
      [ Schema.AgentHint::{
        , role = "backend"
        , description = Some "Backend development"
        , includePaths = [ "payments-core/" ]
        , relatedPackages = [ "payments-core" ]
        }
      ]
    }
```

### Validate and register

```bash
# Type-check the config
mori validate

# View the summary
mori show

# Register in the local registry
mori register --local
```

### Set up automation

Create `mori.automation.dhall`:

```haskell
let EventSelector = ./schema/automation/EventSelector.dhall
let ReactionAction = ./schema/automation/ReactionAction.dhall

in  { events =
      [ EventSelector.ChangesetSelector
          { name = "core-changes"
          , paths = [ "payments-core/**" ]
          , branches = [ "main" ]
          , messagePatterns = [] : List Text
          }
      ]
    , reactions =
      [ { name = "test-on-core-change"
        , on = [ "core-changes" ]
        , actions =
          [ ReactionAction.RunCommand
              { command = "cabal"
              , args = [ "test", "payments-core" ]
              , workingDir = None Text
              , timeout = Some +120
              , env = [] : List { mapKey : Text, mapValue : Text }
              }
          ]
        }
      ]
    , execution =
      { allowLocal = True
      , allowCI = False
      , maxConcurrency = None Integer
      }
    }
```

### Ingest, run, and observe

```bash
# Ingest existing git history
mori automate ingest git

# Start the reactive engine (runs in foreground)
mori automate run

# --- In another terminal ---

# Make a change and commit
echo "-- update" >> payments-core/src/Lib.hs
git add -A && git commit -m "Update core logic"

# Ingest the new commit
mori automate ingest git

# The running engine will match the event and trigger the test reaction.
# Check what happened:
mori automate inspect

# Explain a specific event (use the global position from inspect output)
mori automate explain 15
```
